## Overview [sr-only] \{#overview\}
Master CSS directives describe token definitions, reusable utility names, named conditions, and source discovery. The compiler consumes them before delivering CSS to the browser. Write declarations, selectors, cascade layers, media queries, and keyframes using native CSS.

```css name=app.css
@import "@master/css";

@theme {
  :root, :host { --color-brand: #4f46e5; }
  [data-theme="ocean"] { --color-brand: #0369a1; }
}

@custom-media --wide (width >= 60rem);
@mixin --card-layout { display: grid; gap: var(--spacing-md); }

.card {
  color: var(--color-brand);
  @media (--wide) { grid-template-columns: 1fr 1fr; }
}
```

## Entry markers \{#entry-markers\}
### `@import "@master/css"` \{#import-mastercss\}
The package import is the only project entry marker. It loads the preset's native CSS, including its stable layer order, base styles, and native keyframes, and identifies the stylesheet that receives generated utility CSS.

```css
@import "@master/css";
```

Explicit standalone compiler and manifest APIs remain available. A manifest alone does not load native CSS; applications using runtime or server rendering must also deliver the relevant native stylesheet.

### Removed lightweight entry marker \{#master-entry\}
`@master entry;` is removed and reports an error. Replace it with the package import. There is no replacement lightweight marker.

### Local file URLs

Node file compilation reads CSS import names using CSS escaping and case rules.
Relative `@import` and `@reference` URLs resolve their pathname against the source
file: percent escapes identify filename characters, while query strings and
fragments are excluded from the filesystem path. For example,
`"./tokens%20%23.css?v=1#theme"` reads a sibling file named `tokens #.css`.
Existing bare relative CSS paths such as `"tokens.css"` are also expanded. Bare
package imports without a matching local file remain available to the host
resolver. Reference files remain compile-time context and do not emit their native CSS.
For a prepared virtual stylesheet, the host's explicit filesystem source owner
also supplies the base for relative CSS references. Resources in a referenced
theme token remain relative to the reference file when used elsewhere.

### Stylesheet boundaries and resource URLs

CSS import conditions and layers apply to the imported stylesheet. Moving or
combining files must preserve those boundaries and the URLs of their images and
fonts. A resource used by an imported managed definition retains that definition's
source location when the compiled stylesheet uses it.

Native CLI project scanning reads global definitions from unqualified imports before lowering native variants. A qualified import may contain native CSS, including native rules with `@variant`, but cannot contain global Master definitions. Put those definitions in an unqualified import or a separate `@reference` input.
Relative `@source` patterns are resolved from the file that declares them, and
`@reference` supplies definition context without adding its scanning sources or
exporting its managed classes. Reading this metadata does not publish stylesheet
or resource files. CLI file export is a separate delivery step and does publish the required assets.

The prepared-files compiler method `compileStylesheets()` returns separate CSS
assets and accepts a `resourceURLs` map for parsed `url()` and `image-set()` values.
The map is keyed by source file ID, then by the decoded resource URL; replacements
must be root-relative or absolute. Use absolute replacements when output files
can be served from different origins. All returned stylesheets must be delivered.
Fragment-only references such as `url(#filter)` remain local references.

This prepared-files method requires the host to supply import resolution, resource
mappings and reference context. CLI file export and Vite production builds publish
the required stylesheet and resource assets. Node file and rendered-stylesheet APIs
opt in through their `delivery` options; their caller must publish every returned
asset. `--no-export` and calls without delivery options retain their separate
single-output limitations. Without resource mappings, the host must preserve
original URL bases. See [CSS imports](/guide/css-imports) for the delivery boundaries.


### Preparing native CSS for another transformer

Compiler hosts can opt into `preserveNativeSource: true` when another transformer
needs the untouched native portions of a stylesheet. Master definitions are still
consumed and native `@variant` rules are still lowered, while unrelated comments,
empty rules, value spelling, and rule boundaries are retained. The option defaults
to `false`, preserving the compiler's normal native CSS normalization.

Source preservation cannot be combined with enabled native pruning. Passing a class list alone does not enable pruning. `preserveNativeCSS: false` still suppresses native output. The option
does not prevent subsequent host transforms from optimizing the result or rewriting
its source map, and it does not discover new Master definitions or generated-global
references introduced by a later transform.


### Continuing resource rendering after host transforms

`compileRenderedStylesheet()` and `compileBrowserStylesheet()` accept an optional
`emittedGlobals` resource-count snapshot when another output already supplies
generated theme variables. Positive counts suppress duplicate emission;
zero counts do not. New references still emit their transitive resource closure.
The returned snapshot includes the external context and resources required by this
render, without changing the input snapshot. Omitting the option preserves normal
standalone rendering.

This context prevents a later render from replacing an already processed variable
with its original manifest value. It does not run host plugins on newly generated
CSS. Hosts remain responsible for processing that new CSS and publishing its
resources while preserving plugin ordering and source ownership.

## Reference context \{#reference-context\}
### `@reference` \{#reference\}
Use a reference when compilation needs definitions from another stylesheet without importing its native rules.

```css name=Button.module.css
@reference "../app.css";

.button {
  padding: var(--spacing-md);
  @variant manual-dark { color: white; }
}
```

A reference supplies `@theme`, `@mixin`, `@custom-media`, and `@custom-variant` definitions. It does not deliver the referenced file's native CSS, generate its classes, or add its scanning sources. Used tokens can still cause the local output to include their required theme declarations. Keyframes need an actual `@import` or another delivered stylesheet.

References must be top-level statements containing one quoted resource. Relative paths use the declaring stylesheet's directory. Package references resolve exported CSS entries. References are not entry markers.

Vite, Next.js, and Webpack supply project definition context to local stylesheets, CSS Modules, and SFC styles. An explicit reference is useful for dependencies outside that context or standalone compilation. Local stylesheets do not become scanning or pruning roots. CSS Modules and scoped hosts must deliver generated theme selectors globally.

The standalone API accepts absolute `referenceFiles` and `transformNativeStylesheets: true`. Definition files precede authored references; local definitions follow both. Referenced resources retain their defining file as owner. `emittedGlobals` explicitly identifies theme variables already delivered alongside an output; project discovery alone does not establish that ownership. The snapshot contains variable counts only.

## Project settings \{#project-settings\}
### Removed `@settings` \{#settings\}
The entire directive and manifest `settings` field are removed. Use the `!` suffix on a particular class for importance. Use native selectors, nesting, or `@scope` to define where stylesheet rules apply. Master CSS does not apply a global important or selector-scope setting.

## Theme and variants \{#theme-and-variants\}
### `@theme` \{#theme\}
Declare custom properties under explicit native selectors. A theme block must be top-level and has no prelude or modifiers.

```css
@theme {
  :root, :host {
    --color-panel: white;
    --color-panel: oklch(98% .01 250);
  }

  @media (prefers-color-scheme: dark) {
    :root, :host { --color-panel: #111827; }
  }

  [data-theme="ocean"] {
    --color-panel: var(--color-ocean);
  }

  :root { --color-ocean: #082f49; }
}
```

The compiler preserves selector order, declaration order, repeated declarations, and native nesting. Supported conditional wrappers are `@media`, `@supports`, `@container`, `@scope`, and `@starting-style`. Only custom-property declarations belong in `@theme`; use ordinary stylesheets for other declarations, keyframes, or layer rules. `@variant` is not accepted inside a theme.

Theme declarations are emitted in the `theme` layer. A used token retains every authored declaration of that token in every scope, plus transitive token dependencies. Source scanning never selects one theme scope or removes a branch. The browser computes the winning value through its ordinary cascade and inheritance. Tooling exposes authored scoped values; it does not claim to know the value for a particular DOM element.

The default preset uses native `light-dark()` for adaptive color and shadow tokens. Both `var()` branches remain live. Its native CSS sets the root to `color-scheme: light dark`, with explicit light/dark `data-theme` selectors for elements and shadow hosts. The host otherwise inherits its ancestor's scheme. These declarations are ordinary CSS outside `@theme`; neither the compiler nor runtime chooses a color branch. Preset `@light` / `@dark` variants continue to test system preference, independently of manual `color-scheme`. See [Colors](/guide/colors#native-color-scheme-and-manual-themes) for nesting, browser support and migration.

### Native selectors replace theme modes \{#theme-mode\}
`@theme dark` and other mode preludes are removed. Put the selectors and conditions inside `@theme`, as in the example above. No implicit `:root` or `:host` selector is inserted.

### Native activation replaces `@mode` \{#mode\}
`@mode` is removed. Theme activation comes from native selectors and queries. Define a separate `@custom-variant` if markup needs a matching named condition; its selector is explicit and does not automatically include descendants or insert `:where()`.

```css
@custom-variant ocean {
  &:where([data-theme="ocean"], [data-theme="ocean"] *) { @slot; }
}
```

This enables `color:white@ocean`. Theme declarations can independently use `[data-theme="ocean"]`. Add explicit `:host(...)` selectors where a shadow tree requires them.

### Native custom properties replace inline expansion \{#theme-inline\}
`@theme inline` is removed. Token classes emit `var(--name)` references. Functions, fallbacks, cycles, inheritance, and scoped values retain native custom-property behavior; Master CSS does not substitute a selected theme value into each declaration.

### Native styles replace static resources \{#theme-static\}
`@theme static` is removed. Put properties that must always be delivered in native CSS, for example `@layer theme { :root { --app-version: 1; } }`. Keyframes are always native stylesheet rules, outside Master-generated layer blocks:

```css
@keyframes reveal {
  from { opacity: 0; }
  to { opacity: 1; }
}
```

Animation property utilities remain available. The engine, runtime, server renderer, and hydration data do not register, infer, prune, or recreate animation definitions. Load the stylesheet that owns `reveal` before using `animation:reveal|.2s`.

CSS Modules may rename literal animation identifiers. To consume a global native keyframe across bundlers, declare an animation token in the global theme (for example `--animate-reveal: reveal .2s`) and use `animation: var(--animate-reveal)` inside the module. This retains normal variable inheritance and avoids depending on a bundler-specific `global()` animation syntax.

### `@custom-media` \{#custom-media\}
Define named media queries using the [CSS Media Queries specification](https://drafts.csswg.org/mediaqueries-5/#custom-mq):

```css
@custom-media --wide (width >= 60rem);
@custom-media --reading (--wide), print;
@custom-media --outside not (--reading);
@custom-media --enabled true;
@custom-media --disabled false;

@media (--reading) { .article { max-width: 70ch; } }
```

Names begin with `--`. CSS references use `(--name)`; markup uses `@name`, and a local named block uses `@variant name`. The same registry is used in native CSS, theme scopes, custom variants, utility definitions, and markup queries.

Definitions support query lists, forward references, `true`, `false`, nested boolean expressions, negation, and media types. Expansion is logical: a list retains its disjunction, and negation applies to the complete referenced expression. The compiler emits ordinary media queries, using nested blocks where a single query cannot express mixed media types. No browser custom-media API or JavaScript runtime registration is required.

Undefined, cyclic, and invalid references are compilation errors. A later same-name definition wins. A `@custom-media --name` and `@custom-variant name` cannot share a name. The preset has no `--breakpoint-*` tokens. A project custom property with that prefix remains ordinary CSS and never implicitly declares a media condition. Use native lengths or independently named layout tokens for width caps. Imports that retain external URLs cannot contain unresolved custom-media queries; resolve those stylesheet imports before lowering or use ordinary native queries on the import.

### `@custom-variant` \{#custom-variant\}
Define a named selector or condition with an explicit `@slot;`:

```css
@custom-variant hocus {
  &:hover, &:focus-visible { @slot; }
}

@custom-variant motion-safe {
  @media (prefers-reduced-motion: no-preference) { @slot; }
}
```

Use `bg-blue-60@hocus` or `opacity:1@motion-safe` in markup, or `@variant hocus` in a stylesheet rule. Native selector and condition wrappers express the transformation; supported Master layer wrappers use the established layer names. Every branch must reach a bare `@slot;`. Parameters, declarations in the variant definition, implicit slots, and mixin invocation are not supported. Later same-name definitions replace the complete earlier definition.

## Utilities and native styles \{#managed-definitions\}
### Native defaults \{#defaults\}
Write native defaults in `@layer defaults`. The removed `@defaults` directive remains an error.

### Native components \{#components\}
Write native component selectors in `@layer components`. The removed `@components` directive remains an error.

```css
@layer components {
  .button {
    display: inline-flex;
    padding: var(--spacing-md);
    &:focus-visible { outline: 2px solid currentColor; }
  }
}
```

Native rules are delivered according to the stylesheet import graph. A mixin definition is available to markup and native `@apply`; it emits nothing until used.

### `@mixin` \{#utilities\}
Master implements a static compilation subset of the experimental [CSS Mixins specification](https://drafts.csswg.org/css-mixins-1/#mixin-rule), not a complete browser polyfill. Definitions have dashed names and must be unconditional stylesheet-level rules.

```css
@mixin --card-layout {
  display: grid;
  gap: var(--spacing-md);
  &:hover { outline: 1px solid currentColor; }
}

@mixin --grid-cols(--cols <integer>) {
  display: grid;
  grid-template-columns: repeat(var(--cols), minmax(0, 1fr));
}
```

Use `card-layout` and `grid-cols(3)@sm` in markup. A no-parameter mixin may also be called with empty parentheses. Positional parameters may be untyped or use `<integer>`, `<number>`, `<string>`, or `<custom-ident>`. Static defaults use a colon, for example `--cols <integer>: 2`. Numbers must be numeric literals; grid counts and spans must also be positive integers. Strings require quotes: `text("sm")` is valid, `text(sm)` is not.

### Direct declarations and recipes \{#named-and-enumerated-classes\}
Use full native property names for direct values: `display:block`, `padding:1rem`, `color:red`, `background:#fff`. Raw property abbreviations and single-declaration preset aliases are removed. Genuine native names such as SVG `r` retain their native meaning.

Named tokens keep familiar spellings such as `p-md`, `fg-red-60`, `font-sm`, `font-sans`, and `font-bold`. Rust owns these mappings; presets define their values in `@theme`, without per-family registration directives. `font-*` chooses its property by token existence. If several font namespaces contain the same key, use an explicit family such as `font-size-brand` or `font-family-brand`.

### Named mixin families \{#named-token-patterns\}
A mixin with exactly one `<string>` parameter gains a named family when a matching primary theme token exists:

```css
@theme {
  :root, :host {
    --text-hero: var(--font-size-5xl);
    --text-hero--line-height: 1.15;
    --text-hero--letter-spacing: -.03em;
  }
}
@mixin --text(--step <string>) {
  font-size: var(ident("--text-" var(--step)));
  line-height: var(ident("--text-" var(--step) "--line-height"), normal);
  letter-spacing: var(ident("--text-" var(--step) "--letter-spacing"), normal);
}
```

`text-hero` calls `--text("hero")`. `ident()` folds only when all its inputs are known and produces ordinary CSS custom-property references. Companion tokens containing `--` after the primary name do not create classes. Companions without a primary token create no class; missing companions use the authored fallback.

The rule is generic, with no engine-specific typography recipe. `font-sm` sets only font size; `text-sm` also sets line height and letter spacing. Typography recipes do not set family, weight, or color. The preset's explicit typography scale is an intentional visual change; check headings, paragraphs and wrapping at desktop and mobile widths.

Exact no-parameter mixins take priority. Families use the longest prefix; at the same prefix a named mixin wins over the built-in token mapping. A selected family with an unknown token reports an error and does not retry another interpretation. Built-in negative values and color opacity remain available where supported, but named mixins do not inherit those operations. `p-4` means the token named `4`; `grid-cols-3` does not imply a numeric argument.

### Static arguments \{#dynamic-values\}
Arguments must be statically known. External `var()`, `attr()`, and other browser-dependent values cannot be passed as parameters. A known outer mixin parameter may be forwarded using `var(--parameter)`. Ordinary theme `var()` references in the mixin body remain native CSS and keep all authored scopes.

```css
@mixin --pair(--size) {
  width: var(--size);
  height: var(--size);
}
```

Use `pair(2rem)`. Dynamic dimensions belong in native CSS, for example `.pair { width: var(--size); height: var(--size); }`.

### Native property precedence \{#literal-and-raw-values\}
`property:value` always keeps its native meaning and cannot be overridden by a mixin. Within the same layer and conditions, direct property classes sort after recipes, so a direct declaration can override one property of a recipe independently of markup order. Existing selectors, conditions and `!` modifiers apply to both forms.

### `@apply` \{#reusing-a-matched-value\}
Apply a mixin inside a native style rule or another mixin:

```css
.caption {
  color: currentColor;
  @apply --text("sm");
  font-weight: 600;
}
```

Expansion occurs at the original declaration position, preserving duplicates, importance, nested selectors and conditions. It does not generate a separate `.text-sm` rule. `@apply` accepts one mixin call, not a utility class list. `@compose` remains removed.

Parameters may be used on the applying element, including `&:hover` and condition wrappers. Cross-element parameter use, reassignment, selector or condition interpolation, recursion, overloads, `@private`, `@contents`, contents blocks and unsupported parameter types report compilation errors. Unknown mixins and invalid arity or types include source diagnostics. Relative URLs preserve the defining or calling file's ownership.

### Whole-definition replacement \{#whole-definition-replacement\}
The last definition with the same decoded name replaces the entire previous mixin, including parameters, body, dependencies and cached expansion. An empty definition remains registered. Forward nested calls resolve against the final registry. There is no parameter overloading.

### Definition scope and imports \{#definition-scope-and-imports\}
`@theme`, `@mixin`, `@custom-media`, and `@custom-variant` are top-level definitions. Registering them inside a layer or conditional wrapper is an error. Mixin bodies may contain supported native conditions and named `@variant` blocks.

Classes from source scanning, safelists, engine APIs and runtime DOM changes are usage roots. An `@apply` in delivered native CSS is also a root; one inside an unused mixin or undelivered `@reference` stylesheet is not. Dependency collection occurs after parameter binding and `ident()` folding. Used tokens preserve every authored scope and transitive dependency. Removing the final root releases its resources; native CSS resources remain pinned through `emittedGlobals`.

Runtime manifests retain unused definitions for future DOM classes. On-demand generation concerns CSS and resource output. Native CSS pruning remains opt-in; keyframes retain native delivery. Qualified imports must contain native CSS only. Load definitions through an unqualified import or reference.

`@utility`, its `from()` mapping syntax, and `--master-value()` are removed and report errors. Use the `rc-mixins` migration profile with the saved Manifest v2. Current manifests are v3 with languageVersion 5 and binding ABI 16; hydration and transition structures remain v2 and reject old language data.

## Source boundaries \{#source-boundaries\}
### `@source` \{#source\}
Ordinary application sources use the integrations' and CLI's default discovery. Add explicit exceptions when needed:

```css
@source "../content/**/*.mdx";
```

### `@source not` \{#source-not\}
Exclude matching files from the source set:

```css
@source not "../content/drafts/**";
```

Includes are combined as a union, then all excludes are subtracted. Every relative pattern resolves from the stylesheet that declares it, including bare `src/**`, `./src/**`, imported files, and `@source not`. A reference does not contribute scanning sources.

File-resolving APIs require a declaring file or explicit base file. Source-only directive inspection can return unresolved metadata; it must not invent a filesystem base. The scanner's programmatic `cwd` option retains its existing meaning for scanner options supplied directly through that API.

## Candidate policy \{#candidate-policy\}
### `@safelist` \{#safelist\}
Add complete class candidates that cannot appear literally in scanned source:

```css
@safelist "opacity:1";
@safelist "bg-blue-60@dark";
```

Candidates use the same matching and diagnostic policy as discovered classes. Keep dynamic alternatives bounded and explicit.

### `@blocklist` \{#blocklist\}
Remove unwanted complete candidates with exact strings or `*` and `?` wildcard patterns:

```css
@blocklist "debug-*";
@blocklist "example-token";
```

The stylesheet grammar does not interpret slash-delimited patterns as regular expressions. Wildcard policy belongs in the blocklist; a safelist supplies complete classes.

## Removed utility composition \{#rule-local-composition\}
### `@compose` (removed) \{#compose\}

`@compose` is no longer supported. Compilation reports `removed-compose-directive` wherever the at-rule appears, including native rules and utility definitions.

Write native declarations, selectors and conditions in stylesheets. Share design values through CSS custom properties. Use Master utilities directly in markup, or share native classes and component interfaces when several elements need the same behavior.

```css
@layer components {
  .button {
    display: inline-flex;
    padding: var(--spacing-md);
    border-radius: var(--radius-lg);

    &:focus-visible {
      outline: 2px solid var(--color-accent);
      outline-offset: 2px;
    }
  }
}
```

When migrating an existing statement, preserve its expanded declarations, nested selectors, conditions, importance and destination layer. Replacing it with declarations preserves the current style but removes the dependency on the original utility: future utility changes no longer update that rule. Do not rename it to `@apply`; Master CSS does not provide a replacement composition directive or a native mixin polyfill.

The compiler no longer exposes compose IR or composition traces. Tooling removes compose canonicalization and structural directive fixes, including `composeDirective`, `includeDirectiveFixes`, `preferNativeDeclarationsInCompose`, `preferVariantBlocksInCompose`, and CLI `--fix-directives`. ESLint removes `configs.stylesheet`; its recommended config still handles classes in markup and class builders. `preferCompositionUtilities` continues to apply to markup class lists.

The RC migration command reports an occurrence for manual migration and leaves the statement unchanged. See [Migrating from Master CSS v2 RC](/guide/migration/v2-rc) for the remaining migration steps.

## Conditional blocks \{#conditional-blocks\}
### `@variant` \{#variant\}
Use one named condition inside a native style rule or utility definition:

```css
@custom-media --wide (width >= 60rem);
@custom-variant manual-dark {
  @media (prefers-color-scheme: dark) { @slot; }
}

.notice {
  @variant manual-dark { color: white; }
  @variant wide { padding: 2rem; }
  @supports (display: grid) { display: grid; }
  &:hover { opacity: .8; }
}
```

`@dark`, `@light`, and query-form `@variant media(...)` blocks are removed. Use native `@media`, `@supports`, and `@container` for queries. Unknown names are errors. A named `false` custom media is valid and emits no branch. Markup still supports named conditions such as `@dark` and its existing explicit native query suffixes.

## CLI stylesheet assets \{#cli-stylesheet-assets\}

When using `master-css generate --output dist/output.css`, deploy the generated
sibling CSS and resource files together with `output.css`. The entry imports
those CSS files, preserving local import conditions and external CSS imports.
Relative images and fonts are resolved from their original source stylesheet
and copied beside the output. Referenced definitions can use resources from the
reference file without emitting that file's native CSS.

In file-export watch mode, missing imported stylesheets or resources are reported
while the last successful export stays available. Restoring the files triggers a
rebuild that also includes source edits made while dependency preparation failed.

Custom stylesheet collection hosts can independently select project native CSS,
Master base CSS, and generated utility rules with `includeNativeCSS`,
`includeMasterBaseCSS`, and `includeGeneratedCSS`. Excluding native output keeps
authored definitions available to used utilities. Local imports still connect
selected output; imports to empty excluded branches are omitted so they do not
establish cascade layers. External imports from excluded stylesheets are omitted.
The compiler option `preserveNativeCSS: false` removes raw native CSS and external
imports while keeping compiled native `@variant` in included stylesheets.

When resource URLs are rewritten for delivery, ranged compiler diagnostics still
refer to the original stylesheet and source position, including imported files.

This applies to CLI file export. `--no-export` and existing file/build CSS delivery
paths still have separate import-graph limitations.

Node project manifest loading (`compileProjectManifest`, `loadProjectManifest`,
and their synchronous variants) preserves each imported stylesheet while
compiling shared definitions. Pure native qualified imports may retain external imports without fetching them. Global definitions must be loaded through unqualified imports or references.
`@reference` supplies definitions for resource resolution and contributes dependencies;
its native rules, standalone utility classes, and source policies are not imported.
Every relative `@source` and `@source not` pattern resolves from the declaring file, including bare patterns and imported files. Explicit project entries merge in the supplied order.
These APIs return a manifest and metadata; they do not publish native CSS assets.



`compileManifestFileSync(file, { baseManifest, delivery, preserveNativeCSS: true })`
can prepare a file and its imports for publication as separate stylesheets. The
Node host resolves local imports, package entries and references; the existing
Rust graph compiler retains external import order, conditions and native
native variant positions. `delivery` uses the same URL callbacks as standalone
stylesheet collections: `entryURL`, `stylesheetURL(file)` and `resourceURL(file)`.
Each stylesheet must have a distinct final URL.

The returned `stylesheets` include the entry and every required imported CSS
asset; copy each returned `resources` file to its `href` and publish each
stylesheet at its `href` before loading the entry. Compilation performs reads
and returns assets without writing output files. `css`, `nativeCSS` and
`generatedCSS` describe the entry only, so publishing only `css` is insufficient.
Relative resource URLs are rewritten for their original source owner and retain
query strings and fragments. Reference-only stylesheets are not published.
Omitting `preserveNativeCSS` preserves native CSS across compiler APIs. Explicit `false` suppresses the native portion; it does not enable pruning.
Omitting `delivery` continues to use the legacy single-string file path, whose
external-import limitations remain; other build and `--no-export` consumers
still require their own asset publishing integration.

## Vite production stylesheet delivery \{#vite-stylesheet-delivery\}

Vite production builds preserve managed CSS imports as separate stylesheet assets.
Local imports containing external CSS keep their media, supports and layer scopes,
and external imports retain their position relative to local CSS. Ordinary bundle
rules before or after the managed entry keep that order.

Deploy the complete build output, including generated `master-css-*` stylesheets
and resource files. The CSS entry alone does not contain all rules. Managed and
Node-resolved package resources keep their source ownership, query strings and
fragments. Node-resolved package CSS retains native rules even when project CSS is
pruned. Production CSS imports use Vite's string or regular expression aliases,
package import conditions, and custom plugins that resolve imports to CSS files on
disk. Entry markers and definitions can come from these aliased files or from
null-prefixed virtual `.css` modules supplied by plugin loaders. Virtual imports
retain their original CSS, conditions and layers, including nested imports. Query
suffixes remain part of virtual module identities.
Virtual resource ownership, preprocessors, alias resolution for `@reference` or
resource URLs, watch/HMR delivery, and other bundlers still need further integration.

Vite production builds preprocess Sass entries and imports using the configured
Sass options, aliases and partial dependencies. String or function `additionalData`
runs once per source in each build. CSS imports left by Sass retain their conditions
and source order in the compiler graph. Relative partial resources keep their
original owner, and changing a partial triggers a rebuild. CSS Modules retain Vite's
scoped class names and exports; raw text requests bypass stylesheet compilation.
In Sass, write the entry as `@import url("@master/css");` so Sass preserves it
as a native CSS import for Master CSS to resolve.
Managed `?inline` imports return compiled CSS without injecting a stylesheet:

```js
import css from './style.css?inline'

const style = document.createElement('style')
style.textContent = css
document.head.append(style)
```

Each inline request has its own stylesheet output, including when another file is
loaded automatically. Safe local imports are expanded; imports that protect CSS
scope or external loading remain linked assets. Import-free strings can also be
used with `CSSStyleSheet.replaceSync()`. Asset URLs retain the emitted asset base
when the string is inserted into another document location. Inline CSS content
participates in hashed JavaScript filenames.

During an SSR build, inline CSS uses the configured public `base` for asset URLs.
With Vite’s default `ssrEmitAssets: false`, deploy the matching client build’s
assets. Enable `ssrEmitAssets` when the server build should also publish them.

Inline asset URLs also use Vite’s `experimental.renderBuiltUrl` callback. The
callback receives `hostType: "js"` for inline strings and `hostType: "css"` for
retained stylesheet files. JavaScript URLs can use runtime expressions; stylesheet
files use static URLs or relative-path decisions. URL mapping changes participate
in retained stylesheet filenames as well as the importing JavaScript hash.

Production Sass compiler diagnostics use Vite's preprocessing maps to identify
the original file or partial, including inline requests and Sass imported by CSS.
Unchanged tokens retain their original ranges. Sass expansion can provide only
the originating segment; diagnostics explain when an exact token range is
unavailable. Injected content or an `additionalData` callback without a usable map
can retain a clearly identified preprocessed location. Internal diagnostic maps
do not enable published source maps.

Production CSS Modules, including Sass modules, retain Vite's scoped names,
named/default exports, cross-file `composes`, global selectors and
`localsConvention`. Exported scoped names participate in native CSS usage. Native
CSS is preserved by default; when pruning is enabled, that usage keeps their rules.

Production build-watch tracks resolved CSS Modules `composes` dependencies,
including nested compositions. Editing a composed file rebuilds its consumers;
correcting an invalid Master CSS directive in that file recovers the build.
When Vite provides no original location for composed CSS, diagnostics explicitly
identify the preprocessed location.

Development CSS and Sass modules retain their scoped exports and native rules.
Editing the module or a resolved `composes` dependency updates both its CSS and
exports through HMR, including modules that use local `@variant`.

During development, editing a CSS project entry updates ordinary stylesheet
imports and its `?inline` and `?raw` consumers. Inline requests export processed
CSS without injecting a stylesheet; raw requests retain the original source.
Sass stylesheets attached through a `?url` value update in place during development,
including paths under a configured base, aliases, and allowed files outside the project root.
For CSS and Sass Modules, `?inline` exports the scoped CSS without injecting it,
while `?raw` retains the authored source. Vite 8.2.2 rejects `?url` for
`.module.css` and `.module.scss` paths, even with `css.modules: false`.

Ordinary Sass `@use` and nested `@forward` partials update their stylesheet
consumers during development, including `?inline` and attached `?url` values.
Deleting a partial reports the Sass error; restoring it recovers the stylesheet
without reloading the page. Relative resources keep the partial’s directory as
their source location.
Server-side `?inline` consumers also receive updated Sass output. After restarting
the Vite dev server, connected pages reload and reconnect; stylesheet requests
and subsequent edits use the new server state. This also works in middleware
mode when Vite’s WebSocket connection is attached to the host HTTP server.
Closing one configured development environment leaves stylesheet loading and
updates available in the remaining environments. An initialized replacement can
stay idle while the other environments close, then load styles when needed.
With per-environment start/end hooks enabled, existing Sass partials continue
updating as other environments start.
The plugin array can also be reused across concurrent Vite roots. Each resolved
configuration keeps its own stylesheet, manifest, and rendering state; restarting
or closing one development server leaves the others available. Client and SSR
builds retain their own configured asset bases.

Pre-render and progressive builds and development CSS entries support qualified
local imports whose descendants retain external imports. The browser applies the
original layer, supports, and media conditions to the delivered child stylesheets.
Development entries serve retained child CSS and resources under the configured
base. Loading an entry normally and through SSR `?inline` shares its source identity.
In pre-render mode, changing the project manifest reloads the page to refresh
server-rendered rules; progressive mode applies the update through its runtime.
Native-only CSS edits do not require a manifest reload.
Editing a retained development CSS child or an image resource updates connected
pages without reloading them. Resource filenames can include percent-encoded
spaces, Unicode, `#`, `?`, and `%`, while separate query strings and fragments
retain their meaning. Resources respect the original file's `server.fs.deny`.
Previously published CSS and resource URLs retain their contents until their
server context closes, including URLs held by SSR inline CSS consumers. Closing
another root that uses the same plugin array, or closing the SSR environment,
leaves the remaining client's resource delivery available. Retained versions use
server memory and temporary files until that context closes.
Each development resource version uses the same captured bytes for its URL and
published contents, even when the source is replaced or deleted before the CSS
is delivered. Deleting a referenced resource reports a development compilation
error while previously published versions remain readable. Restoring the resource
updates connected pages and dismisses the error overlay without reloading them.
An initialized replacement environment can remain idle while the old environment,
client, and SSR environments close, then load new retained graphs and receive
child stylesheet updates. This works with either value of
`server.perEnvironmentStartEndDuringDev`.
Restarting a standalone or middleware development server releases the previous
context's resource copies. Connected pages reload and reconnect to new asset URLs;
subsequent child CSS and image edits update without another page reload.
Local stylesheets compile imported local rules and retain qualified child imports
and resources in development and production builds. This also applies when the
root and intermediate stylesheets contain only native CSS, and `@variant` appears
only in an imported descendant. These graphs remain local stylesheets rather than
becoming project entries or native CSS pruning roots.
CSS Modules keep the root module's scoped exports; SSR inline requests return
compiled CSS, and raw requests retain the authored source. Child CSS and resource
edits update connected development pages; CSS Module consumers need the HMR
handling described below to retain page state. Production inline
strings publish their retained assets as well. Local entries keep their positions
within the built stylesheet, and content-based asset names are independent of
asynchronous entry registration order.
Local CSS and Sass imported through `?url` deliver their compiled stylesheet
and retained child assets. When that URL is attached as a stylesheet link,
editing a retained CSS child or its image updates the styles without reloading
the page, including when only an imported descendant contains `@variant`.
CSS Modules that import local CSS files expose the imported classes through the
root module's exports, with the same scope as its own classes. Imports retain their
conditions and layers, and relative resources keep their original file's directory.
Shared inputs retain each importing root's scope; identical CSS files in different
directories retain their own resource paths. This applies in development and builds.
Imported SCSS and indented Sass files also keep the root module's scope when
different source files compile to identical CSS. Each file retains its own resource
directory, and processing the import graph does not repeat its `additionalData`
callback. String values and callbacks that return source maps are supported.
Consumers must accept CSS Module updates, directly or through their framework's
HMR handling, to apply changed exported names without reloading the page.
Relative CSS `@reference` directives emitted from Sass partials resolve from the
mapped partial's directory, including through CSS Modules. Referenced definitions
retain their own image and font bases. A supplied map that cannot identify an
original filesystem source produces an error.

Diagnostics for imported CSS and Sass use their original files and source maps,
including Sass partials and mapped `additionalData`. Imported Sass is preprocessed
once per prepared Module graph; temporary map data is removed before CSS delivery.
Interpolation can identify an originating segment without an exact token range.
When a callback changes source without supplying a map, diagnostics explicitly
identify a preprocessed location instead of inventing an original Sass position.
Root-relative public CSS URLs that already include Vite's `base` can fail during
Vite Modules preprocessing. Virtual sources and retained-graph Sass edge cases
still require further validation.

Missing CSS Modules composition recovery, other development request modes, other preprocessors
and user PostCSS transformations still require integration and validation.

For production graph delivery, an alias or custom resolver pointing to project
CSS follows the project's native CSS pruning policy. A bare-looking import name
alone does not make the file package CSS: the resolved file must belong to the
named package. Package export conditions may select another CSS file within that
package while retaining its native rules. `@preserve native;` explicitly keeps
project-native rules regardless of class usage.

## Native CSS preservation \{#native-css-preservation\}
Native CSS is preserved by default, even when a class list is supplied. Set
`pruneNativeCSS: true` in an integration or stylesheet API to prune project-owned
sources. Package CSS stays preserved unless its own source explicitly opts in.

### `@prune native` \{#prune-native\}

```css
@prune native;
.used { color: red; }
.unused { color: blue; }
```

This directive opts only its declaring file into pruning. It does not propagate
to imported stylesheets. `@preserve native;` takes precedence in the same file,
including when the integration enables project-wide pruning. The native-output
switch `preserveNativeCSS: false` is separate and suppresses native output
regardless of either directive.

### `@preserve native` \{#preserve-native\}
Use `@preserve native;` when a Master-managed stylesheet contains native CSS class rules that must not be removed by native CSS pruning.

```css
@import "@master/css";
@preserve native;

.injected-by-payment-widget {
  color: blue;
}
```

The stylesheet is still processed by Master CSS. Native class rules are retained even when no scanned source uses their classes; ordinary compiler normalization still applies. This policy does not force unused managed classes into the generated output and does not mean that the original CSS bytes are preserved.

For the full native CSS pruning model, see [Native CSS pruning](/guide/native-css-pruning).

### Group rule identity

Each item in a declaration group retains its declaration identity, value source, conditions, importance, and shorthand or longhand priority. Groups can emit multiple rules for the same escaped group selector. This lets direct values override tokens within the same scope in generated CSS, SSR, and hydration, independently of item order.

## Native queries and validation \{#native-queries-and-validation\}

A condition suffix accepts a registered name or a complete native query. The
outer parentheses belong to Master; parentheses inside them belong to CSS:

```text name="Language v2 queries"
width:10px@sm
width:20px@media((width>=800px))
width:30px@media((aspect-ratio>=1.5))
width:40px@media((width>=50rem))
display:grid@supports((display:grid))
display:grid@supports((display:grid))
width:50px@container(card|(width>=40rem))
width:60px@container(style(--density:compact))
```

Query units remain authored: `800px` is not rewritten to `50rem`. Pipes decode
to spaces outside quoted strings and escapes. Repeated wrappers retain their
nesting and order. Comparable ranges with identical units use range priority;
other queries use stable normalized syntax without assuming a browser root size.
Bare numeric ranges, feature shorthand, and unknown-container-name inference
are removed. Undefined mode or variant references are diagnosed.

The engine emits structurally valid native declarations independently of host
support databases and `CSS.supports()`. Tooling checks every expanded declaration,
including managed utilities. Known-invalid values remain in normal output with
`CSS_VALUE_INVALID` diagnostics. Unknown properties, functions, units, and values
that depend on `var()` are not represented as verified computed values.

Inspection separates `matchStatus` (`matched`, `unmatched`, `ambiguous`,
`syntax-error`), `cssValueStatus` (`valid`, `invalid`, `unknown`, `not-checked`),
and `browserSupport` (`supported`, `unsupported`, `unknown`, `not-checked`).
Checks report their validator version. Browser support remains `not-checked`
unless a target browser was actually queried.

Compiler APIs accept `validation: 'error'` to reject known-invalid values in
the complete result before returning any assets; the default `'report'` preserves
CSS and diagnostics. CLI builds opt in with `master-css generate --strict`.
Unknown capabilities do not fail this policy. Syntax and name-resolution errors
remain distinct from native value validity.

## Native value boundaries

Stylesheet declarations and `@theme` values use native CSS token streams. Master CSS preserves `$`, `|`, strings, escapes and custom functions. Untyped custom properties such as `--pipe: a|b` and `--money: $100` have an unknown value grammar; that does not prevent generation.

`--master-value()` is removed. Use lexical `var(--parameter)` references in a mixin body. `--value()` is always an ordinary native function. `--alpha()` has no compiler meaning. Use native `color-mix()` for opacity expressions:

```css
@theme { :root {
  --color-muted: color-mix(in oklab, var(--color-primary) 50%, transparent);
} }
```

For conditions outside the [simple class query subset](/guide/conditional-queries), define a named `@custom-variant` in CSS. Native media and custom-variant queries keep their native query syntax and do not decode class whitespace.

Compiler and stylesheet APIs use `validation: 'report' | 'error'`, with `report` as the default. Report mode preserves declarations and returns diagnostics. Error mode rejects the entire result for definite syntax or value errors; unknown capabilities alone do not fail the build. The former `cssValuePolicy` option produces a configuration error.


### Source ownership and document extraction

`scanSource(source, content, { owner, kind, parentSource })` replaces that source's contribution, including an empty string. `removeSource` also removes its virtual children. `reconcileSources(owner, inputs)` replaces the owner's complete source snapshot; `removeOwner` revokes its sources and native-class registrations. `registerNativeClasses(owner, names)` replaces a stylesheet's native names. Shared classes and their theme tokens remain until their last owner releases them.

`changed` reports data affecting generation or pruning. `sourceChanged` separately reports source/provenance changes. Candidate collection is pure. A parse or read error is not an empty source: development retains the last successful output and production fails.

Markdown and MDX prose, inline code, fences and frontmatter are excluded from automatic generation. Actual HTML/JSX, ESM and expressions are parsed; their ordinary static strings may still be candidates. Register executable examples as virtual sources with their parent source ID, or use `@safelist`. Use explicit `kind: 'raw'` only for deliberate text sources. Parse failures report `SOURCE_PARSE_ERROR`.

Automatic discovery respects project/workspace `.gitignore` files and excludes generated/dependency/output directories. Explicit `@source` may include normally ignored source files; explicit exclusions and Master/bundler outputs remain excluded.


## Definition ownership and removed preset sizes

A top-level mixin name has one final definition. A later definition replaces its complete parameter list and body, including nested calls and resource dependencies. Empty definitions remain registered. Mixins are not registered inside layers or conditions; use an explicit layer variant at a call site when needed.

An exact zero-parameter mixin wins over named token families. Otherwise the longest family prefix wins, and a named string mixin wins over a built-in token mapping with the same prefix. Once selected, a family with a missing token reports an error instead of falling back. Native `property:value` classes always keep their property meaning.

`font-brand` is ambiguous when both `--font-size-brand` and `--font-family-brand` exist. Use `font-size-brand` or `font-family-brand`. Namespace lookup order within one property remains deterministic; token values are never used to guess the property.

The preset has no `size`, `min-size` or `max-size` recipe. Use explicit width and height declarations, or author a parameter mixin such as `--box`. Native `@page { size: A4; }`, SVG `r`, logical dimensions, and other CSS properties retain their native meaning. See the [RC sizing migration](/guide/migration/v2-rc#sizing-and-resolution).

## Sass interoperability

Place CSS mixin definitions in a `.css` file when using Sass. Current Dart Sass reserves `@mixin --name` for future CSS support and rejects it as a Sass mixin; see [Sass's compatibility notice](https://sass-lang.com/documentation/breaking-changes/css-function-mixin/). An SCSS file may emit the native at-rule through interpolation before Master CSS compiles it:

```scss
@#{'mixin'} --card {
  padding: 1rem;
}

.card { @apply --card; }
```

This is Sass interpolation, not additional Master CSS syntax. Sass `@include` and CSS `@apply` remain separate constructs.
