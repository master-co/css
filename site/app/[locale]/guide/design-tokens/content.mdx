## Overview [sr-only]
Design tokens are named decisions in your design system. They give shared meaning to color, spacing, typography, corner radius, elevation, motion, and responsive breakpoints, so the same class names produce consistent interfaces across product surfaces.

Master CSS includes a set of preset foundation tokens, and each project can extend or override them in the project CSS entry. Use a token-first approach: choose the theme token that communicates intent before reaching for low-level values such as `6x`, `1rem`, `24px`, raw colors, or raw shadows.

## Token-first policy
Use the most meaningful token available for the design decision you are making.

1. Prefer role tokens when your project or UI layer defines product meaning, such as `bg:canvas`, `bg:surface`, `text:strong`, `text:muted`, `b:subtle`, `bg:accent`, or `text:danger`.
2. Prefer scale tokens when the value belongs to a foundation scale, such as `p:md`, `gap:lg`, `font:2xl` for font-size-only, `text:2xl` for a complete type treatment, `r:xl`, `shadow:md`, `animation-duration:normal`, or `animation-timing-function:smooth`.
3. Prefer contextual shorthand when a utility already knows the token namespace, such as `b:1px|solid|subtle` instead of `b:1px|solid|line-subtle`.
4. Use structural values when the value describes layout behavior rather than visual styling, such as `w:full`, `w:50%`, `max-w:5xl`, `h:100dvh`, `@md`, or `@container(md)`.
5. Use low-level values only when no token represents the decision, when the value is local and measured, or when the guide is teaching the syntax itself.
6. If the same low-level value appears in more than one product surface, promote it to a named token instead of repeating it.

(x) Visual decisions are hard-coded.

```html
<article class="p:6x r:8px bg:#fff shadow:0|4px|12px|black/.12 font:1rem">
    ...
</article>
```

(o) Visual decisions use theme tokens.

```html
<article class="p:lg r:lg bg:surface shadow:sm font:md">
    ...
</article>
```

Token-first does not mean every class must be a token. It means reusable visual decisions should come from the design system, while structural CSS values can still be written directly when they describe the layout.

## Foundation tokens
Foundation tokens are the shared vocabulary for the most common UI decisions.

| Foundation | Prefer | Avoid for normal UI |
| --- | --- | --- |
| Color | `text:strong`, `text:muted`, <code>b:1px&#124;subtle</code>, `bg:blue-5`, project roles such as `bg:surface` | `bg:#fff`, `text:oklch(...)`, one-off palette values where a role token fits |
| Spacing | `p:sm`, `gap:md`, `mt:lg`, `pi:xl` | `p:3x`, `gap:1rem`, `mt:12px` |
| Typography | `font:lg`, `text:lg`, `font:medium`, `leading:md`, `tracking:tight` | `font:18px`, `leading:1.4`, `tracking:-0.02em` when a token exists |
| Corner radius | `r:md`, `r:lg`, `r:2xl`, `rounded`, `round` | `r:2x`, `r:8px` for standard cards and controls |
| Elevation | `shadow:xs`, `shadow:sm`, `shadow:md`, `shadow:lg`, or project aliases such as `shadow:card` | Raw multi-part `box-shadow` values in markup |
| Motion | `animation-duration:normal`, `transition-duration:fast`, `animation-timing-function:smooth`, `transition-timing-function:crisp` | Repeated `150ms`, `300ms`, or custom cubic-bezier values |
| Breakpoints | `@md`, `@lg` | Repeated viewport queries such as `@media(768px)` |
| Container sizes | `max-w:md`, `@container(md)` | Repeated component or wrapper widths such as `@container(448px)` |
| Sizing | `w:full`, `w:fit`, `max-w:7xl`, `size:*` for measured elements | Fixed widths in page layout when a fluid or container token fits |

## Semantic tokens first
Role tokens describe why a value exists. Scale tokens describe where a value sits on a scale. Prefer role tokens when the UI decision is semantic.

(o) The text role is clear and can adapt across modes.

```html
<p class="text:text text:md">Supporting copy</p>
```

(o) The surface role is clear and can adapt across modes.

```html
<section class="bg:surface b:1px|solid|subtle">...</section>
```

(o) The palette token is appropriate when demonstrating the palette.

```html
<div class="bg:blue-5 text:blue-60">Blue swatch</div>
```

Use palette scale tokens such as `blue-60`, `green-70`, or `amber-40` when the page is teaching colors, showing a swatch, or intentionally choosing a brand color. For product surfaces, define roles such as `canvas`, `surface`, `accent`, `strong`, `muted`, `subtle`, and status roles such as `success`, `warning`, `danger`, or `info` in your project theme or UI layer.

## Shorthand syntax first
Master CSS utilities often provide shorthand at the property level and at the token namespace level. Prefer the shortest syntax that still communicates the decision clearly.

Property shorthand keeps frequently used declarations compact:

| Prefer | Instead of | Use for |
| --- | --- | --- |
| `text:text` | `color:text` | Foreground color |
| `bg:surface` | `background-color:surface` | Background color |
| `p:md`, `pi:lg`, `m:0` | `padding:md`, `padding-inline:lg`, `margin:0` | Spacing |
| `w:full`, `h:100dvh` | `width:full`, `height:100dvh` | Sizing |
| `r:lg`, `rtl:md` | `border-radius:lg`, `border-top-left-radius:md` | Corner radius |
| <code>b:1px&#124;subtle</code>, <code>bt:1px&#124;line</code> | <code>border:1px&#124;subtle</code>, <code>border-top:1px&#124;line</code> | Border width, style, and color |
| `shadow:md` | `box-shadow:md` | Elevation |
| <code>transition:opacity&#124;normal&#124;smooth</code> | <code>transition-property:opacity transition-duration:normal transition-timing-function:smooth</code> | Transitions |
| `animation-duration:normal`, `animation-timing-function:smooth` | `animation-duration:200ms`, `animation-timing-function:cubic-bezier(...)` | Animation timing |

Contextual token shorthand removes redundant namespace prefixes from values. The utility already knows which namespace to search.

| Prefer | Avoid | Why |
| --- | --- | --- |
| `text:muted` | `text:text-muted` | `text` resolves text color tokens. |
| `caret-color:placeholder` | `caret-color:text-placeholder` | `caret` resolves text color tokens before general colors. |
| `text:accent` | `text:text-accent` | Text color resolves text color tokens. |
| <code>b:1px&#124;subtle</code> | <code>b:1px&#124;line-subtle</code> | Border shorthands resolve line color tokens. |
| <code>outline:1px&#124;subtle</code> | <code>outline:1px&#124;line-subtle</code> | Outline shorthands resolve line color tokens. |
| `p:md`, `gap:lg` | `p:spacing-md`, `gap:spacing-lg` | Spacing utilities resolve spacing tokens. |
| `r:lg`, `rtl:md` | `r:radius-lg`, `rtl:radius-md` | Radius utilities resolve corner radius tokens. |
| `shadow:md` | `shadow:shadow-md` | Shadow utilities resolve elevation tokens. |
| `leading:md` | `leading:leading-md` | Line-height utilities resolve leading tokens. |
| `tracking:tight` | `tracking:tracking-tight` | Letter-spacing utilities resolve tracking tokens. |
| `animation-duration:normal` | `animation-duration:duration-normal` | Animation duration resolves duration tokens. |
| `transition-delay:fast` | `transition-delay:duration-fast` | Transition and animation delay properties resolve duration tokens. |
| `video` | `aspect-ratio:16/9` | Static shortcut for common media frames. |
| `font-feature-settings:tabular` | `font-feature-settings:font-feature-tabular` | Font feature settings resolve font-feature tokens. |
| <code>transition:opacity&#124;normal&#124;smooth</code> | <code>transition:opacity&#124;duration-normal&#124;easing-smooth</code> | Transition shorthand resolves duration and easing tokens. |

The namespace comes from explicit preset registry references, such as `spacing` for padding and gap utilities or `duration` for animation and transition timing properties. It is not inferred from arbitrary property names. See [How namespaces are resolved](/guide/theme#how-namespaces-are-resolved) for the resolution rules and current default namespace sources.

Use the longer form only when it improves clarity in a syntax lesson, or when you are intentionally showing how variable namespaces map to generated CSS.

## Spacing and sizing
Spacing tokens express rhythm between and inside elements. Use them for padding, margin, gap, inset, and layout separation.

(x) The spacing is visually tuned but not named.

```html
<div class="p:6x gap:3x mt:1rem">...</div>
```

(o) The spacing follows the shared scale.

```html
<div class="p:lg gap:sm mt:md">...</div>
```

The `x` suffix is still useful for measured dimensions, especially icons, avatars, skeletons, illustrations, and component-specific widths or heights.

(o) Local measured dimensions are allowed.

```html
<button class="size:10x round">...</button>
<aside class="w:80x max-w:md">...</aside>
```

For page layout, prefer fluid and constrained values first: `w:full`, percentages, `max-w:*`, container queries, and CSS functions when a fluid bound is the design requirement.

## Typography
Use `font:<size>` when you only want the font-size token. Use `text:<size>` when you want the complete type treatment; it can apply the tuned font size, line height, and letter spacing for that scale.

(x) The type size, line height, and tracking are manually assembled.

```html
<h2 class="font:32px leading:1.2 tracking:-0.02em">...</h2>
```

(o) The text token carries the full type treatment.

```html
<h2 class="text:3xl">...</h2>
```

Use lower-level typography tokens when you are intentionally adjusting one property:

```html
<p class="font:md leading:lg">Long-form content</p>
<button class="font:sm font:medium tracking:normal">Save</button>
```

Avoid raw font sizes, line heights, or letter spacing in product examples unless the guide is comparing them against the tokenized approach or teaching the underlying declaration.

## Motion
Motion tokens keep timing and easing consistent across transitions and animations.

(x) Timing is hard-coded.

```html
<button class="transition:opacity|150ms|cubic-bezier(.4,0,.2,1)">...</button>
```

(o) Timing and easing use shared motion tokens.

```html
<button class="transition:opacity|normal|smooth">...</button>
```

Native CSS values such as `linear`, `ease-in-out`, `steps()`, and `cubic-bezier()` are valid when the exact timing function is part of the lesson or when no easing theme token expresses the interaction. For ordinary UI transitions, prefer `transition-duration:*` and `transition-timing-function:*`.

## When low-level values are allowed
Low-level values are not forbidden. They need a clear reason.

| Situation | Examples | Why it is allowed |
| --- | --- | --- |
| Syntax teaching | `p:2x`, `w:clamp(16rem,50vw,40rem)`, `bg:#ceb195` | The guide is explaining the value syntax itself. |
| No token exists | `m:0`, `m:1px`, `z:1`, `opacity:.64` | The value is a precise primitive or a native CSS control, not a reusable design decision. |
| Local measured geometry | `size:10x`, `w:80x`, `aspect-ratio:16/9` | The value belongs to one asset, icon, component, or media frame. |
| Fluid layout requirement | `w:50%`, `h:100dvh`, `max-w:72ch`, `w:clamp(...)` | The value describes layout behavior that a token scale should not hide. |
| One-off content value | `content:"New"`, `grid-cols:3`, `order:first` | The value is semantic content or structural behavior. |
| Custom system extension | `--spacing-card: 1.5rem`, `--shadow-popover: ...` in light and dark modes | The value is being promoted into the design system. |

When the reason is not obvious, prefer a token or add a small note in the surrounding docs that explains why the low-level value is intentional.

## Add project tokens
Create a project token when a value is reused, named in design specs, shared across components, or expected to change by theme or mode.

```css name=index.css
@theme {
    --spacing-card: 1.5rem;
    --radius-card: 0.75rem;
    --color-accent: $color-blue-60;
    --color-on-accent: $color-white;
}

@theme light {
    --shadow-popover: 0 4px 8px -2px oklch(0% 0 none / .08), 0 12px 24px -4px oklch(0% 0 none / .10);
}

@theme dark {
    --shadow-popover: 0 0 0 1px oklch(100% 0 none / .08), 0 8px 18px -8px oklch(0% 0 none / .44), 0 18px 40px -12px oklch(0% 0 none / .36);
}
```

Use the new tokens from markup:

```html
<article class="p:card r:card bg:accent text:on-accent shadow:popover">
    ...
</article>
```

Choose descriptive keys. Avoid numeric token names such as `spacing-1` or `radius-2`, because numeric keys can be confused with unitless values in class syntax. Prefer names that communicate role, scale, or component intent.

## Review checklist
Before publishing a page, component, or demo, review the class names against this checklist:

* Can a role token express this color, text color, surface, or line?
* Can a spacing token replace this margin, padding, gap, or inset?
* Can `text:<size>` replace separate font size, line height, and letter spacing classes?
* Can a radius or mode-aware shadow token replace this raw radius or shadow?
* Can a duration or easing token replace this hard-coded timing value?
* Is this width or height a reusable design decision, or is it local measured geometry?
* If a low-level value appears more than once, should it become a named token?
* If the page keeps a low-level value, is it teaching syntax or solving a specific layout requirement?

Token-first markup is easier to scan, easier to theme, and safer to update because design decisions stay connected to the system that defines them.
