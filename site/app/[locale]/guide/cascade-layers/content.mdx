## How layers control the cascade [sr-only]
CSS cascade layers let a stylesheet decide which groups of rules should win before selector specificity is compared. Master CSS uses that native model as the backbone of its output, so utilities, project styles, presets, variables, and resets can coexist without turning every override into a specificity contest.

Every generated stylesheet starts with the same layer statement:

```css
@layer base,theme,preset,main,general;
```

Layers declared later have higher priority for normal declarations. In Master CSS, the practical order is:

```txt
general > main > preset > theme > base
```

<LayersDefault />

This order is intentional. Foundation rules go early, product vocabulary goes in the middle, and one-off utility decisions stay late enough to override project styles when markup asks for it.

---

## The five layers
### Base
Use `base` for low-level resets and normalization. This layer should make the browser environment predictable, not express a brand or component design.

Rules enter the base layer through `@base` syntax or regular CSS written inside `@layer base`.

### Theme
Use `theme` for generated CSS custom properties. Variables defined in `@master` or `config.variables` are emitted here only when a generated rule references them.

Theme rules are intentionally early: they provide values that later layers consume, but they should not compete with layout, color, or component declarations directly.

### Preset
Use `preset` for broad element defaults such as typography inside an article, code styling, or vendor defaults you want to keep below app-level styles.

Rules enter the preset layer through `@preset` syntax or explicit `@layer preset` definitions. Because preset sits before `main` and `general`, components and utilities can still override it without `!important`.

### Main
Use `main` for project styles that carry product meaning: `.btn`, `.card`, `.field`, `.toolbar`, `.app-shell`. In CSS config, write these class definitions directly inside `@master`.

```css name=master.css
@master {
    .btn {
        @compose "inline-flex";
        background-color: var(--color-primary);
    }
}
```

The compiler converts these definitions into static `config.utilities` entries with `layer: 'main'`. They remain on-demand: defining `.btn` does not emit CSS until `btn` is used or extracted.

### General
Use `general` for utilities: built-in utilities, animation utilities, and custom static utilities written in `@layer general` inside `@master`.

```css name=master.css
@master {
    @layer general {
        .content-auto {
            content-visibility: auto;
            contain-intrinsic-size: auto 32rem;
        }
    }
}
```

General is the final layer, so utility classes can intentionally override main styles from markup.

## A complete flow
This example touches every generated layer. The CSS config defines theme variables and a main style, while the markup uses base, preset, and general utilities.

```css name=master.css
@master {
    light {
        --color-primary: #000000;
    }

    dark {
        --color-primary: #ffffff;
    }

    .btn {
        @compose "inline-flex";
        background-color: var(--color-primary);
    }
}
```

## Base is for normalization
Put reset-style rules in the base layer when they should sit below every design decision.

(i) Add base rules in a global CSS file when the reset is part of the application shell.

```css name=globals.css

    ul {
        list-style: none;
```

## General can override main
Layer order is checked before selector specificity. That means a general utility can override a main style even when the main style comes from a named component.

For example, `.btn` defines `display: inline-flex` in the main layer. Adding `flex` in markup moves the final `display` decision to the general layer.

```html
<!-- @MARK btn flex -->
<button class="btn flex">Submit</button>
```

<details>
    <summary>Generated CSS</summary>
    ```css
    @layer base,theme,preset,main,general;

    @layer main {
        .btn {
            display: inline-flex;
            …
        }
    }

    @layer general {
        .flex {
            display: flex;
        }
    }
    ```
</details>

Use this as the normal override path: keep reusable product styles in `main`, then use utilities in `general` for local adjustments.

## Writing regular CSS
Regular CSS outside `@layer` follows the native cascade outside Master CSS's layer model. If you want a rule to participate in the same priority system, place it in the layer that matches its responsibility.

```css name=app.css
@layer preset {
    article :is(h1, h2, h3) {
        font-weight: 700;
    }
}

@layer main {
    .card {
        border-radius: .75rem;
    }
}
```

Inside `@master`, prefer the configured forms:

```css name=master.css
@master {
    @layer general {
        .content-auto {
            content-visibility: auto;
        }
    }

    .card {
        @compose "block";
        border-radius: .75rem;
    }
}
```

## Summary
Cascade layers are the contract that makes Master CSS predictable:

1. `base` normalizes the platform.
1. `theme` provides generated variables.
1. `preset` sets broad defaults.
1. `main` holds project vocabulary from `@master` class definitions.
1. `general` holds utilities and final local adjustments.

When declarations conflict, solve the problem by choosing the correct layer first. Reach for specificity or `!important` only when you are intentionally integrating with CSS that sits outside this layer model.
