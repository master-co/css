AI coding works best when the agent can see the same styling system your team uses: the framework, the CSS entry, the theme tokens, the reusable component vocabulary, and the checks that keep class strings valid.

Master CSS gives people and agents the same project vocabulary and Rust-backed checks. Local declarations, named tokens and static recipes can be traced to generated CSS. Evaluate the result through subsequent changes, review and browser checks; class length and first-draft speed do not establish maintainability.

Use AI to move faster through routine styling decisions, generate first drafts, compare alternatives, and review class strings. Keep decisions about semantics, shared tokens, reusable components, and visual quality with the person reviewing the change.

Popular local coding agents include [Codex App](https://openai.com/codex/), [Claude Code](https://code.claude.com/docs/en/setup), [Cursor](https://cursor.com/download), and [Windsurf / Devin Desktop](https://devin.ai/download). Use a local agent that can inspect your repository, edit files in small batches, and run the project's own checks.

## Set up the project first
AI output improves when the project already has a real Master CSS setup. Install Master CSS, import the stylesheet from the CSS file your app already loads, and choose the [rendering mode](/guide/rendering-modes) that fits the framework.

```css name=app.css
@import '@master/css';
```

Then give the project a vocabulary the agent can reuse. Theme tokens make repeated values explicit, and component classes give shared product patterns a stable name.

```css name=app.css
@import '@master/css';

@theme {
  --color-brand: #4f46e5;
  --spacing-card: 1.5rem;
  --radius-card: 0.75rem;
 }

@layer components {
  .btn {
    display: inline-flex;
    align-items: center;
    justify-content: center;
    gap: 0.5rem;
    padding-inline: var(--spacing-md);
    height: 2.5rem;
    border-radius: var(--radius-md);
    font-weight: 500;
  }
}
```

Use [Language Service](/guide/language-service) for completions, syntax highlighting, color tools, and generated CSS hover previews. Use [Code linting](/guide/code-linting) when AI-generated class strings should be checked before they enter the codebase.

```js name=eslint.config.js
import { defineConfig } from 'eslint/config'
import masterCSS from '@master/eslint-config-css'

export default defineConfig([
  ...masterCSS
])
```

This setup gives both the developer and the agent fast feedback. The agent can use project tokens instead of raw values, and linting can catch invalid classes, conflicting declarations, non-canonical syntax, and unstable class order.

## Give the agent useful context
Do not start with "make this look better." Ask the agent to inspect the project first, then make a focused change.

Good context includes:

- The official documentation URL: `https://rc.css.master.co`
- The framework, build tool, package manager, and rendering mode.
- The CSS entry that imports `@master/css`.
- Existing `@theme`, `@layer components`, `@mixin`, and `@custom-media` definitions.
- Existing component, template, and design-system patterns near the target UI.
- The formatter, lint, type-check, test, build, and visual review commands.

Use a prompt like this from the project root:

```text name=prompt
You are working in a Master CSS project.

Read the installed package/language/binding versions and project manifest first. Use documentation that matches those versions.
Documentation: https://rc.css.master.co

Before editing, inspect the framework, package manager, CSS entry, theme tokens, component classes, nearby UI patterns, and available validation commands.

When styling markup:
- use valid Master CSS syntax
- prefer existing theme tokens and component classes
- use full native property names for direct declarations and canonical token families for project vocabulary
- do not invent Master CSS APIs, directives, package names, or Tailwind-style syntax
- keep semantic HTML and accessibility behavior unchanged
- explain any value that should become a shared token

Work in a small batch. After editing, show the changed files, explain the styling decisions, and run the relevant formatter, lint, type-check, test, or build command when available.
```

## Use the MCP server
When your AI client supports the Model Context Protocol, connect it to the [Master CSS MCP server](/guide/mcp-server). The server lets the agent inspect the active manifest, scan project sources, lint class strings, inspect generated CSS, request syntax suggestions, and create safe write previews from one local tool surface.

```json name=mcp.json
{
  "mcpServers": {
    "master-css": {
      "command": "npx",
      "args": ["-y", "@master/css-mcp@rc", "--root", "/absolute/path/to/project"]
    }
  }
}
```

Use MCP for project-aware AI tool calls. Read `matchStatus`, `cssSyntaxStatus`, `cssValueStatus` and `browserSupport` separately; an unknown value is not a failed match, and an unchecked browser is not verified support. Manifest load failure requires fixing the project context rather than silently answering from a preset.

Keep complex selectors and container relationships in native CSS. Use `@custom-media` for shared media conditions and static mixins only for meaningful parameterized combinations. Classes accept only the [simple query subset](/reference/rules/conditions). Markdown/MDX code fences are display content; register executable examples or safelist bounded classes.

The shared CLI/editor/MCP workflow fixtures check tool consistency. They do not measure model generation accuracy.

Use MCP for project-aware AI tool calls. When an agent cannot use MCP, fall back to the CLI JSON commands in the review workflow below.

## Add project agent rules
For recurring work, add a short Master CSS rules block to the project's agent instructions, such as `AGENTS.md`, Claude instructions, Cursor rules, or Copilot instructions.

```text name=AGENTS.md
When editing Master CSS:
- Inspect installed package/language/binding versions and the active manifest before consulting matching documentation at https://rc.css.master.co.
- Before editing, inspect the framework, package manager, CSS entry, rendering mode, theme tokens, component classes, utilities, custom variants, and validation commands.
- Put resets and normalization in @layer base, broad project visual defaults in @layer defaults, and named UI classes in @layer components.
- For example, put button font inheritance in base, the page text color in defaults, and a .btn design in components; defaults does not mean browser defaults.
- Prefer existing @theme tokens. Use @utility for on-demand classes and @mixin for CSS reuse.
- Write native declarations and selectors in CSS; use utilities directly in markup. Native component classes do not derive Master suffixes.
- Use the Master CSS MCP server when available. Without MCP, use CLI JSON fallback commands such as `npx @master/css-cli lint --format json --exit-code never` and `npx @master/css-cli inspect --format json --exit-code never`.
- Use ESLint for class policy diagnostics and the Master CSS Language Service for completion, hover, colors, highlighting, and directive formatting.
- Do not invent Master CSS APIs, directives, package names, or Tailwind-style syntax.
- Preserve semantic HTML, accessibility attributes, and behavior.
- Run the relevant formatter, lint, type-check, test, or build command before reporting completion.
```

Keep project-specific commands in the same file so the agent does not have to infer how validation works.

## Prompt for readable class strings
Ask the agent to optimize for readable markup, not the shortest possible class list.

```html
<button class="display:inline-flex align-items:center gap-xs height:2.5rem px-md r-md fg-white bg-blue-70:hover opacity:.5:disabled bg-brand">
  Save
</button>
```

Readable Master CSS usually follows these habits:

- Use complete class strings instead of building classes from small string fragments.
- Prefer project tokens such as `bg-brand`, `p-card`, and `r-card` when they exist.
- Use native declaration syntax such as `scroll-margin-top:4rem` when it is clearer than a custom abstraction.
- Keep selector states and conditions attached to the class they affect, such as `bg-blue-70:hover` and `grid-cols(3)@md`.
- Move repeated product values into `@theme`; move repeated product patterns into `@layer components` only when a named abstraction improves maintainability.

Use [Global styles](/guide/global-styles#shared-vocabulary) for abstraction decisions and [Code linting](/guide/code-linting) for the class policy that keeps AI-generated markup reviewable.

When a class list becomes hard to scan, ask the agent whether the problem is repetition, missing tokens, or a real component abstraction.

```text name=prompt
Review this component's Master CSS classes for readability.

Look for invalid syntax, conflicting declarations, repeated raw values that should become tokens, over-specific one-off styling, missing responsive or dark-mode states, and class strings that should be split into a component class.

Do not rewrite working markup only to make it shorter. Explain each recommended change.
```

## Review AI output
Treat AI-generated styling as a first draft. Review the diff as code and as UI.

Check the class strings:

- Are all classes valid Master CSS syntax?
- Did the agent use Tailwind, Bootstrap, or another framework's class syntax by mistake?
- Do repeated colors, spacing, radius, shadow, or typography values belong in `@theme`?
- Do reusable product patterns belong in `@layer components`, or are local utility classes clearer?
- Are responsive conditions, mode conditions, selector states, and disabled states attached to the correct declarations?
- Did the generated CSS preview match the intended CSS?

Use linting for mechanical feedback:

```bash name=Terminal
eslint .
```

When an agent needs machine-readable Master CSS preflight output without an MCP client, use the CLI's JSON output:

```bash name=Terminal
npx @master/css-cli lint --format json --exit-code never
```

When the agent needs to debug scanner coverage or explain missing generated CSS, inspect the extraction state instead of rerunning lint policy:

```bash name=Terminal
npx @master/css-cli inspect --classes "btn card" --format json --exit-code never
```

Use the browser for visual feedback. Compare the important states: default, hover, focus-visible, disabled, loading, narrow containers, dark mode, and reduced motion when the component supports them.

## Know what to leave alone
Not every style should become a Master CSS class. Ask the agent to keep regular CSS when conversion would make the project harder to maintain.

Leave these alone unless there is a clear benefit:

- Vendor CSS, reset CSS, generated CSS, and third-party package styles.
- Complex keyframe animation rules that are easier to read as CSS.
- Highly dynamic values controlled by user input, pointer position, charts, maps, or editors.
- One-off native declarations where a direct CSS rule is more obvious than a dense class string.
- Framework or library styles that external code expects to own.

For dynamic values, prefer stable classes plus CSS variables or inline styles at the boundary.

```html
<div class="opacity:var(--opacity) transform:translateX(var(--x))">
  ...
</div>
```

## Prompt templates
### Feature styling
```text name=prompt
Style this feature with Master CSS.

Use existing project tokens and component classes when they fit. Keep local one-off decisions in markup. Add new `@theme` tokens only for values that are reused or represent product vocabulary. Do not change semantic HTML, accessibility attributes, or behavior.

After editing, explain the class choices and run the available checks.
```

### Token extraction
```text name=prompt
Find repeated visual values in this component or route.

Recommend which values should become Master CSS `@theme` tokens, which repeated patterns should become `@layer components`, and which values should stay local. Do not edit until you explain the proposed token names and why they are product vocabulary.
```

### Class review
```text name=prompt
Review these Master CSS class strings.

Check for invalid classes, conflicts, non-canonical syntax, condition order, repeated raw values, missed states, and places where a component class would make the code easier to maintain. Prefer small fixes over broad rewrites.
```

### Visual QA
```text name=prompt
Visually review this Master CSS change.

Run the app, inspect the affected page in desktop and mobile widths, and compare default, hover, focus-visible, disabled, responsive, and dark-mode states where applicable. Report any layout shift, overflow, missing CSS, or behavior change before editing further.
```

## Named tokens and native values


Use explicit `var(--name)` references inside raw values, including functions and multi-value declarations. Use native CSS units for lengths and resolution descriptors in `image-set()`. Do not invent numeric names such as `p-4` unless the project defines that token.

Resolve ambiguous short names with an explicit prefix, for example `font-family-brand` or `font-size-brand`. Check compiler diagnostics and generated declarations; the revised spelling alone does not establish CSS validity or improved AI accuracy.

Use explicit dimensions: `width:20px height:20px` or `w-sm h-sm`. A project can define a parameter mixin for paired dimensions. Do not infer token identity from equal values or invent an alternative prefix that the project does not register. `flex` means `display:flex`, while `flex:1` and `flex:hover` are native `flex` declarations. To apply display on hover, write `display:flex:hover`.



Use native conditions and explicit mixin calls for wrappers. Define media names with `@custom-media --name …;` and use `@name` in classes. For selectors or other reusable conditions, define `@mixin --name { … @contents; … }` and call it with `@apply --name { … }` in CSS or `@apply(--name)` in a class. Preserve the left-to-right order of wrapper suffixes. Keep layer placement at the call site using outer native `@layer` blocks or `@layer(base|defaults|components|utilities)` class suffixes. Verify wrapper names against the project definitions.


## Review the second change

Before changing shared definitions, save a project snapshot. The next inspection can compare it with the current project even when markup has not changed:

```bash name=Terminal
npx @master/css-cli inspect --snapshot > before.json
npx @master/css-cli inspect --compare before.json > impact.json
```

Run the second command after editing. Review changed definitions, known consumers, generated rules, native stylesheet references and output delivery in `impact.json`. Read the coverage limits, then check affected layouts and states in the browser. In MCP, use `mastercss_scan_project` with `includeSnapshot: true` and pass both snapshots to `mastercss_css_compare`.

Evaluate maintenance with repeatable tasks, using the same requirements, model version and resource limits for native CSS, current Master CSS, and the candidate change. Include a markup framework baseline when useful.

| Second change | Evidence to collect |
| --- | --- |
| Change brand color while retaining an equal information color | Only consumers of the intended role change. |
| Put one card in a main region and a sidebar | The card responds to its container. |
| Restyle a button | Applicable focus-visible, disabled, dark and reduced-motion states still work. |
| Change a token or recipe | Known consumers appear in the impact report; unknown scope is disclosed. |
| Introduce changing progress or coordinates | Stable classes and custom properties handle dynamic values. |
| Mix native, vendor and Master CSS | Cascade, import boundaries, declaration order, duplicates and resource URLs are retained. |

Record first-edit time, second-edit time, human review, corrections, verification time and unresolved failures. Repeat trials; one successful output is not evidence of a general advantage. The repository's compiler and browser fixtures establish mechanical correctness, not a measured reduction in team maintenance time.
