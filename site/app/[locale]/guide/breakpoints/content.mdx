## Overview [sr-only]
Breakpoints are viewport thresholds. They answer one question: when the available page width changes, which product-level decisions should change with it?

Use breakpoint variants for navigation modes, app shells, page grids, typography shifts, and density changes that should follow the viewport. Use [containers](/guide/containers) when a reusable component should respond to the size of its parent instead.

The preset defines named queries with `@custom-media`. The suffix `@md` reads `@custom-media --md`; it is independent of theme variables. The preset has no `--breakpoint-*` custom properties; use native lengths or layout tokens for width caps.

## Define named media queries
Custom media definitions belong in your project CSS entry. Keep them product-wide and stable; they are part of the layout language shared by docs, components, designers, and tests.

```css name=index.css
@custom-media --sm (width >= 48rem);
@custom-media --md (width >= 64rem);
@custom-media --lg (width >= 80rem);
```

Use native media query syntax and explicit units. The preset scale tables show px/rem equivalents using a 16px reference for readability; generated queries preserve the authored unit.

## Use breakpoint variants
Append `@<breakpoint>` to a utility when that declaration should start at a viewport threshold.

```html
<!-- @MARK font-2xl --><!-- @MARK font-3xl@md -->
<h1 class="font-2xl font-3xl@md">Build for the current viewport</h1>
```

<details>
  <summary>Generated CSS</summary>
  <Class2CSS>

</details>

Unqualified classes are the base state. Breakpoint variants layer changes on top, which makes the default mental model mobile-first without forcing every product to design only for phones.

## Breakpoint scale
Use the scale as design vocabulary, not as device names. A token such as `md` should mean "the medium page layout starts here", not "iPad" or "desktop".

<BreakpointQueries />

The exact values can differ by product. The important part is that the tokens stay semantically consistent: smaller tokens unlock compact layout changes, larger tokens unlock wider page structures.

---

## Manifest changes around decisions
A breakpoint should exist because something meaningful changes. Avoid adding thresholds only because a popular device width exists.

| Decision | Good breakpoint use | Better handled elsewhere |
| --- | --- | --- |
| Navigation | Switch from bottom tabs to top navigation | A single card changing layout inside a sidebar |
| App shell | Add a persistent sidebar at `@md` | Button padding that only belongs to one component |
| Page grid | Move from 4 columns to 8 or 12 columns | A gallery that depends on its rendered container |
| Typography | Increase heading scale when line length and hierarchy need it | Local text measure such as `max-width:72ch` |
| Density | Increase section rhythm and outer margins | Hard-coded spacing values repeated in markup |

```html
<!-- @MARK grid-cols(4) --><!-- @MARK grid-cols(8)@sm --><!-- @MARK grid-cols(12)@md -->
<section class="grid-cols(4) gap-md grid-cols(8)@sm grid-cols(12)@md gap-lg@md">
  ...
</section>
```

## Query viewport ranges
Use a complete [native media query](/reference/rules/conditions#media-queries) when a style belongs to a range instead of every larger viewport.

```html
<!-- @MARK display:none@media((52.125rem<=width<=64rem)) -->
<aside class="display:none@media((52.125rem<=width<=64rem))">...</aside>
```

<details>
  <summary>Generated CSS</summary>
  <Class2CSS>
    {['display:none@media((52.125rem<=width<=64rem))']}
  </Class2CSS>
</details>

Ranges should be rare. If a rule appears at one size, disappears, and returns later, check whether the component is really responding to its container or whether the layout hierarchy should change.

---

## Pair with container width caps
Viewport breakpoints decide when the page changes. Container size values decide how wide a wrapper may grow. Keep those roles separate.

```html
<!-- @MARK max-w-4xl@sm --><!-- @MARK max-w-5xl@md --><!-- @MARK max-w-7xl@lg -->
<main class="width:100% margin-inline:auto px-md max-w-4xl@sm max-w-5xl@md px-xl@md max-w-7xl@lg">
  ...
</main>
```

Here `@sm`, `@md`, and `@lg` come from the breakpoint namespace. The `4xl`, `5xl`, and `7xl` width values come from the [container namespace](/guide/containers).

---

## Prefer stable breakpoint habits
(x) Breakpoints are named after devices.

```css
@theme {

}

@custom-media --iphone (width >= 24.375rem);
@custom-media --ipad (width >= 51.25rem);
```

(o) Breakpoints are named after layout thresholds.

```css
@theme {

}

@custom-media --xs (width >= 40rem);
@custom-media --sm (width >= 48rem);
@custom-media --md (width >= 64rem);
```

(x) A reusable card responds to the viewport, so it breaks when placed in a narrow sidebar.

```html
<article class="grid-cols(2)@md">...</article>
```

(o) Page structure uses breakpoints, while reusable components use container queries.

```html
<main class="grid-cols(12)@md">
  <section class="container-type:inline-size">
    <article class="grid-cols(2)@container((width>=28rem))">...</article>
  </section>
</main>
```

Use breakpoints sparingly, name them for layout meaning, and keep component-local responsiveness in [containers](/guide/containers).
