## Overview [sr-only]
Reusable styling starts with a decision, not a file. Keep local choices in markup, move shared values into theme tokens, and define component classes only when a repeated pattern has product meaning.

Writing `.btn` at the top level of a stylesheet creates a normal CSS rule. It can use `@compose` and `@at`, but it is still emitted by that stylesheet as native CSS. Writing `.btn` in top-level `@layer components` defines a Master CSS component class instead: it is generated on demand when `btn` is used in markup, scanned from source, or composed by another CSS-defined style.

---

## Start with utilities
Use utility classes when the style belongs to one element, one state, or one local layout decision. This keeps the relationship between markup and style explicit while the pattern is still changing.

```html
<button class="inline-flex ai:center jc:center gap:xs px:md py:xs r:lg font:sm font:medium bg:primary fg:white">
    Save changes
</button>
```

Do not abstract just to shorten a class list. Abstract when the name improves the product vocabulary: `btn`, `card`, `field`, `toolbar`, `empty-state`, or another role that appears across the interface.

---

## Move shared values into the theme
When the repeated part is a value, make it a token instead of a class. Tokens keep markup semantic while still letting each component choose its own structure.

```css name=index.css
@theme {
    --color-yellow-ring: $color-black/.1;
    --color-touch-yellow: $color-yellow-30;
    --color-text-yellow-contrast: $color-yellow-90;
    --border-radius-control: 8;
    --spacing-control-x: 16;
}
```

```html
<button class="px:control-x r:control bg:yellow fg:text-yellow-contrast">
    Submit
</button>
```

Use [Customizing your theme](/guide/theme) and [Variables and Modes](/guide/variables-and-modes) when the reusable part is color, spacing, typography, radius, shadow, motion, screens, or mode-specific values.

## Create component classes
<span id="components" />
Use a component class when a repeated class list becomes a reusable UI pattern. Define components in top-level `@layer components`, put Master CSS classes in `@compose`, and write native declarations directly in the rule.

```css name=index.css
@layer components {
    .btn {
        @compose "inline-flex ai:center jc:center gap:xs px:md py:xs r:lg font:sm font:medium";
        background: var(--color-primary);
        color: white;
    }
}
```

```html
<button class="btn">Save changes</button>
```

The generated CSS is emitted in the `components` layer:

```css
@layer components {
    .btn {
        display: inline-flex;
        gap: 0.5rem;
        border-radius: 0.5rem;
        padding-left: 1rem;
        padding-right: 1rem;
        padding-top: 0.5rem;
        padding-bottom: 0.5rem;
        align-items: center;
        font-size: 0.875rem;
        font-weight: 500;
        justify-content: center;
        background: var(--color-primary);
        color: #fff;
    }
}
```

Component definitions are config, not output. Defining `.btn` does not generate CSS until `btn` appears in scanned classes or is composed by another CSS-defined style.

You can still apply component classes alongside conditional utility classes when a variation belongs to one usage site:

## Add states and conditions
Put selector states in nested selectors and conditional variants in `@at` blocks. This keeps the component definition readable and keeps the markup semantic.

```css name=index.css
@layer components {
    .btn {
        @compose "inline-flex ai:center jc:center px:md py:xs r:lg";
        transition: background-color .15s ease, box-shadow .15s ease;

        &:hover {
            @compose "bg:primary/.9";
        }

        &:focus-visible {
            @compose "outline:2|primary outline-offset:2";
        }

        @at <sm {
            @compose "block";
        }
    }
}
```

Equivalent markup stays short:

```html
<button class="btn">Continue</button>
```

## Keep variants composable
Avoid hiding every option behind a new component. Give each component class one responsibility, then combine it with tokens, utilities, or smaller component classes.

```css name=styles/button.css
@layer components {
    .btn {
        @compose "inline-flex ai:center jc:center";
        font-weight: 600;
        outline-offset: -0.0625rem;
    }

    .btn-xs {
        @compose "r:sm px:xs font:xs h:6x";
    }

    .btn-sm {
        @compose "r:md px:sm font:xs h:8x";
    }

    .btn-md {
        @compose "r:md px:md font:sm h:10x";
    }

    .btn-lg {
        @compose "r:lg px:lg font:md h:12x";
    }

    .btn-xl {
        @compose "r:xl px:lg font:md h:14x";
    }
}
```

```html
<!-- @MARK btn-xs -->
<button class="btn btn-xs">Submit</button>
<!-- @MARK btn-sm -->
<button class="btn btn-sm">Submit</button>
<!-- @MARK btn-md -->
<button class="btn btn-md">Submit</button>
<!-- @MARK btn-lg -->
<button class="btn btn-lg">Submit</button>
<!-- @MARK btn-xl -->
<button class="btn btn-xl">Submit</button>
```

If one class tries to own size, color, shape, layout, and interaction variants, overrides become fragile. Smaller classes compose better with utilities and rarely need `!important`.

## Build shared structures
Create explicit classes for each meaningful part of a repeated structure. Avoid relying on descendant selectors when separate class names make the output easier to trace.

```css name=index.css
@layer components {
    .card {
        border-radius: 0.5rem;
    }

    .card-header {
        border-bottom: 0.0625rem solid oklch(0% 0 none);
    }

    .card-content {
        padding: 1.25rem;
    }

    .card-footer {
        border-top: 0.0625rem solid oklch(0% 0 none);
    }
}
```

```html
<article class="card">
    <header class="card-header">Title</header>
    <div class="card-content">Content</div>
    <footer class="card-footer">Actions</footer>
</article>
```

Use nested selectors when the selector is truly part of the component behavior:

```css name=index.css
@layer components {
    .empty-state {
        @compose "grid ai:center jc:center min-h:64x p:lg text:center";

        &::before {
            @compose "{content:'';block;size:12x;r:full}";
            background: color-mix(in oklab, currentColor 12%, transparent);
        }
    }
}
```

In this example, `size:12x` is generated for `.empty-state::before`, not for `.empty-state`.

## Use native CSS when output should be native
`@compose` is not limited to component definitions. It can also be used in native style rules. The difference is output ownership:

- `@layer components`, `@layer preset`, and `@layer utilities` create on-demand managed class definitions.
- Native style rules lower to ordinary CSS in the stylesheet that contains them.

```css name=index.css
@layer utilities {
    .flow {
        @compose "grid gap:md";
    }
}

.marketing-card {
    @compose "flow p:lg r:xl shadow:md";
    background: var(--color-surface);

    @at dark {
        @compose "shadow:none";
    }
}
```

Use native CSS when the selector is part of a stylesheet surface you already ship. Use components when the class should behave like a generated Master CSS class and only emit when it appears in markup or source scanning.

## Organize component files
Split component definitions only when it helps ownership. Local CSS imports from the project CSS entry are compiled into one graph.

    ]},
    { name: 'index.css' }
]}
</ExplorerView>

```css name=index.css
@master;
@import './styles/button.css';
@import './styles/base.css';
```

```css name=styles/base.css
@theme light {
    --color-yellow-ring: $color-black/.1;
    --color-touch-yellow: $color-yellow-30;
    --color-text-yellow-contrast: $color-yellow-90;
}

@theme dark {
    --color-yellow-ring: $color-white/.3;
    --color-touch-yellow: $color-yellow-40;
    --color-text-yellow-contrast: $color-yellow-95;
}

@layer components {
    .yellow {
        outline: 0.0625rem var(--color-yellow-ring) solid;
        background-color: var(--color-yellow);
        color: var(--color-text-yellow-contrast);
    }

    .touch-yellow:hover {
        background-color: var(--color-touch-yellow);
    }
}
```

```html
<!-- @MARK yellow touch-yellow -->
<button class="btn btn-md yellow touch-yellow">Submit</button>
```

`@theme` and `@master` config blocks, top-level custom directives, top-level managed layers, top-level `@keyframes`, and native style rules with `@compose` or `@at` are consumed by the Master CSS compiler. Ordinary CSS outside those managed targets remains native CSS in your app stylesheet pipeline.

## Component rules
- Put component definitions in top-level `@layer components`; use `@layer preset` only when a definition intentionally belongs to the earlier preset layer.
- Component selectors must start with a single class selector such as `.btn`, `.card`, or `.field::before`.
- `@compose` is valid inside managed class definitions and native style rules.
- Component definitions accept native declarations, `@compose`, nested selectors, native nested at-rules, and `@at` condition blocks.
- CSS-defined managed classes can compose other CSS-defined managed classes. Circular `@compose` dependencies are invalid.
- Standard HTML tag selectors such as `body` or `html` are not valid inside managed layer definitions.
- Utilities still win over components because `@master/css/base.css` declares `@layer theme, base, preset, components, utilities;`.

---

## Summary
- Keep local styling in markup until a pattern proves it should be shared.
- Move shared values into theme tokens before creating new classes.
- Use component classes for reusable UI roles, not for every repeated declaration.
- Keep component classes small enough to combine with tokens, utilities, states, and conditions.
- Use native CSS when the selector belongs to a stylesheet you already ship; use managed component classes when the class should be generated on demand.
