Master CSS semantics now run through one Rust core. Parsing, lowering, rule generation,
priority ordering, manifests, built-in extraction, scanner state, lint policy, and
language intelligence are no longer duplicated in TypeScript.

This is a breaking API migration for tools that imported engine objects or low-level
semantic helpers. It does not change class syntax, Manifest v1, or intended generated
CSS output.

---

## Choose the correct entry

Every semantic package follows the same lifecycle:

| Environment | Initialization | Backend behavior |
| --- | --- | --- |
| Universal | Asynchronous `create*()` | Prefer native in Node, then use the package's corresponding Wasm surface. |
| Node | Synchronous `create*Sync()` from `./node` | Native binding only; missing or incompatible artifacts are explicit errors. |
| Browser | Asynchronous `create*()` from `./browser` | Load only the corresponding Wasm surface. |

After creation, session operations are synchronous and batched. Dispose long-lived
sessions when the owning process, workspace, or document service is released.

The three browser artifacts remain separate:

- `wasm-runtime` contains only live class execution and resource transitions.
- `wasm-compiler` contains CSS parsing, lowering, manifest compilation, and graph operations.
- `wasm-tooling` contains lexer, extraction, scanner, validator, lint, diagnostics, and language operations.

Do not bundle compiler or tooling Wasm into a runtime-only application.

## Replace the engine object

Remove imports of `MasterCSS`, `Rule`, `Layer`, `UtilityLayer`, `ThemeLayer`,
`VariableRule`, `AnimationRule`, `compareRulePriority`, `@master/css-engine/inspect`,
and `@master/css-engine/compiler`.

```ts
import { createEngine } from '@master/css-engine'

const engine = await createEngine({ manifest })
const transition = engine.ensureClassRules([
  'fg:red',
  'font:semibold'
])

console.log(engine.text)
console.log(engine.snapshot().resources)
engine.dispose()
```

Node code that must initialize synchronously uses the native entry:

```ts
import { createEngineSync } from '@master/css-engine/node'

const engine = createEngineSync({ manifest })
```

Consume inspection, transition, snapshot, rule, layer, and resource IR. Do not depend on
mutable TypeScript rule instances or parse generated CSS to recover variable and
animation references.

## Replace compiler helpers

Remove TypeScript semantic imports such as `core`, `lowerCSSDirectives`, and
`createMasterCSSManifest`. Use one compiler session for related operations.

```ts
import { createCompiler } from '@master/css-compiler'

const compiler = await createCompiler()
const directives = compiler.compileCSS(source, { from: 'src/app.css' })
const result = compiler.lowerCSSDirectives({
  manifestInput: directives.manifestInput,
  styleDefinitions: directives.styleDefinitions ?? [],
  warnings: directives.warnings
}, { baseManifest })
compiler.dispose()
```

Use `@master/css-compiler/node` for `createCompilerSync()`. Node file helpers may still
perform filesystem IO and package `exports` resolution, but semantic graph analysis and
lowering remain in Rust. Browser code imports `@master/css-compiler/browser` and cannot
resolve filesystem references unless the host supplies a prepared graph.

## Migrate lexer and extraction calls

Individual TypeScript tokenizer and scanner exports are replaced by versioned batches.

```ts
import { createLexerSession } from '@master/css-lexer'
import { createSourceExtractor } from '@master/css-source'

const lexer = await createLexerSession()
const lexical = lexer.analyze({
  classLists: [{ source: 'fg:red:hover font:semibold' }]
})

const source = await createSourceExtractor()
const extracted = source.extract({
  files: [{ source: 'src/app.tsx', content, kind: 'oxc' }]
})

lexer.dispose()
source.dispose()
```

Svelte, Vue, and custom adapters should use their host parser only to identify relevant
source regions. Send those regions to the Rust extractor instead of implementing a
second class candidate parser.

## Migrate lint, language, and validation

Lint and language APIs require a Manifest v1 value and a Rust session. They no longer
accept a legacy engine instance.

```ts
import { createLintSession } from '@master/css-lint'
import { createLanguageSession } from '@master/css-language'
import { createValidator } from '@master/css-validator'

const lint = await createLintSession(manifest)
const language = await createLanguageSession(manifest)
const validator = await createValidator(manifest)

const document = language.analyzeDocument({ source, languageId: 'typescriptreact' })
const classes = validator.generate(document.classPositions.map(({ token }) => token))

lint.dispose()
language.dispose()
validator.dispose()
```

ESLint integrations should only visit AST nodes, map source ranges, and adapt reports or
fixes. LSP integrations should only map Rust IR to protocol objects and manage
cancellation. A missing native backend in synchronous tooling is a configuration error;
do not construct a TypeScript fallback engine.

## Regenerate hydration manifests

Hydration manifest version 1 now includes the Rust-generated `resourceOrder` array in
addition to `rules`. The order preserves variable and animation resource identity when
the runtime recreates the server render snapshot without parsing generated CSS.

Do not hand-author hydration manifests or reuse manifests produced by the legacy
TypeScript engine. Generate them through the Rust render/session API and deploy the
manifest together with its matching `style#master-css`; a missing `resourceOrder` is an
invalid hydration contract and causes the runtime to rebuild safely.

---

## Handle backend failures

Treat backend and contract failures as operational errors. Important stable cases
include unavailable native artifacts, failed Wasm loading, ABI or IR version mismatch,
disposed sessions, invalid manifests, and invalid requests.

Do not catch these errors and continue through older semantic code. Either surface the
error with installation guidance or, from a universal asynchronous entry, allow the
official wrapper to select its corresponding Wasm backend.

---

## Verify the migration

- Confirm production code contains no `MasterCSS` construction or removed semantic subpath imports.
- Exercise native and the relevant Wasm surface with the same fixture corpus.
- Compare CSS text, layer/rule order, keyframes, Manifest v1 output, diagnostics, UTF-16 ranges, and edit plans.
- Test missing native artifacts, Wasm load failures, ABI mismatch, invalid manifests, and disposed sessions.
- Check that runtime bundles contain neither compiler nor tooling Wasm.
- Run browser hydration/CSSOM tests for runtime changes and ESLint/LSP end-to-end tests for tooling changes.
