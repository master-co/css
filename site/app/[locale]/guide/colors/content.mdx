## Overview [sr-only]

Master CSS color tokens cover fixed palette steps, preset UI roles, and fixed hue aliases and adaptive text aliases. Use palette steps when you need an exact swatch. Use preset roles for the repeated color decisions that define application structure, text hierarchy, and light or dark mode behavior.

---

## Default color palette
The preset defines fixed color families using OKLCH. Each family has steps `0`, `5`, `10` through `90` in tens, `95`, and `100`. These are palette names, not percentages or opacity values.

Browse and copy the complete [palette and adaptive aliases](/reference/tokens/color) in Reference. In this guide, select a base surface, readable foreground and one accent before adding more roles.

Choose palette steps directly for swatches, illustrations, brand accents, and status-color foundations. For page backgrounds, surfaces, lines, and text hierarchy, use preset roles so the same markup can adapt across modes.

```html
<!-- @MARK bg-blue-5 --><!-- @MARK fg-blue-60 -->
<div class="bg-blue-5 fg-blue-60">…</div>
```

### Natural material colors

Eight material-inspired families extend the palette with warm neutrals, botanical greens, mineral blue-green, and fired earth. Each has all thirteen fixed steps, a base hue alias such as `bg-petrol`, and a foreground alias such as `fg-text-petrol`.

| Family | Character | Pairing direction |
| --- | --- | --- |
| `sand` | Golden beige with warm umber shadows | Plaster, paper, and warm editorial surfaces |
| `taupe` | Restrained red-brown gray | Quiet typography and architectural neutrals |
| `olive` | Mature yellow-green | Botanical accents beside sand or taupe |
| `sage` | Soft gray-green | Calm surfaces and natural lifestyle interfaces |
| `moss` | Fuller leaf green | Plant imagery and accents beside sage |
| `petrol` | Deep mineral blue-green | Cool backdrops beside warm materials |
| `copper` | Golden orange-brown | Warm accents distinct from red clay |
| `terracotta` | Muted red clay with peach tints | Ceramic, craft, and boutique compositions |

The lightest steps retain a tint; the darkest retain the material's hue. Step numbers describe an ordered palette, not equal lightness or guaranteed contrast between families. The curves are individually tuned rather than shared across every hue.

```html
<article class="bg-sand-5 fg-taupe-80 bg-taupe-95@dark fg-sand-10@dark">
  Warm materials, with explicit light and dark pairings.
</article>
<p class="bg-surface-raised fg-text-petrol">A mode-aware mineral accent.</p>
```

<NaturalMaterials />

All eight families fit within Display P3. Petrol's `60` and `70` steps use a small extension beyond sRGB; other new steps fit sRGB. Browsers map colors to the display's available gamut. Copy the OKLCH value or CSS variable to preserve the authored color; a hex representation is an sRGB approximation.

The new `text-<family>` aliases meet at least 4.5:1 against the matching preset `base`, `inset`, `raised`, and `floating` surfaces in both modes, measured after sRGB gamut mapping. Check contrast again when changing the surface, adding transparency, or choosing a fixed step or base hue alias. See [WCAG's text contrast guidance](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).

(!) `olive` resolves to the fixed preset alias, just as `red` and `blue` do. Existing classes such as `fg-olive` and `bg-olive` therefore change appearance. To retain the CSS named olive color, use a literal such as `color:#808000` or `background-color:#808000`.

## Choose a color token

<FoundationColorRoles />
Start with the kind of decision you are making. Most app chrome should use roles first, then reach for palette steps or hue aliases when the color itself is the point.

| Decision | Use | Examples |
| --- | --- | --- |
| Fixed swatch | Palette steps | `bg-blue-5`, `fg-blue-60` |
| App structure and hierarchy | Preset roles | `bg-surface-base`, `bg-surface-raised`, `b-line-divider`, `fg-text-body` |
| Fixed hue swatch | Hue aliases | `bg-blue`, `fg-blue` |
| Adaptive readable foreground | Text hue aliases | `fg-text-blue`, `fg-text-petrol` |

```html
<!-- @MARK bg-surface-base --><!-- @MARK fg-text-body --><!-- @MARK bg-surface-raised --><!-- @MARK border-width:1px border-style:solid b-line-divider --><!-- @MARK fg-text-strong --><!-- @MARK fg-text-muted --><!-- @MARK fg-text-link -->
<main class="bg-surface-base fg-text-body">
  <section class="border-width:1px border-style:solid b-line-divider bg-surface-raised">
    <h2 class="fg-text-strong">Project updates</h2>
    <p class="fg-text-muted">Three milestones changed this week.</p>
    <a class="fg-text-link text-decoration:underline" href="#">Continue</a>
  </section>
</main>
```

## Namespaces for color
Color utilities use focused namespaces so role names stay short in markup. Use `b-line-divider` for decorative dividers, `b-line-control` for required control boundaries, `bg-surface-inset` for recessed areas, and `fg-text-muted` for secondary text.

`bg-`, `fg-` and `b-` read the canonical color namespace. A role suffix such as `surface-raised` selects `--color-surface-raised`; it does not create another family. See [all color consumers](/reference/tokens/color#consumers).

Use the narrow role namespace first when the color describes structure, line work, or text hierarchy. Use the general color namespace when the hue or swatch itself is the decision.

## Preset color roles
Preset roles describe the job a color performs in the interface. Their values are mode-aware, so `bg-surface-base`, `bg-surface-raised`, `b-line-divider`, and `fg-text-body` can stay stable while light and dark modes choose different underlying colors.

### Surfaces
Surface tokens are for the page background, raised panels, floating layers, and inverse blocks. Use `bg-surface-base` for the root canvas and `bg-surface-*` for every surface role.

### Line roles
Line tokens are for borders, dividers, outlines, and strokes. `divider` and `subtle` are decorative; use `control` when a boundary is necessary to identify a control. Use the explicit `line-` part in a role name, such as `b-line-control`; `b-blue-60` selects a fixed palette step.

## Fixed and adaptive hue aliases \{#mode-aware-hue-aliases\}
The 30 general hue aliases are fixed swatches. Only the text aliases select light and dark foreground values. Use them when the hue itself matters; use roles when the color is describing structure or text hierarchy.

### Base hue aliases
Base hue aliases use the same value in every scheme. They are accents and swatches, with no text contrast guarantee.

Text hue aliases choose foreground-oriented palette steps for light and dark modes. They are useful for colored text, but they do not replace semantic text roles such as `fg-text-body`, `fg-text-muted`, or `fg-text-link`.

## Customize color roles
Override preset role tokens when a repeated UI decision needs product-specific colors. Keep markup semantic so components do not need separate light and dark color classes.

```css name=index.css
@theme {
  --color-surface-base: light-dark(var(--color-white), var(--color-gray-95));
  --color-text-body: light-dark(var(--color-neutral-70), var(--color-gray-30));
}
```

```html
<!-- @MARK bg-surface-base --><!-- @MARK fg-text-body --><!-- @MARK bg-surface-raised --><!-- @MARK border-width:1px border-style:solid b-line-divider --><!-- @MARK fg-text-muted -->
<main class="bg-surface-base fg-text-body">
  <section class="border-width:1px border-style:solid b-line-divider bg-surface-raised">
    <p class="fg-text-muted">The classes stay the same in every mode.</p>
  </section>
</main>
```

Use `light-dark()` for color pairs. Both token dependencies stay in generated CSS; the browser selects the color on the consuming element. A local override of a referenced primitive does not retroactively recompute a custom-property alias inherited from an ancestor: redeclare the role in that local scope when needed.


## Native color scheme and manual themes

The preset sets `:root { color-scheme: light dark; }`. Its 45 adaptive semantic colors and six shadows use native [`light-dark()`](https://www.w3.org/TR/css-color-5/#light-dark). The browser follows the system preference until an element selects a scheme. Native controls follow [`color-scheme`](https://www.w3.org/TR/css-color-adjust-1/#color-scheme-prop) too.

```html
<html data-theme="dark">
  <body class="bg-surface-base fg-text-body">
    <section data-theme="light" class="bg-surface-raised fg-text-body">A light region</section>
  </body>
</html>
```

`data-theme="light"` and `data-theme="dark"` work on the root, nested regions, and shadow hosts. Direct `color-scheme: light` or `color-scheme: dark` works too. A shadow host inherits its ancestor's scheme unless it makes an explicit choice; load the preset native CSS and generated CSS inside the shadow tree. Changing the scheme needs no recompilation.

For a page-level light, dark or system control, change only the root attribute:

```js
function applyTheme(theme) {
  const root = document.documentElement;
  if (theme === "system") root.removeAttribute("data-theme");
  else root.setAttribute("data-theme", theme); // light or dark
}
```

With no root attribute, CSS follows system changes automatically. Persist the choice in application storage, or use a cookie for SSR. Apply a stored client preference before the first paint and keep hydration consistent with that choice. Removing an attribute from a nested region restores inheritance from its parent; it does not independently reset that region to the system preference.

Brand values can use the same native selectors:

```css
@theme {
  [data-theme="ocean"], :host([data-theme="ocean"]) {
    --color-surface-base: light-dark(#eff6ff, #082f49);
  }
}
```

The ocean token remains adaptive to the inherited color scheme. To make ocean always dark, add a native `[data-theme="ocean"], :host([data-theme="ocean"]) { color-scheme: dark; }` rule. A nested light region changes the scheme but still inherits the ocean token; it does not reset every token to the default brand. If brand and scheme vary independently, use `[data-brand="ocean"]` for the brand and `data-theme="light"` or `data-theme="dark"` for the scheme. Restore a complete brand by explicitly redeclaring its role tokens at that boundary.

Move a token definition outside `@theme` when it should always ship with its native stylesheet. It still provides the same named utilities. Native overrides keep their original cascade layer; see the [theme delivery contract](/reference/directives/theme#theme-static).

The preset `@light` and `@dark` class suffixes still mean **system preference media queries**. A manual theme changes tokens and native controls but does not activate these suffixes. If an application needs a selector variant, declare a separate name:

```css
@mixin --manual-dark {
  &:where([data-theme="dark"], [data-theme="dark"] *) { @contents; }
}
```

This selector also matches inside nested light regions; it is an explicit application selector, not a test of the browser's used color scheme. Prefer adaptive tokens for nested themes.

Native support starts at Chrome 123, Firefox 120, and Safari 17.5. The preset does not ship a parallel media-query fallback for older browsers. See [Chrome 123](https://developer.chrome.com/blog/new-in-chrome-123), [Firefox 120](https://developer.mozilla.org/en-US/docs/Mozilla/Firefox/Releases/120), and [Safari 17.5](https://webkit.org/blog/15383/webkit-features-in-safari-17-5/).

## Contrast

- `fg-text-body`, `fg-text-strong`, links, and all 30 `fg-text-*` hue aliases target at least 4.5:1 on the opaque base, inset, raised, and floating surfaces in both schemes. `fg-text-yellow` uses yellow-90 in light mode, a deliberately deep ochre foreground.
- `fg-text-muted` is for base, inset, and raised surfaces. Use `fg-text-body` on floating surfaces. `fg-text-disabled` is reserved for genuinely disabled controls.
- `line-control` uses neutral-50 / gray-40 for necessary boundaries, targeting at least 3:1. `line-divider` and `line-subtle` are decorative.
- Pair `bg-surface-inverse` with `fg-text-inverse`. Keep link underlines or another non-color cue; `fg-text-link-hover` needs `:hover` explicitly.
- Recheck transparency, gradients, and custom backgrounds in their actual context; the opaque preset contrast matrix does not cover them.

Inputs need a visible label independent of placeholder text. General hue aliases stay fixed across schemes; numbered palette steps supply explicit colors.
