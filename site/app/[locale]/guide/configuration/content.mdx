## Overview [sr-only]
`master.css` is the primary configuration file for Master CSS. It is where your project turns CSS knowledge into a configured design system: tokens are written as custom properties, conditions are written as at-rules, selectors stay selectors, and reusable UI patterns are written as class rules.

That makes configuration feel closer to authoring CSS than filling out a JavaScript object. A single file can describe the scale of the system, the tokens it exposes, the conditions it understands, the utilities it adds, and the components it abstracts.

```css name=master.css
@master {
    root-size: 16;
    base-unit: 4;
    default-mode: light;
    mode-trigger: media;
    scope: #app;

    --color-primary: #4f46e5;
    --color-panel: #ffffff;
    --screen-md: 768;

    dark {
        --color-primary: #818cf8;
        --color-panel: #111827;
    }

    @custom-at motion-safe @media (prefers-reduced-motion: no-preference);
    @custom-selector :interactive :is(:hover, :focus-visible);
}

@master utilities {
    .content-auto {
        content-visibility: auto;
        contain-intrinsic-size: auto 32rem;
    }
}

@master components {
    .btn {
        @compose "inline-flex ai:center jc:center gap:.5rem px:1rem py:.625rem r:.5rem font:14 font:medium";
        background: var(--color-primary);
        color: white;

        &:interactive {
            @compose "outline:2|primary outline-offset:2";
        }
    }
}

@master animations {
    fade-in {
        from { opacity: 0; transform: translateY(.25rem); }
        to { opacity: 1; transform: translateY(0); }
    }
}
```

The `@master` rules are configuration, not regular stylesheet output. They are compiled into a Master CSS config object, then the engine generates CSS only for classes that appear in markup or are found by extractors.

If you do not have a `master.css` file yet, create one from the starter command:

```bash action=create
@master/css@rc
```

---

## Why CSS configuration
CSS-first configuration keeps the design system close to the platform. Instead of moving every decision into JavaScript, `master.css` lets CSS carry the structure of the system.

For teams, that means the configuration can be reviewed like CSS. Designers and engineers can read token declarations, scan component rules, and understand where custom utilities come from. For the build, it means the config can be compiled ahead of time and shared with extractors, runtimes, language tooling, and framework integrations.

Use native CSS imports when the file grows. This keeps tokens, utilities, components, and animations in focused files without inventing a separate module system.

```css name=master.css
@import './styles/tokens.css';
@import './styles/utilities.css';
@import './styles/components.css';
@import './styles/animations.css';
```

Local relative CSS imports are resolved as one configuration graph. Package imports and regular CSS outside `@master` remain normal CSS.

## Root options
Root options live in the base `@master` block. They are the small set of decisions that shape every generated rule: how numbers convert to units, how spacing scales, where selectors are scoped, and how modes are written.

Most projects set these once near the top of `master.css`, then spend most of their time defining tokens, utilities, and components below them.

```css name=master.css
@master {
    root-size: 16;
    base-unit: 4;
    default-mode: light;
    mode-trigger: media;
    scope: #app;
}
```

### `root-size`
Use `root-size` when the project has a different root font-size convention. Master CSS uses it to convert numeric values into `rem` and `em`.

<DocProp defaultValue="16" types={['number']} />

```css name=master.css
@master {
    root-size: 10;
}
```

```css
.font\:16 {
    font-size: 1.6rem;
}
```

### `base-unit`
Use `base-unit` to define the rhythm behind multiplier units such as `1x`, `2x`, and `4x`. With the default `base-unit: 4`, `4x` equals `16px`, then converts through `root-size`.

<DocProp defaultValue="4" types={['number']} />

```html
<div class="p:4x gap:2x"></div>
```

```css
.p\:4x {
    padding: 1rem;
}

.gap\:2x {
    gap: .5rem;
}
```

### `scope`
Use `scope` when Master CSS should only affect a specific application root, such as an embedded widget, admin app, or migration area inside a larger page.

<DocProp defaultValue="''" types={['string']} />

```css name=master.css
@master {
    scope: #app;
}
```

```css
#app .text\:center {
    text-align: center;
}
```

### `important`
Use `important` only when the surrounding cascade is hard to control, such as when integrating with a legacy stylesheet or third-party system. It is intentionally global.

<DocProp defaultValue="false" types={['boolean']} />

```css name=master.css
@master {
    important;
}

@master {
    !important;
}
```

```css
.hidden {
    display: none !important;
}
```

### `default-mode`
Use `default-mode` to decide which mode should also apply when no explicit mode is active.

<DocProp defaultValue="'light'" types={["'light'", "'dark'", 'string', 'false']} />

```css name=master.css
@master {
    default-mode: light;
}
```

Set it to `false` when the application should not attach any mode to `:root` by default.

```css name=master.css
@master {
    default-mode: false;
}
```

### `mode-trigger`
Use `mode-trigger` to choose how mode-specific values are emitted. System-driven themes usually use `media`; manually switched themes usually use `class`; shadow DOM integrations can use `host`.

<DocProp defaultValue="'media'" types={["'media'", "'class'", "'host'"]} />

```css name=master.css
@master {
    mode-trigger: class;
}
```

Variables and mode behavior are covered in [Variables and Modes](/guide/variables-and-modes).

## Variables and modes
Variables are design tokens. In `master.css`, write them as native custom property declarations inside `@master`.

```css name=master.css
@master {
    --color-primary: #4f46e5;
    --color-panel: #ffffff;
    --font-family-sans: Inter, ui-sans-serif, system-ui, sans-serif;
    --spacing-card: 24;
    --screen-md: 768;
}
```

Token names are contextual. `primary` resolves as a color in `bg:primary`, `sans` resolves as a font family in `font:sans`, and `md` becomes a screen at-rule token in `@md`.

```html
<section class="bg:panel font:sans p:card grid-cols:2@md">
    <button class="bg:primary">Save</button>
</section>
```

Mode-specific values are nested under the mode name. `light` and `dark` are always available, and new modes are added when you define them.

```css name=master.css
@master {
    light {
        --color-panel: #ffffff;
        --color-primary: #4f46e5;
    }

    dark {
        --color-panel: #111827;
        --color-primary: #818cf8;
    }

    high-contrast {
        --color-primary: #ffff00;
    }
}
```

For deeper behavior, mode switching, default mode, and mode triggers, continue to [Variables and Modes](/guide/variables-and-modes). For responsive screen tokens, see [Screen Sizes](/guide/screen-sizes).

## Custom at tokens
Use `@custom-at` to name reusable `@media`, `@supports`, `@container`, and similar at-rules. This is useful when the condition has meaning in your product, not just in the browser syntax.

```css name=master.css
@master {
    @custom-at motion-safe @media (prefers-reduced-motion: no-preference);
    @custom-at supports-backdrop @supports (backdrop-filter: blur(0));
    @custom-at card-wide @container card (width >= 42rem);
    @custom-at start @starting-style;
}
```

Use them in markup as at-rule suffixes:

```html
<div class="@fade-in|.2s@motion-safe bg:white/.8@supports-backdrop"></div>
```

Inside CSS-defined components and utilities, prefer `@at` blocks so the utility list stays plain.

```css name=master.css
@master components {
    .toast {
        @at motion-safe {
            @compose "@fade-in|.2s";
        }
    }
}
```

See [At Tokens](/guide/at-tokens) for naming rules and conflict behavior.

## Custom selector tokens
Use `@custom-selector` to name selectors that repeat across utilities or component definitions. The token keeps markup readable while the generated CSS still uses the real selector.

```css name=master.css
@master {
    @custom-selector :headings :is(h1, h2, h3, h4, h5, h6);
    @custom-selector :interactive :is(:hover, :focus-visible);
    @custom-selector ::scrollbar ::-webkit-scrollbar;
}
```

```html
<article class="font:semibold_:headings">
    <button class="fg:primary:interactive">Save</button>
</article>
```

Nested component selectors can use the same tokens:

```css name=master.css
@master components {
    .link {
        &:interactive {
            @compose "fg:primary";
        }
    }
}
```

See [Selector Tokens](/guide/selector-tokens) for selector token usage in markup and CSS config.

## Custom utilities
Use `@master utilities` for reusable primitives that should behave like utility classes. These are not semantic components; they are low-level capabilities you want available everywhere. CSS-defined utilities are static utilities: one class name maps to one set of native declarations.

```css name=master.css
@master utilities {
    .content-auto {
        content-visibility: auto;
        contain-intrinsic-size: auto 32rem;
    }

    .print-hidden {
        @at print {
            display: none;
        }
    }
}
```

```html
<article class="content-auto print-hidden">…</article>
```

Custom utilities cannot use `@compose`. If the class describes a semantic UI pattern such as a button or card, use a component instead. See [Utilities](/guide/utilities) for details.

## Components
Components are named style compositions for UI patterns such as `.btn`, `.card`, `.field`, and `.page`. They let you turn repeated class lists into project vocabulary without emitting unused CSS.

```css name=master.css
@master components {
    .btn {
        @compose "inline-flex ai:center jc:center gap:.5rem px:1rem py:.625rem r:.5rem font:14 font:medium";
        background: var(--color-primary);
        color: white;

        &:disabled {
            @compose "opacity:.55 pointer-events:none";
        }
    }
}
```

```html
<button class="btn">Save changes</button>
```

Component definitions are converted to config. They are generated only when the component class is used in markup or extracted from source files.

```css
@layer components {
    .btn {
        display: inline-flex;
        align-items: center;
        justify-content: center;
        background: var(--color-primary);
        color: #fff;
    }
}
```

Use [Reusing Styles](/guide/reusing-styles) for the design strategy around when to abstract, and [Components](/guide/components) for complete component definition behavior, merging, layers, nested selectors, and variants.

## Animations
Put keyframes in `@master animations`. They become config-backed animations and are emitted only when a generated class or declaration references them.

```css name=master.css
@master animations {
    fade-in {
        from { opacity: 0; }
        to { opacity: 1; }
    }

    @keyframes slide-up {
        from { transform: translateY(.5rem); }
        to { transform: translateY(0); }
    }
}
```

```html
<div class="@fade-in|.2s|ease-out @slide-up|.2s@motion-safe"></div>
```

Animations are emitted outside cascade layers, while animation-related utilities remain in the utilities layer.

```css
@keyframes fade-in {
    from { opacity: 0; }
    to { opacity: 1; }
}
```

## Functions
Functions are the programmatic extension point for custom value transforms. Because a function transformer is executable JavaScript, define advanced custom functions in a JavaScript or TypeScript config object and merge it with CSS-derived config when needed.

```ts name=master.css.ts
import { extendConfig, type Config } from '@master/css'
import cssConfig from './master.css?master-css-config'

const config: Config = extendConfig(cssConfig, {
    functions: {
        // Define executable function transformers in TypeScript.
    }
})

export default config
```

For most design-system work, prefer variables, static utilities, components, and built-in Master CSS functions in `master.css`. Reach for `functions` only when a token or utility declaration cannot express the transformation.

## Programmatic config
`master.css` should be the default source of truth, but the core API still accepts config objects.

```ts
import { MasterCSS, config, createCSS, extendConfig } from '@master/css'

const css = createCSS({
    scope: '#app'
})

const merged = extendConfig(config, {
    scope: '#app'
})

const engine = new MasterCSS(config, {
    scope: '#app'
})
```

Use programmatic config for tests, library presets, integration glue, and executable extension points. Use `master.css` for app-level tokens, utilities, components, selectors, at tokens, animations, and structural CSS config.

## Output model
Configuration changes affect the generated CSS model:

```css
@layer base, theme, preset, components, utilities;
```

- Variables generate theme rules only when referenced by generated utilities or components.
- Components generate in the `components` layer only when their class is used.
- Utilities generate in the `utilities` layer only when their class is used.
- Animations generate keyframes only when referenced.
- Root options such as `scope`, `important`, `root-size`, and `base-unit` alter generated rules globally.

This is why CSS configuration pairs well with static extraction and build integrations: `master.css` can contain the whole design system, while the final stylesheet still contains only the pieces used by the application.
