## Overview [sr-only]
Your project CSS entry is the primary configuration source for Master CSS. It is where your project turns CSS knowledge into a configured design system: tokens are written as custom properties, conditions are written as at-rules, selectors stay selectors, and reusable UI patterns are written as class rules.

That makes configuration feel closer to authoring CSS than filling out a JavaScript object. A single file can describe the scale of the system, the tokens it exposes, the conditions it understands, the general utilities it adds, and the main styles it abstracts.

```css name=index.css
@master {
    root-size: 16;
    base-unit: 4;
    default-mode: light;
    mode-trigger: media;
    scope: #app;

    --color-primary: #4f46e5;
    --color-panel: #ffffff;
    --screen-md: 768;

    @mode dark {
        --color-primary: #818cf8;
        --color-panel: #111827;
    }

    @custom-at motion-safe @media (prefers-reduced-motion: no-preference);
    @custom-selector :interactive :is(:hover, :focus-visible);

    @layer general {
        .content-auto {
            content-visibility: auto;
            contain-intrinsic-size: auto 32rem;
        }
    }

    .btn {
        @compose "inline-flex ai:center jc:center gap:xs px:md py:xs r:lg font:sm font:medium";
        background: var(--color-primary);
        color: white;

        &:interactive {
            @compose "outline:2|primary outline-offset:2";
        }
    }

    @keyframes fade-in {
        from { opacity: 0; transform: translateY(.25rem); }
        to { opacity: 1; transform: translateY(0); }
    }
}
```

The `@master` rules are configuration, not regular stylesheet output. They are compiled into a Master CSS config object, then the engine generates CSS only for classes that appear in markup or are found by extractors.

If you do not have a CSS entry yet, create one by adding the project marker to `index.css`:

```css name=index.css
@master;
```

## Why CSS configuration
CSS-first configuration keeps the design system close to the platform. Instead of moving every decision into JavaScript, the project CSS entry lets CSS carry the structure of the system.

For teams, that means the configuration can be reviewed like CSS. Designers and engineers can read token declarations, scan main style rules, and understand where custom utilities in the general layer come from. For tooling, it means one config graph can be compiled ahead of time and shared with renderers, extractors, language services, framework integrations, and lint rules.

Build integrations discover the default graph from project CSS files that contain `@master;` or `@import '@master/css'`. The entry can define `@master` content directly, or import local CSS files that contain `@master` blocks. Use native CSS imports when the file grows; this keeps tokens, general utilities, main styles, and animations in focused files without inventing a separate module system.

```css name=index.css
@master;
@import './styles/theme.css';
@import './styles/animations.css';
@import './styles/btn.css';
@import './styles/card.css';
```

```css name=styles/btn.css
@master {
    .btn {
        background: var(--color-primary);
        color: white;
    }
}
```

Local relative CSS imports are resolved as one configuration graph. Only `@master` content contributes to the config; ordinary CSS outside `@master` is ignored by the config compiler. Keep app-level native CSS in the stylesheet entry owned by your framework or bundler.

Only `@master` sections become configuration. Defining `.btn` this way does not emit `.btn` immediately; Master CSS still generates CSS only after `btn` is used by the active renderer or discovered by tooling.

### Config graph and style entries
The project CSS entry is the config graph root. It can import files that contain tokens, mode blocks, custom at tokens, custom selector tokens, main styles, general utilities, and keyframes. Build integrations load this graph automatically from the discovered entry, or from an explicit `Config` object passed to their `config` option.

Application stylesheets are different: they are browser-facing CSS entries. Import `@master/css` from the stylesheet your app already loads when that entry should receive generated Master CSS and default base/theme/utility definitions.

```css name=src/style.css
@import '@master/css';

.native-card {
    border: 1px solid rgb(0 0 0 / 12%);
}
```

If that same stylesheet also contains `@master {}` blocks, it can be the project entry itself because `@import '@master/css'` is also an entry marker.

```css name=src/style.css
@import '@master/css';

@master {
    --color-primary: #4f46e5;
}
```

This keeps the mental model small: the stylesheet that imports `@master/css` receives generated CSS, and its import graph also provides project-level config.

## Variables and modes
Variables are design tokens. In the project CSS entry, write them as native custom property declarations inside `@master`.

```css name=index.css
@master {
    --color-primary: #4f46e5;
    --color-panel: #ffffff;
    --font-family-sans: Inter, ui-sans-serif, system-ui, sans-serif;
    --spacing-card: 24;
    --screen-md: 768;
}
```

Token names are contextual. `primary` resolves as a color in `bg:primary`, `sans` resolves as a font family in `font:sans`, and `md` becomes a screen at-rule token in `@md`.

```html
<section class="bg:panel font:sans p:card grid-cols:2@md">
    <button class="bg:primary">Save</button>
</section>
```

Mode-specific values live in `@mode` blocks. `light` and `dark` are always available, and new modes are added when you define them.

```css name=index.css
@master {
    @mode light {
        --color-panel: #ffffff;
        --color-primary: #4f46e5;
    }

    @mode dark {
        --color-panel: #111827;
        --color-primary: #818cf8;
    }

    @mode high-contrast {
        --color-primary: #ffff00;
    }
}
```

For deeper behavior, mode switching, default mode, and mode triggers, continue to [Variables and Modes](/guide/variables-and-modes). For responsive screen tokens, see [Screen Sizes](/guide/screen-sizes).

## Custom at tokens
Use `@custom-at` to name reusable `@media`, `@supports`, `@container`, and similar at-rules. This is useful when the condition has meaning in your product, not just in the browser syntax.

```css name=index.css
@master {
    @custom-at motion-safe @media (prefers-reduced-motion: no-preference);
    @custom-at supports-backdrop @supports (backdrop-filter: blur(0));
    @custom-at card-wide @container card (width >= 42rem);
    @custom-at start @starting-style;
}
```

Use them in markup as at-rule suffixes:

```html
<div class="@fade-in|fast@motion-safe bg:white/.8@supports-backdrop"></div>
```

Inside CSS-defined main styles and general utilities, prefer `@at` blocks so the utility list stays plain.

```css name=index.css
@master {
    .toast {
        @at motion-safe {
            @compose "@fade-in|fast";
        }
    }
}
```

See [At Tokens](/guide/at-tokens) for naming rules and conflict behavior.

## Custom selector tokens
Use `@custom-selector` to name selectors that repeat across general utilities or main style definitions. The token keeps markup readable while the generated CSS still uses the real selector.

```css name=index.css
@master {
    @custom-selector :headings :is(h1, h2, h3, h4, h5, h6);
    @custom-selector :interactive :is(:hover, :focus-visible);
    @custom-selector ::scrollbar ::-webkit-scrollbar;
}
```

```html
<article class="font:semibold_:headings">
    <button class="fg:primary:interactive">Save</button>
</article>
```

Nested component selectors can use the same tokens:

```css name=index.css
@master {
    .link {
        &:interactive {
            @compose "fg:primary";
        }
    }
}
```

See [Selector Tokens](/guide/selector-tokens) for selector token usage in markup and CSS config.

## General utilities
Use `@layer general` inside `@master` for reusable primitives that should behave like utility classes. These are not semantic components; they are low-level capabilities you want available everywhere. CSS-defined general utilities are static utilities: one class name maps to one set of native declarations.

```css name=index.css
@master {
    @layer general {
        .content-auto {
            content-visibility: auto;
            contain-intrinsic-size: auto 32rem;
        }

        .print-hidden {
            @at print {
                display: none;
            }
        }
    }
}
```

```html
<article class="content-auto print-hidden">…</article>
```

General utilities cannot use `@compose`. If the class describes a semantic UI pattern such as a button or card, use a main style instead. See [Utilities](/guide/utilities) for details.

## Main styles
Main styles are named style compositions for UI patterns such as `.btn`, `.card`, `.field`, and `.page`. They let you turn repeated class lists into project vocabulary without emitting unused CSS.

```css name=index.css
@master {
    .btn {
        @compose "inline-flex ai:center jc:center gap:xs px:md py:xs r:lg font:sm font:medium";
        background: var(--color-primary);
        color: white;

        &:disabled {
            @compose "opacity:.55 pointer-events:none";
        }
    }
}
```

```html
<button class="btn">Save changes</button>
```

Main style definitions are converted to config. They are generated only when the class is used in markup or extracted from source files.

```css
@layer main {
    .btn {
        display: inline-flex;
        align-items: center;
        justify-content: center;
        background: var(--color-primary);
        color: #fff;
    }
}
```

Use [Reusing Styles](/guide/reusing-styles) for the design strategy around when to abstract, and [Components](/guide/components) for complete component definition behavior, merging, layers, nested selectors, and variants.

## Animations
Put keyframes in `@master`. They become config-backed animations and are emitted only when a generated class or declaration references them.

```css name=index.css
@master {
    @keyframes fade-in {
        from { opacity: 0; }
        to { opacity: 1; }
    }

    @keyframes slide-up {
        from { transform: translateY(.5rem); }
        to { transform: translateY(0); }
    }
}
```

```html
<div class="@fade-in|fast|decelerate @slide-up|fast@motion-safe"></div>
```

Animations are emitted outside cascade layers, while animation-related utilities remain in the general layer.

```css
@keyframes fade-in {
    from { opacity: 0; }
    to { opacity: 1; }
}
```

## Functions
Functions are the programmatic extension point for custom value transforms. Because a function transformer is executable JavaScript, define advanced custom functions in a JavaScript or TypeScript config object and merge it with CSS-derived config when needed.

```ts name=config.ts
import { extendConfig, type Config } from '@master/css'
import cssConfig from 'virtual:master-css-config'

const config: Config = extendConfig(cssConfig, {
    functions: {
        // Define executable function transformers in TypeScript.
    }
})

export default config
```

If TypeScript cannot resolve the virtual import, add the client type reference for the integration that compiles the CSS config, such as `@master/css.vite/client`, `@master/css.next/client`, or `@master/css.webpack/client`.

For most design-system work, prefer variables, static utilities in the general layer, main styles, and built-in Master CSS functions in the project CSS entry. Reach for `functions` only when a token or utility declaration cannot express the transformation.

## Root options
Root options live in the base `@master` block. They are the small set of decisions that shape every generated rule: how numbers convert to units, how spacing scales, where selectors are scoped, and how modes are written.

Most projects set these once near the top of the project CSS entry, then spend most of their time defining tokens, general utilities, and main styles below them.

```css name=index.css
@master {
    root-size: 16;
    base-unit: 4;
    default-mode: light;
    mode-trigger: media;
    scope: #app;
}
```

### `root-size`
Use `root-size` when the project has a different root font-size convention. Master CSS uses it to convert numeric values into `rem` and `em`.

<DocProp defaultValue="16" types={['number']} />

```css name=index.css
@master {
    root-size: 10;
}
```

```css
.font\:16 {
    font-size: 1.6rem;
}
```

### `base-unit`
Use `base-unit` to define the rhythm behind multiplier units such as `1x`, `2x`, and `4x`. With the default `base-unit: 4`, `4x` equals `16px`, then converts through `root-size`.

<DocProp defaultValue="4" types={['number']} />

```html
<div class="p:4x gap:2x"></div>
```

```css
.p\:4x {
    padding: 1rem;
}

.gap\:2x {
    gap: .5rem;
}
```

### `scope`
Use `scope` when Master CSS should only affect a specific application root, such as an embedded widget, admin app, or migration area inside a larger page.

<DocProp defaultValue="''" types={['string']} />

```css name=index.css
@master {
    scope: #app;
}
```

```css
#app .text\:center {
    text-align: center;
}
```

### `important`
Use `important` only when the surrounding cascade is hard to control, such as when integrating with existing stylesheet contracts or third-party systems. It is intentionally global.

<DocProp defaultValue="false" types={['boolean']} />

```css name=index.css
@master {
    important;
}
```

The shorthand `!important;` is also accepted in the same position.

```css
.hidden {
    display: none !important;
}
```

### `default-mode`
Use `default-mode` to decide which mode should also apply when no explicit mode is active.

<DocProp defaultValue="'light'" types={["'light'", "'dark'", 'string', 'false']} />

```css name=index.css
@master {
    default-mode: light;
}
```

Set it to `false` when the application should not attach any mode to `:root` by default.

```css name=index.css
@master {
    default-mode: false;
}
```

### `mode-trigger`
Use `mode-trigger` to choose how mode-specific values are emitted. System-driven themes usually use `media`; manually switched themes usually use `class`; shadow DOM integrations can use `host`.

<DocProp defaultValue="'media'" types={["'media'", "'class'", "'host'"]} />

```css name=index.css
@master {
    mode-trigger: class;
}
```

Variables and mode behavior are covered in [Variables and Modes](/guide/variables-and-modes).

## Programmatic config
The project CSS entry should be the default source of truth, but the core API still accepts explicit config objects.

```ts
import { MasterCSS, config, createCSS, extendConfig } from '@master/css'

const css = createCSS({
    scope: '#app'
})

const merged = extendConfig(config, {
    scope: '#app'
})

const engine = new MasterCSS(merged)
```

Use programmatic config for tests, library presets, integration glue, and executable extension points. Use the project CSS entry for app-level tokens, general utilities, main styles, selectors, at tokens, animations, and structural CSS config.

## Import compiled config
Most projects let the integration load the project CSS entry automatically. When application code needs the compiled config object, import the default virtual config module:

```ts
import config from 'virtual:master-css-config'
```

The virtual module is the canonical project-level config API. It resolves the integration's discovered or configured project CSS entry and returns the compiled JavaScript config object.

Use this when a server hook, runtime initializer, test, or framework adapter needs the same project config object that the build integration uses.

```ts
import { initCSSRuntime } from '@master/css-runtime'
import config from 'virtual:master-css-config'

initCSSRuntime(config)
```

In TypeScript projects, add the matching client type reference for the integration that handles the import:

```ts
// Vite
/// <reference types="@master/css.vite/client" />

// Next.js
/// <reference types="@master/css.next/client" />

// Webpack
/// <reference types="@master/css.webpack/client" />
```

## Output model
Configuration changes affect the generated CSS model. The default `@master/css/base.css` stylesheet declares the layer order, and generated rules are emitted into the matching layer blocks.

- Variables generate theme rules only when referenced by generated general utilities or main styles.
- Main styles generate in the `main` layer only when their class is used.
- General utilities generate in the `general` layer only when their class is used.
- Animations generate keyframes only when referenced.
- Root options such as `scope`, `important`, `root-size`, and `base-unit` alter generated rules globally.

This is why CSS configuration pairs well with static extraction and build integrations: the project CSS entry can contain the whole design system, while the final stylesheet still contains only the pieces used by the application.
