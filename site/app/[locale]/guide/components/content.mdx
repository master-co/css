## Overview [sr-only]
Components are named style compositions for UI patterns such as buttons, cards, fields, and layout shells. They are useful when a repeated class list becomes a design-system concept instead of one-off styling.

In the project CSS entry or a local CSS file imported by it, define components in top-level `@layer components`. The definitions are converted into static `config.utilities` entries with `layer: 'components'`; they are not emitted by themselves. Master CSS generates component CSS only when the component class is used in markup, extracted from source files, or composed by another CSS-defined style. If you are deciding whether a style should become a component at all, read [Reusing Styles](/guide/reusing-styles) first.

---

## Define a component
Use a class selector inside top-level `@layer components`. Put Master CSS classes in `@compose`, and put native CSS declarations directly in the rule.

```css name=index.css
@layer components {
    .btn {
        @compose "inline-flex ai:center jc:center gap:xs px:md py:xs r:lg font:sm font:medium";
        background: var(--color-primary);
        color: white;
    }
}
```

Use the component class in markup:

```html
<button class="btn">Save changes</button>
```

The generated CSS is emitted in the `components` layer:

```css
@layer components {
    .btn {
        display: inline-flex;
        gap: 0.5rem;
        border-radius: 0.5rem;
        padding-left: 1rem;
        padding-right: 1rem;
        padding-top: 0.5rem;
        padding-bottom: 0.5rem;
        align-items: center;
        font-size: 0.875rem;
        font-weight: 500;
        justify-content: center;
        background: var(--color-primary);
        color: #fff;
    }
}
```

## Composition
`@compose` accepts Master CSS utility declarations and CSS-defined utilities or components. Keep it quoted so grouped declarations and punctuation-heavy syntax can be parsed without ambiguity. In component definitions, put selector states in nested selectors and put conditional variants in `@at` blocks.

```css name=index.css
@layer components {
    .empty-state {
        @compose "grid ai:center jc:center min-h:64x p:lg text:center";

        &::before {
            @compose "{content:'';block;size:12x;r:full}";
            background: color-mix(in oklab, currentColor 12%, transparent);
        }
    }
}
```

When the selector is derived from the same component class, nest the selector inside the component rule. In the example above, `size:12x` is generated for `.empty-state::before`, not for `.empty-state`.

---

## Compose outside components
`@compose` is not limited to component definitions. It can also be used in CSS-defined utilities and native style rules. The difference is output ownership:

- `@layer components`, `@layer preset`, and `@layer utilities` create on-demand managed class definitions.
- Native style rules lower to ordinary CSS in the stylesheet that contains them.

```css name=index.css
@layer utilities {
    .flow {
        @compose "grid gap:md";
    }
}

.marketing-card {
    @compose "flow p:lg r:xl shadow:md";
    background: var(--color-surface);

    @at dark {
        @compose "shadow:none";
    }
}
```

Use native CSS when the selector is part of a stylesheet surface you already ship. Use components when the class should behave like a generated Master CSS class and only emit when it appears in markup or extraction.

## States and conditions
Component definitions can include nested selectors and `@at` condition blocks.

```css name=index.css
@layer components {
    .btn {
        @compose "inline-flex ai:center jc:center px:md py:xs r:lg";
        transition: background-color .15s ease, box-shadow .15s ease;

        &:hover {
            @compose "bg:primary/.9";
        }

        &:focus-visible {
            @compose "outline:2|primary outline-offset:2";
        }

        @at <sm {
            @compose "block";
        }
    }
}
```

Equivalent markup stays semantic:

```html
<button class="btn">Continue</button>
```

## Variants in markup
Component classes also accept selector and at-rule suffixes when the variant belongs to the usage site rather than the component definition.

```css name=index.css
@layer components {
    .btn {
        @compose "block";
    }

    .btn:disabled > span {
        @compose "opacity:.55";
    }
}
```

```html
<button class="btn:hover@sm">
    <span>Preview</span>
</button>
```

The generated selector keeps the class identity and places the selector variant on the component root before the configured selector:

```css
@media (width >= 40rem) {
    .btn\:hover\@sm:hover {
        display: block;
    }

    .btn\:hover\@sm:hover:disabled > span {
        opacity: .55;
    }
}
```

For a configured selector such as `.btn:disabled > span`, `btn:hover` becomes `:hover:disabled > span` on the component root. The hover state is not appended to the final descendant.

---

## Generation behavior
Component definitions are config, not output. Defining `.btn` does not generate CSS until `btn` appears in extracted classes or is composed by another CSS-defined style.

```css name=index.css
@layer components {
    .btn {
        @compose "inline-flex px:md";
    }

    .card {
        @compose "p:md r:xl";
    }
}
```

```html
<!-- only btn is generated -->
<button class="btn">Save</button>
```

This keeps unused component definitions out of the final CSS. In Vite extract mode, the project CSS entry and its imported local CSS files can hold the definitions while the extractor and style compiler decide which classes are actually used or composed.

## Definition order
You can split a component into multiple rules. Definitions with the same selector, at-rules, and layer are merged. Native declarations keep their source order relative to `@compose`, while composed utilities are sorted with Master CSS rule priority before they are merged.

```css name=index.css
@layer components {
    .btn {
        @compose "inline-flex";
        display: inline-flex;
        color: black;
    }

    .btn {
        @compose "block";
        display: block;
        font-size: 1rem;
    }
}
```

The compiler expands `@compose` into merged static utility definitions:

```js
{
    utilities: [
        {
            name: 'btn',
            type: -4,
            layer: 'components',
            declarations: {
                color: 'black',
                display: 'block',
                'font-size': '1rem'
            }
        }
    ]
}
```

## Selectors, at-rules, and layers
Component definitions are grouped by resolved selector, resolved at-rules, and layer before they are emitted. That means the following definitions become separate buckets:

```css name=index.css
@layer components {
    .btn {
        @compose "inline-flex";
    }

    .btn:hover {
        @compose "bg:primary";
    }

    @at md {
        .btn {
            @compose "font:md";
        }
    }
}

@layer preset {
    .btn {
        @compose "r:lg";
    }
}
```

The base `.btn`, `.btn:hover`, `@md .btn`, and `preset` layer definitions are kept as separate component rules. Repeated definitions inside the same bucket are merged.

## Split files
Use native CSS `@import` from the project CSS entry to organize components.

```css name=index.css
@master;
@import './styles/button.css';
@import './styles/card.css';

@master {
    --color-primary: #4f46e5;
}
```

```css name=styles/button.css
@layer components {
    .btn {
        @compose "inline-flex ai:center jc:center px:md py:xs r:lg";
        background: var(--color-primary);
        color: white;
    }
}
```

Local relative `.css` imports are compiled into one graph. `@master` config blocks, top-level managed layers, top-level `@keyframes`, and native style rules with `@compose` or `@at` are consumed by the Master CSS compiler; ordinary CSS outside those managed targets remains native CSS in your app stylesheet pipeline.

---

## Rules and constraints
- Put component definitions in top-level `@layer components`; use `@layer preset` only when a definition intentionally belongs to the earlier preset layer.
- Component selectors must start with a single class selector such as `.btn`, `.card`, or `.field::before`.
- `@compose` is valid inside managed class definitions and native style rules.
- Component definitions accept native declarations, `@compose`, nested selectors, native nested at-rules, and `@at` condition blocks.
- CSS-defined managed classes can compose other CSS-defined managed classes. Circular `@compose` dependencies are invalid.
- Standard HTML tag selectors such as `body` or `html` are not valid inside managed layer definitions.
- Utilities still win over components because `@master/css/base.css` declares `@layer theme, base, preset, components, utilities;`.

---

## When to use components
Use components when the class name describes a reusable UI pattern: `.btn`, `.card`, `.field`, `.page`, `.toolbar`. Use utilities when the class describes a reusable primitive or a one-off declaration.

Good component definitions usually stay small and composable. Prefer combining components with utilities in markup instead of hiding every variation behind a new component name.
