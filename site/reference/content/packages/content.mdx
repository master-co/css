## editorial--master-css-usage \{#copy-editorial--master-css-usage\}

Pass an explicit manifest to engine and render APIs in Node.js, or a runtime program from `compileRuntimeProgram()` anywhere; browsers execute only programs. Reuse a session for repeated work and dispose it when finished. For stylesheet authoring and project loading, use [the compiler](/reference/packages#css-compiler); for DOM observation, use [the runtime](/reference/packages#css-runtime).

Build integrations expose the delivery artifacts as virtual modules declared by `./client`: `virtual:master-css-manifest` is the compiled `MasterCSSManifest` for the Node engine, server renderer and tooling; `virtual:master-css-program` is the browser engine program, a hashed `.bin` asset in production builds; `virtual:master-css-emitted-globals` lists variables and keyframes the CSS entry already emits, so runtime generation does not repeat them. A page hydration manifest is separate and describes one response.

Build-time and server generation use Rust semantics; the browser engine executes compiled programs and produces the same CSS for the same definitions and classes. Compile with matching compiler, server and runtime releases: unsupported execution or language versions are rejected.

`executionState(names)` reads stored rule references in request order, repeats included, without generating rules; unknown or never-ensured classes have empty references. Use `snapshot()` for complete rules and CSS. The browser engine has no inspection or render sessions. A host must synchronize resource state even when a transition has no CSS mutations, and a wrapper must forward every `MasterCSSEngine` member, including `executionState`, `registerEmittedGlobals`, `replaceEmittedGlobals`, `refresh`, `dispose` and `Symbol.dispose`.

## editorial--master-css-compiler-usage \{#copy-editorial--master-css-compiler-usage\}

Supply the base manifest explicitly when an API requires it. Inspect returned diagnostics before using the result. A delivery result is an asset set: publish every stylesheet and resource at its assigned URL. See [Imports](/reference/directives/imports) for resolution and delivery boundaries.

**Publishing a file compilation**

`compileManifestFileSync(file, { baseManifest, delivery })` reads the file graph and returns assets without writing them. `delivery` supplies `entryURL`, `stylesheetURL(file)` and `resourceURL(file)`; give distinct stylesheets distinct final URLs. Publish every returned `stylesheets` item at its `href`, and copy each `resources` item from `file` to `href`. The top-level `css`, `nativeCSS` and `generatedCSS` describe the entry only. Relative resource URLs keep their original source owner, query and fragment; reference-only stylesheets do not become published assets. Missing resources and colliding stylesheet URLs fail before publication. Omitting `delivery` returns the single-string result, without this asset-publication contract.

`preserveNativeCSS` defaults to `true`; explicit `false` suppresses raw native CSS while retaining compiled native mixin applications in included output. It does not enable pruning. Stylesheet collections separately select native CSS, Master base CSS and generated utilities through `includeNativeCSS`, `includeMasterBaseCSS` and `includeGeneratedCSS`. Excluded native output does not remove definitions used by generated utilities. See [native pruning](/reference/directives/pruning) for file policy.

`validation: 'report'` is the default: inspect diagnostics while retaining the result. `validation: 'error'` rejects known-invalid CSS in the complete result before returning assets; unknown capabilities alone do not fail it. Ranged diagnostics identify original stylesheet sources where a usable source map exists. A host transform that cannot map a generated segment must not invent an original position.

**Preparing native CSS for another transformer**

Compiler hosts can opt into `preserveNativeSource: true` when another transformer
needs the untouched native portions of a stylesheet. Master definitions are still
consumed and native `@apply` rules are still lowered, while unrelated comments,
empty rules, value spelling, and rule boundaries are retained. The option defaults
to `false`, preserving the compiler's normal native CSS normalization.

Source preservation cannot be combined with enabled native pruning. Passing a class list alone does not enable pruning. `preserveNativeCSS: false` still suppresses native output. The option
does not prevent subsequent host transforms from optimizing the result or rewriting
its source map, and it does not discover new Master definitions or generated-global
references introduced by a later transform.

**Continuing resource rendering after host transforms**

`compileRenderedStylesheet()` and `compileBrowserStylesheet()` accept an optional
`emittedGlobals` resource-count snapshot when another output already supplies
generated theme variables or keyframe definitions. Positive counts suppress duplicate emission;
zero counts do not. New references still emit their transitive resource closure.
The returned snapshot includes the external context and resources required by this
render, without changing the input snapshot. Omitting the option preserves normal
standalone rendering.

This context prevents a later render from replacing an already processed variable
with its original manifest value. It does not run host plugins on newly generated
CSS. Hosts remain responsible for processing that new CSS and publishing its
resources while preserving plugin ordering and source ownership.

## editorial--master-eslint-config-css-usage \{#copy-editorial--master-eslint-config-css-usage\}

Add the preset to your ESLint flat configuration. Configure project-specific behavior through [the plugin settings](/reference/packages#eslint-plugin-css); [Code linting](/guide/code-linting) shows each rule.

| Rule | Default | Fixable | Reports |
| --- | --- | --- | --- |
| `@master/css/sort-classes` | `warn` | Yes | Classes out of generated-rule order, and duplicates. |
| `@master/css/no-invalid-classes` | `error` | No | Invalid Master CSS syntax and invalid generated CSS; unmatched classes only with `disallowUnknownClass`. |
| `@master/css/no-conflicting-classes` | `warn` | Yes | Full and partial declaration conflicts in the same variant scope; only full overrides are fixed. |
| `@master/css/prefer-canonical-classes` | `warn` | Yes | Non-canonical forms, only when token identity and generated-rule behavior are preserved. |

## editorial--master-eslint-plugin-css-usage \{#copy-editorial--master-eslint-plugin-css-usage\}

Use [the official preset](/reference/packages#eslint-config-css) for the standard rules, or register the plugin in your own flat configuration. See [Code linting](/guide/code-linting) for rule behavior.

Settings live under the `@master/css` settings key. Arrays replace their defaults.

| Setting | Default | Use |
| --- | --- | --- |
| `classAttributes` | `['class', 'className']` | Markup attributes that contain class strings. |
| `classFunctions` | `clsx`, `cva`, `ctl`, `cv`, `class`, `classnames`, `classVariant`, `styled`, `classList.add/remove/toggle/replace` | Callees and tagged templates whose arguments can contain class strings; `styled` also accepts member forms such as `styled.button`. |
| `classDeclarations` | `[]` | Project variables or object properties treated as class declarations. |
| `ignoredKeys` | `['compoundVariants', 'defaultVariants']` | Object keys skipped while traversing variant config objects. |

`@master/css/no-unapproved-raw-values` reports raw values in token-backed utilities. `requireProperties` limits it to listed native properties (empty or omitted checks every token-backed property); `allowProperties` and `allowedPatterns` add exceptions; `allowRawValues` disables it. Native custom-property references stay valid. Its diagnostic `data` names the property scope and canonical token families; it has no autofix.

`@master/css/prefer-component-classes` reports a class list in which more than `max` classes (default `3`) style other elements through a top-level `_`, `>`, `+` or `~` combinator. Its diagnostic `data` lists `classNames` and their `targets`; it has no autofix.

`@master/css/no-legacy-classes` reports pre-2.0 `property:value` classes, such as `p:8px`, that 2.0 no longer generates. Its diagnostic `data` names the `className`, the declaration `property` and, when 2.0 generates an equivalent class, the `replacement` its autofix writes.

## editorial--master-css-runtime-usage \{#copy-editorial--master-css-runtime-usage\}

Await `MasterCSSRuntime.start()` before using the session, and call `dispose()` when its owner is finished. `withMasterCSSRuntime()` integrates startup and disposal with custom-element connection callbacks and requires a shadow root. See [Rendering modes](/guide/rendering-modes) for the browser workflow.

Official integrations inject startup. A custom entry passes `program` as a loader, such as `() => import('virtual:master-css-program').then(module => module.default)`, plus `emittedGlobals`, then calls `observe()`. Runtime-only pages load the program during startup; progressive pages with a valid `hydrationManifest` defer the engine until a class outside it appears, unless `engine: 'eager'` or `enginePrefetch: 'idle'` is set. `emittedGlobals` applies to every page using the bundle. The runtime inserts generated rules and on-demand keyframes into its own stylesheet and never writes to linked stylesheets.

`snapshot()` separates `usageCounts`, connected DOM usage, from `classRules`, which can also hold warmed, hydrated or retained rules. `engine` is `'deferred'`, `'loading'`, `'ready'` or `'failed'`; before a deferred engine starts, class snapshots have no rule entries and `layers` is empty. `ensureClassRules()` and `deleteClassRules()` act independently of DOM usage; deletion is synchronous and bypasses retention. Before the engine is ready they throw `RUNTIME_ENGINE_NOT_READY` and start it, so await `ready()` first.

## editorial--master-css-schema-usage \{#copy-editorial--master-css-schema-usage\}

Import types from the narrow subpath that owns them. A type declaration describes a data shape; it does not validate arbitrary input or compile stylesheet directives. Preserve version fields when passing manifests and diagnostics between APIs; editing them by hand does not make a manifest compatible.

Store manifests with `serializeMasterCSSManifest()`. Serialization normalizes derived fields; it does not replace engine validation or keep comments and editable CSS formatting. Unknown fields are not an extension mechanism: an outer envelope that retains them does not make nested fields accepted or executable.

## editorial--master-css-server-usage \{#copy-editorial--master-css-server-usage\}

Provide a compiled manifest before rendering. Keep emitted-global and hydration metadata aligned with the CSS delivered to the client, and dispose reusable sessions after use. See [Rendering modes](/guide/rendering-modes) for complete HTML examples.

`createServerRenderer()` caches rules across renders: recreate it when the manifest changes, and bound `maxCachedClasses` in a long-lived server. Custom hosts can pass the final `stylesheets` a page may link, as `{ href, css, imports }` from `describeLinkedStylesheet()` in `@master/css-compiler/stylesheet`, with the `documentURL` that resolves them; theme variables and native keyframes those stylesheets already deliver are not repeated in `style#master-css`. Rendering tracks each keyframe definition independently, including same-name definitions in different layers or conditions.
