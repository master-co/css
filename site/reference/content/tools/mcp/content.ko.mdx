## editorial-mastercss_lint_project-purpose \{#copy-editorial-mastercss_lint_project-purpose\}


선택 파일에 네이티브 클래스 진단을 실행합니다. lint 페이로드 v5의 `coverage.checkedFiles`는 검사 입력을, `summary.checkedFiles`는 그 수를, `summary.filesWithDiagnostics`는 진단이 있는 파일 수를 나타냅니다. `files`는 진단 결과만 포함합니다. `coverage.status`는 `complete` 또는 `no-inputs`이며 입력 없는 진단 0은 소스를 검증하지 않습니다. `coverage.description`이 설명하듯 manifest 스타일시트 진입점은 lint한 소스 입력이 아닙니다. manifest 실패는 MCP 오류 결과로 남습니다. 프로젝트 파서, 플러그인 설정, 팀 규칙에는 별도로 프로젝트 ESLint 명령을 사용하세요.

## editorial-mastercss_lint_project-lifecycle \{#copy-editorial-mastercss_lint_project-lifecycle\}

## editorial-mastercss_contract_check-purpose \{#copy-editorial-mastercss_contract_check-purpose\}


저장하지 않은 버퍼(`content`, 메시지에 쓸 `filePath`는 선택)나 프로젝트 파일(`patterns`)을 병합한 계약에 비추어 검사합니다. 진단은 의존하는 디자인 시스템이 선언한 검사기에서 나오며 `checkers`는 실행된 검사기를 각각 표시합니다. `classValidation`과 `strict`는 다른 어떤 클래스가 존재하는지 프로젝트 manifest가 검사기에 알려 주었는지 보고합니다. 아무것도 실행되지 않았다면 `coverage.status`는 `no-checker` 또는 `no-contracts`이며, 이때 진단이 0개여도 아무것도 검증되지 않은 것입니다.

## results-0 \{#copy-results-0\}


모든 도구는 `metadata`, `diagnostics`, 필수 `result`를 포함한 버전 3 객체를 반환합니다. 성공은 `result: { status: 'success', data }`이고 실패는 `result: { status: 'error', error: { code, message } }`이며 MCP `isError`도 설정합니다. JSON 텍스트와 `structuredContent`는 같은 객체를 포함합니다. 두 분기를 도구의 `outputSchema`로 검증하세요.

## results-1 \{#copy-results-1\}


`metadata`는 패키지·언어·바인딩 버전, 실제 사용 맥락, manifest 지문, 진입점과 의존성을 보고합니다. 사용할 수 없는 값은 null이나 빈 배열입니다. 기본값은 프로젝트 맥락이며 진입점 누락이나 컴파일 실패는 오류이고 프리셋으로 조용히 전환하지 않습니다. 프리셋만 조회하려면 `context: 'preset'`을 명시하세요.

## results-2 \{#copy-results-2\}


클래스 검사는 `matchStatus`, `cssSyntaxStatus`, `cssValueStatus`, `browserSupport`를 별도로 보고하며 각 기록은 버전, 단계, 범위를 명시합니다. CSS 문법 오류와 알 수 없는 미래 기능은 다릅니다. `var()`는 계산 값을 확정하지 않으며 브라우저 검사를 실행하지 않으면 `browserSupport`는 `not-checked`입니다. 알려진 CSS 수학 타입은 검사하되 길이를 계산하거나 단위를 변환하지 않습니다. 서로 다른 토큰 정의는 값이 같아도 모호한 상태로 남습니다.

## results-3 \{#copy-results-3\}


Markdown과 MDX 추출은 실제 마크업과 코드를 표시 텍스트와 구분하고 원래 UTF-16 범위와 포함/제외 이유를 반환합니다. CLI, 편집기, MCP는 같은 Rust 추출과 일치를 공유합니다. CLI 보고서 버전은 이 응답 형식과 독립적입니다. MCP 페이로드의 `root`는 설정한 작업공간 루트이고 CLI 보고서의 `cwd`는 명령 루트입니다.

## results-4 \{#copy-results-4\}


프로젝트 비교는 편집 전후에 `includeSnapshot: true`로 `mastercss_scan_project`를 호출한 뒤 두 `result.data.snapshot` 객체를 `beforeSnapshot`과 `afterSnapshot`으로 `mastercss_css_compare`에 전달합니다. class, content, `filePath`, `context` 입력과 혼합할 수 없습니다. 결과는 `{ version: 3, mode: 'project', comparison }`이며 `comparison.version`은 1입니다. 변경 정의, 알려진 사용처와 파일, 전후 규칙, 네이티브 참조, 출력 에셋, 전달 순서, `coverage`를 나열합니다. 네이티브 사용처는 스타일시트 단위로 보수적으로 분석합니다.

## results-5 \{#copy-results-5\}


디자인 시스템 검사에서 `mastercss_scan_project.designSystem`은 [디자인 시스템 옵션](/reference/tools/cli#design-system-options) 객체를 받으며 `context: 'preset'`과 함께 쓸 수 없습니다. `result.data.designSystem`의 버전 1 보고서는 작성한 `var()` 참조와 소스 범위, 선택자와 at-rule 조상, 가져오는 주체, 토큰 계열 충돌, 컴포넌트 속성 어휘(`components`), 정책 진단을 나열합니다. JavaScript로 가져온 스타일시트는 `routeStylesheets` glob에 추가하고 `project.routeStylesheets`, `project.excluded`, `coverage`를 읽으세요. 등록되지 않은 사용자 지정 속성도 네이티브 CSS로 해석될 수 있으므로 자동 오류가 아닙니다.

## body-13 \{#copy-body-13\}

## 디자인 시스템의 계약 \{#contracts-of-a-design-system\}

## body-23 \{#copy-body-23\}


Master CSS로 만든 디자인 시스템은 각 컴포넌트를 계약으로 기술할 수 있습니다. 클래스와 위치, 상태, 공개 속성, 가장 작은 올바른 마크업입니다. 라이브러리는 자신의 `package.json`에 계약을 선언합니다.

```json
{
  "name": "your-design-system",
  "masterCSS": {
    "contracts": "./dist/contracts.json",
    "check": "./check/index.js"
  }
}
```

`contracts`는 패키지 안의 경로로, `{ "contracts": [...] }`를 담은 JSON 파일을 가리킵니다. 계약은 문자열 `name`과 `classes` 배열을 가진 객체이며 나머지 필드는 라이브러리가 정합니다. 선택 사항인 `check`는 패키지 안의 경로로, `check(source, contracts, { knows, strict })`를 내보내는 ES 모듈을 가리킵니다. 이 함수는 `code`, `severity`, `message`, `line`, `column`과, 해당하는 경우 `className`과 `contract`를 가진 진단을 반환합니다. [`@master/ui`](https://ui.master.co)는 이 방식으로 계약을 제공하는 첫 라이브러리입니다.

## body-24 \{#copy-body-24\}


서버는 작업공간 루트의 `package.json`에서 `dependencies`, `devDependencies`, `peerDependencies`를 읽고, 그 루트에서 각 패키지를 해석해 `masterCSS.contracts`를 선언한 패키지를 사용합니다. 해당하는 패키지가 없으면 상위 monorepo 루트의 같은 필드를 읽습니다. 대상은 `package.json`에 `workspaces`가 있거나 `pnpm-workspace.yaml`이 있는 가장 가까운 디렉터리이며, 저장소 밖으로는 나가지 않습니다. 프로젝트는 루트 `package.json`의 같은 필드에 glob을 적어 자체 계약을 추가할 수 있습니다. 예: `"masterCSS": { "contracts": "contracts/*.json" }`. 자체 저장소에 있는 라이브러리는 같은 곳에 `masterCSS.check`도 선언해 그 계약을 자체 검사기로 검사할 수 있습니다. `master-ui.json`이 있는 프로젝트는 그 `directory`(기본값 `ui`) 안의 JSON 파일과 `contracts` glob도 함께 제공합니다. 프로젝트 계약은 같은 `name`의 라이브러리 계약을 대체합니다. 결과의 모든 계약에는 `source`가 있습니다. 패키지와 버전, 또는 프로젝트 파일과 그것이 대체한 라이브러리 계약입니다.

## body-25 \{#copy-body-25\}


선언된 의존성이나 작업공간 자체의 `package.json`이 지정한 검사기만 가져오며, 경로는 해당 패키지 안에 있어야 합니다. 프로젝트의 계약 파일은 데이터로만 읽고 실행하지 않습니다. 검사기는 해당 패키지가 제공하는 코드입니다. 서버는 이를 worker thread에서 실행하며, 한 파일 검사가 10초를 넘기거나 검사기가 메모리 한도를 넘으면 중지하고 `CONTRACT_CHECKER_FAILED`를 보고합니다. 검사할 때마다 검사기를 다시 불러오므로 업그레이드한 라이브러리는 재시작 없이 반영됩니다. 검사기는 `knows(className)`을 받습니다. 이 함수는 클래스가 유효한 Master CSS 클래스인지, 프로젝트 스타일시트가 정의한 네이티브 클래스인지를 프로젝트 manifest로 답합니다. `strict: true`는 그 manifest를 불러온 경우에만 전달됩니다. 그렇지 않으면 `knows`는 생략되고 `strict`는 false입니다. 검사기는 작성된 마크업을 그대로 읽으며 런타임에 만들어지는 클래스나 브라우저 동작은 확인하지 않습니다.
