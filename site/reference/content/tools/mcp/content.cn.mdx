## editorial-mastercss_lint_project-purpose \{#copy-editorial-mastercss_lint_project-purpose\}

## results-0 \{#copy-results-0\}


每个工具返回版本 3 对象，包含 `metadata`、`diagnostics` 及必填 `result`。成功为 `result: { status: 'success', data }`；失败为 `result: { status: 'error', error: { code, message } }`，并设置 MCP `isError`。JSON 文本与 `structuredContent` 包含同一对象；请按工具 `outputSchema` 验证两个分支。

## results-1 \{#copy-results-1\}


`metadata` 报告包、语言与绑定版本、实际使用的上下文、manifest 指纹、入口和依赖；无法获取的值为 null 或空数组。默认为项目上下文：缺少入口或编译失败均报错，绝不静默改用预设。仅查询预设时，请显式传入 `context: 'preset'`。

## results-2 \{#copy-results-2\}


类检查分别报告 `matchStatus`、`cssSyntaxStatus`、`cssValueStatus` 和 `browserSupport`，每项记录均标明版本、阶段与范围。CSS 语法错误不同于未知未来能力；`var()` 不代表已确定计算值，未实际运行浏览器检查时 `browserSupport` 保持 `not-checked`。已知 CSS 数学类型会被检查，但不计算长度或转换单位；不同令牌定义即使值相同仍有歧义。

## results-3 \{#copy-results-3\}


Markdown 与 MDX 提取将实际标记、代码与展示文本分开，返回原始 UTF-16 范围及包含或排除原因；CLI、编辑器与 MCP 共用相同 Rust 提取和匹配。CLI 报告版本独立于此封装。MCP 载荷的 `root` 是配置的工作区根目录；CLI 报告的 `cwd` 是命令根目录。

## results-4 \{#copy-results-4\}


项目比较：编辑前后分别以 `includeSnapshot: true` 调用 `mastercss_scan_project`，再将两个 `result.data.snapshot` 对象以 `beforeSnapshot` 和 `afterSnapshot` 传入 `mastercss_css_compare`；不可混用 class、content、`filePath` 或 `context` 输入。结果为 `{ version: 3, mode: 'project', comparison }`，其中 `comparison.version` 为 1，列出变更定义、已知引用方与文件、前后规则、原生引用、输出资源、交付顺序及 `coverage`。原生引用方按样式表粒度保守分析。

## 设计系统的契约 \{#contracts-of-a-design-system\}

## body-23 \{#copy-body-23\}


基于 Master CSS 构建的设计系统，可以用契约描述每个组件：它的类与放置位置、状态、公开属性，以及最小的正确标记。库在自己的 `package.json` 中声明契约：

```json
{
  "name": "your-design-system",
  "masterCSS": {
    "contracts": "./dist/contracts.json",
    "check": "./check/index.js"
  }
}
```

`contracts` 是包内的路径，指向内容为 `{ "contracts": [...] }` 的 JSON 文件。契约是带有字符串 `name` 与 `classes` 数组的对象；其他字段都由库自行定义。可选的 `check` 是包内的路径，指向一个 ES 模块；该模块导出 `check(source, contracts, { knows, strict })`，返回的诊断包含 `code`、`severity`、`message`、`line`、`column`，并在适用时包含 `className` 与 `contract`。[`@master/ui`](https://ui.master.co) 是第一个以这种方式提供契约的库。

## body-24 \{#copy-body-24\}


服务器读取工作区根目录 `package.json` 的 `dependencies`、`devDependencies` 与 `peerDependencies`，从该根目录解析每个包，并保留声明了 `masterCSS.contracts` 的包。如果都没有，服务器会改读上层 monorepo 根目录的相同字段：即最近一个 `package.json` 列出 `workspaces`、或包含 `pnpm-workspace.yaml` 的目录，且不会超出该代码仓库。项目可在根目录 `package.json` 的同一字段用 glob 加入自己的契约，例如 `"masterCSS": { "contracts": "contracts/*.json" }`。库在自己的代码仓库中，也可以在同一处声明 `masterCSS.check`，用自己的检查器检查这些契约。有 `master-ui.json` 的项目，还会加入其 `directory`（默认为 `ui`）内的 JSON 文件与其 `contracts` glob。项目契约会替换同 `name` 的库契约。结果中的每个契约都带有 `source`：包与版本，或项目文件及其替换的库契约。

## body-25 \{#copy-body-25\}


服务器只导入已声明依赖包或工作区自身 `package.json` 所指定的检查器，而且路径必须位于该包内；项目的契约文件只作为数据读取，绝不执行。检查器是该包提供的代码。服务器在 worker thread 中运行它；单个文件超过 10 秒，或检查器超出内存上限时，会停止它并报告 `CONTRACT_CHECKER_FAILED`。每次检查都会重新加载检查器，因此升级后的库无需重启即可生效。检查器会收到 `knows(className)`，它根据项目 manifest 回答某个类是否为有效的 Master CSS 类，或项目样式表定义的原生类；只有在 manifest 加载成功时才会收到 `strict: true`。否则不提供 `knows`，且 `strict` 为 false。检查器按照编写的标记判读，无法确认运行时生成的类或浏览器行为。
