## editorial-mastercss_contract_check-purpose \{#copy-editorial-mastercss_contract_check-purpose\}


依合併後的契約檢查未儲存的緩衝區（`content`，可附上訊息用的 `filePath`）或專案檔案（`patterns`）。診斷來自相依設計系統所宣告的檢查器；`checkers` 列出實際執行的每一個。`classValidation` 與 `strict` 回報專案 manifest 是否已告訴檢查器還有哪些 class 存在。沒有任何檢查執行時，`coverage.status` 為 `no-checker` 或 `no-contracts`，此時即使零診斷，也沒有驗證任何內容。

## results-0 \{#copy-results-0\}


每個工具回傳版本 3 物件，包含 `metadata`、`diagnostics` 與必填 `result`。成功為 `result: { status: 'success', data }`；失敗為 `result: { status: 'error', error: { code, message } }`，並同時設定 MCP `isError`。JSON 文字與 `structuredContent` 含相同物件；請依工具 `outputSchema` 驗證兩個分支。

## results-1 \{#copy-results-1\}


`metadata` 回報套件、語言與綁定版本、實際使用的情境、manifest 指紋、入口與相依關係；無法取得的值為 null 或空陣列。預設為專案情境：缺少入口或編譯失敗會造成錯誤，絕不無聲改用預設集。僅查詢預設集時，請明確傳入 `context: 'preset'`。

## results-2 \{#copy-results-2\}


class 檢查分別回報 `matchStatus`、`cssSyntaxStatus`、`cssValueStatus` 與 `browserSupport`，每項檢查記錄都指定版本、階段與範圍。CSS 文法錯誤不同於未知的未來能力；`var()` 不代表已確定計算值，除非真的執行瀏覽器檢查，`browserSupport` 都維持 `not-checked`。已知 CSS 數學型別會檢查，但不計算長度或轉換單位；不同 token 定義即使值相同，仍屬歧義。

## results-3 \{#copy-results-3\}


Markdown 與 MDX 擷取會將實際標記、程式碼與展示文字分開，回傳原始 UTF-16 範圍與納入或排除原因；CLI、編輯器與 MCP 共用相同 Rust 擷取及比對。CLI 報告版本獨立於此封套。MCP 酬載的 `root` 是設定的工作區根目錄；CLI 報告的 `cwd` 是指令根目錄。

## results-4 \{#copy-results-4\}


專案比較：編輯前後分別以 `includeSnapshot: true` 呼叫 `mastercss_scan_project`，再將兩個 `result.data.snapshot` 物件以 `beforeSnapshot` 與 `afterSnapshot` 傳入 `mastercss_css_compare`；不可混用 class、content、`filePath` 或 `context` 輸入。結果為 `{ version: 3, mode: 'project', comparison }`，其中 `comparison.version` 為 1，列出變更定義、已知使用端與檔案、前後規則、原生參照、輸出資源、交付順序與 `coverage`。原生使用端採樣式表粒度保守分析。

## results-5 \{#copy-results-5\}


設計系統檢查：`mastercss_scan_project.designSystem` 接受[設計系統選項](/reference/tools/cli#design-system-options)物件，不可搭配 `context: 'preset'`。`result.data.designSystem` 中的版本 1 報告，列出原本撰寫的 `var()` 參照及來源範圍、選擇器與 at-rule 祖先、匯入端、token 家族衝突、元件屬性詞彙（`components`）與政策診斷；從 JavaScript 匯入的樣式表請加入 `routeStylesheets` glob，並閱讀 `project.routeStylesheets`、`project.excluded` 與 `coverage`。未註冊自訂屬性仍可能透過原生 CSS 解析，不會自動視為錯誤。

## 設計系統的契約 \{#contracts-of-a-design-system\}

## body-23 \{#copy-body-23\}


以 Master CSS 建構的設計系統，可以用契約描述每個元件：它的 class 與放置位置、狀態、公開屬性，以及最小的正確標記。函式庫在自己的 `package.json` 宣告契約：

```json
{
  "name": "your-design-system",
  "masterCSS": {
    "contracts": "./dist/contracts.json",
    "check": "./check/index.js"
  }
}
```

`contracts` 是套件內的路徑，指向內容為 `{ "contracts": [...] }` 的 JSON 檔案。契約是帶有字串 `name` 與 `classes` 陣列的物件；其他欄位都由函式庫自行定義。選用的 `check` 是套件內的路徑，指向一個 ES 模組；該模組匯出 `check(source, contracts, { knows, strict })`，回傳的診斷包含 `code`、`severity`、`message`、`line`、`column`，並在適用時包含 `className` 與 `contract`。[`@master/ui`](https://ui.master.co) 是第一個以這種方式提供契約的函式庫。

## body-24 \{#copy-body-24\}


伺服器讀取工作區根目錄 `package.json` 的 `dependencies`、`devDependencies` 與 `peerDependencies`，從該根目錄解析每個套件，並保留宣告了 `masterCSS.contracts` 的套件。若都沒有，伺服器會改讀上層 monorepo 根目錄的相同欄位：也就是最近一個 `package.json` 列出 `workspaces`、或含有 `pnpm-workspace.yaml` 的目錄，且不會超出該 儲存庫。專案可在根目錄 `package.json` 的同一欄位用 glob 加入自己的契約，例如 `"masterCSS": { "contracts": "contracts/*.json" }`。函式庫在自己的 儲存庫 中，也可以在同一處宣告 `masterCSS.check`，用自己的檢查器檢查這些契約。有 `master-ui.json` 的專案，還會加入其 `directory`（預設為 `ui`）內的 JSON 檔案與其 `contracts` glob。專案契約會取代同 `name` 的函式庫契約。結果中的每個契約都帶有 `source`：套件與版本，或專案檔案及其取代的函式庫契約。

## body-25 \{#copy-body-25\}


伺服器只匯入已宣告相依套件或工作區本身 `package.json` 所指定的檢查器，而且路徑必須位於該套件內；專案的契約檔案只當作資料讀取，絕不執行。檢查器是該套件提供的程式碼。伺服器在 worker thread 中執行它；單一檔案超過 10 秒，或檢查器超出記憶體上限時，會停止它並回報 `CONTRACT_CHECKER_FAILED`。每次檢查都會重新載入檢查器，因此升級後的函式庫不必重新啟動就會生效。檢查器會收到 `knows(className)`，它依專案 manifest 回答某個 class 是否為有效的 Master CSS class，或專案樣式表定義的原生 class；只有在 manifest 載入成功時才會收到 `strict: true`。否則不提供 `knows`，且 `strict` 為 false。檢查器依照撰寫的標記判讀，無法確認執行階段產生的 class 或瀏覽器行為。
