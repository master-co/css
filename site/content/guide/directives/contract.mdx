## Entry markers \{#entry-markers\}
Use `@import` to deliver a stylesheet and make its definitions available. Use `@reference` when local compilation needs those definitions but another output owns the native stylesheet. For application setup, follow [Installation](/guide/installation); for route-specific ownership, see [Route-level styles](/guide/route-level-styles).

<ReferenceIllustration id="import-reference-output" />

### `@import "@master/css"` \{#import-mastercss\}
The package import is the only project entry marker. It loads the preset's native CSS, including its stable layer order and base styles, and identifies the stylesheet that receives generated utility CSS.

```css
@import "@master/css";
```

Explicit standalone compiler and manifest APIs remain available. A manifest alone does not load native CSS; applications using runtime or server rendering must also deliver the relevant native stylesheet.

### Local file URLs \{#local-file-urls\}

Node file compilation reads CSS import names using CSS escaping and case rules.
Relative `@import` and `@reference` URLs resolve their pathname against the source
file: percent escapes identify filename characters, while query strings and
fragments are excluded from the filesystem path. For example,
`"./tokens%20%23.css?v=1#theme"` reads a sibling file named `tokens #.css`.
Existing bare relative CSS paths such as `"tokens.css"` are also expanded. Bare
package imports without a matching local file remain available to the host
resolver. Reference files remain compile-time context and do not emit their native CSS.
For a prepared virtual stylesheet, the host's explicit filesystem source owner
also supplies the base for relative CSS references. Resources in a referenced
theme token remain relative to the reference file when used elsewhere.

### Stylesheet boundaries and resource URLs \{#stylesheet-boundaries-and-resource-urls\}

Import media, supports and layer qualifiers apply to the imported stylesheet. Keep those boundaries when publishing CSS, and resolve image and font URLs from their original source file. A token used through `@reference` also retains its defining file as the resource owner.

Global Master definitions belong in unqualified imports or references. A qualified import can contain native CSS, including native rules that apply a previously available mixin; it cannot register `@theme`, `@utility`, `@mixin`, `@custom-media` or `@custom-container` definitions.

```css
@import "./tokens.css";
@import "./print.css" print;
@import "./components.css" layer(components);
```

Each `@import` inlines its stylesheet again, so a file imported from several places is repeated. One import graph inlines at most 10,000 stylesheets and 64 MiB of CSS; import shared files once instead of from every file that uses them.

Loading definitions and scanning metadata does not publish files. CLI file export and Vite production builds publish the required stylesheet and resource assets. Custom compiler hosts must publish every asset returned by their delivery APIs; a manifest alone does not deliver native rules. See [rendering and stylesheet delivery](/guide/rendering-modes#native-css-entries) and [compiler entrypoints](/reference/packages#css-compiler).


### Publish the complete asset set \{#publish-stylesheet-assets\}

A compiled CSS entry can still import other CSS files or refer to images and fonts. Publishing only the entry text leaves those dependencies unavailable. Preserve each returned URL and import qualifier; flattening a child with an external import can change its loading order or conditional scope.

<ReferenceIllustration id="stylesheet-asset-graph" />

| Delivery path | Owner of publication |
| --- | --- |
| CLI `generate --output dist/app.css` | The CLI flattens local imports into the entry and writes the resource files and any sibling CSS a retained boundary needs. Deploy that whole set. |
| Vite production build | The integration flattens managed imports into Vite's CSS asset and emits the remaining assets into the build. Deploy the complete output with its configured public base. |
| `compileManifestFileSync()` with `delivery` | The API returns stylesheet contents and resource destinations. The custom host writes or serves them. |
| A manifest or CSS string | Neither publishes files. The caller still owns native CSS delivery and referenced resources. |

Production flattening keeps the cascade: layer statements stay in place, `layer()`, `supports()` and media qualifiers become the equivalent `@layer`, `@supports` and `@media` blocks, and empty stylesheets disappear. External imports at the top of a stylesheet move up with it when only other external imports precede it. A stylesheet that keeps a namespace or an import under a qualifier, or whose external imports would follow inlined rules, remains a separate file, as do the imports before it in the same file, because an `@import` cannot follow rules.

Images and fonts retain the defining stylesheet as their source owner, including resources used through `@reference`. Publication rewrites their URLs while retaining query strings and fragments. Reference-only stylesheets are not published merely because their definitions were read.

The CLI's `--no-export` path prints CSS without copying assets. Its file-export watch path keeps the last successful output when an imported stylesheet or resource is missing, reports the error, and rebuilds after recovery. Do not treat stale output as a successful latest build.

For a custom host, use the [compiler delivery contract](/reference/packages#css-compiler). For Vite's processed-text, raw-source and URL imports, use [Stylesheet loading](/guide/installation/vite#stylesheet-loading). [Route-level styles](/guide/route-level-styles) explains which page owns a local stylesheet.

## Reference context \{#reference-context\}
### `@reference` \{#reference\}
Use a reference when compilation needs definitions from another stylesheet without importing its native rules. This example loads a spacing token and a selector mixin from the app entry:

```css name=app.css
@import "@master/css";

@mixin --manual-dark {
  &:where([data-theme="dark"], [data-theme="dark"] *) { @contents; }
}
```

```css name=Button.module.css
@reference "../app.css";

.button {
  padding: var(--spacing-md);
  @apply --manual-dark { color: white; }
}
```

A reference supplies tokens, utilities, mixins, custom media, custom containers and native keyframe definitions for resolution. It does not deliver the referenced file's native CSS, generate its classes, or add its scanning sources. Used managed tokens and keyframes can still cause local output to include their dependencies. Referenced native rules are never usage roots. Native overrides need an actual `@import` or another delivered stylesheet. Referenced keyframes are emitted only when locally used.

<ReferenceIllustration id="reference-no-roots" />

References must be top-level statements containing one quoted resource. Relative paths use the declaring stylesheet's directory. Package references resolve exported CSS entries. References are not entry markers.

Vite, Next.js, and Webpack supply project definition context to local stylesheets, CSS Modules, and SFC styles. An explicit reference is useful for dependencies outside that context or standalone compilation. Local stylesheets do not become scanning or pruning roots. CSS Modules and scoped hosts must deliver generated theme selectors globally.

Definition context loads before local definitions, so local definitions can replace imported or referenced ones. Compiler hosts that split CSS output must also track which output delivers shared variables and keyframes; see [compiler resource ownership](/reference/packages#css-compiler).

## Theme declarations \{#theme-declarations\}
`@theme` registers tokens for utility definitions. Its modifiers independently control which token declarations are delivered and whether generated values use `var()` or substitute the authored value. [Theme tokens](/guide/theme) teaches project setup; [Variables and modes](/reference/rules/modes) explains scope, inheritance and resolution.

### `@theme` \{#theme\}
Declare utility tokens as custom properties. A theme block must be top-level and accepts only custom-property token declarations. Declare keyframes in native CSS outside the block.

```css
@theme {
  --color-brand: #4f46e5;
  --spacing-card: 1.5rem;
}
```

Unknown or repeated modifiers are errors. The `static` and `inline` modifiers can appear in either order.

| Declaration | Token delivery | Generated value |
| --- | --- | --- |
| `@theme` | On demand | `var(--token)` |
| `@theme static` | Always | `var(--token)` |
| `@theme inline` | Only if retained by another reference or dependency | Declared value |
| `@theme static inline` | Always | Declared value |

Tokens emit in `@layer theme` under `:root, :host`. The compiler preserves declaration order and repeated values. Used tokens retain their transitive variable dependencies. Selectors and conditional rules belong in native CSS outside the block.

Only `@theme` registers named tokens for utility patterns. A native declaration such as `:root { --app-brand: red; }` remains ordinary CSS; use it directly with `(color:var(--app-brand))` or bridge it through an inline theme token.

<ReferenceIllustration id="theme-modifier-axes" />

### `@theme inline` \{#theme-inline\}
Use `inline` to substitute a token's declared value into Master-generated declarations:

```css
@theme inline { --color-brand: var(--app-brand); }
:root { --app-brand: #4f46e5; }
[data-theme="ocean"] { --app-brand: #0369a1; }
```

`bg-brand` emits `background-color:var(--app-brand)`, resolving the native variable on the element using the class. The same substitution applies to direct declaration classes, utility classes, and native `@apply` expansion. Handwritten native declarations retain their authored `var()` references.

Substitution runs once. Variables, functions, and fallbacks inside the replacement value keep native CSS semantics. Dependencies are collected from the resulting declarations; using an inline utility alone does not force its replaced token to emit. A direct native reference to the token can still retain its declaration.

For repeated theme definitions, importance and then source order select the inline value and mode. Custom-property `!important` does not make the generated utility important. Ordinary aliases resolve in their declaring scope; use inline when a bridge must read another variable at its use site.

### `@theme static` \{#theme-static\}
Use `static` when tokens must be emitted even without a class or native reference:

```css
@theme static { --color-integration: #4f46e5; }
@theme static inline { --color-brand: var(--app-brand); }
```

`static` controls token delivery; `inline` controls generated values. They can be combined in either order. A token with any static declaration stays retained, together with its dependencies, until its definition is removed. Referenced stylesheets do not become output roots merely because their tokens are static.

### Native theme overrides \{#theme-mode\}
Register the default value in `@theme`, then override the variable using native selectors or queries:

```css
@theme { --color-panel: white; }
[data-theme="ocean"] { --color-panel: #082f49; }
@media (prefers-color-scheme: dark) {
  :root { --color-panel: #111827; }
}
```

Native overrides retain their authored scope, layer, and stylesheet delivery. Unlayered normal overrides outrank normal theme-layer declarations on the same element. A later layer such as `defaults` also gives overrides priority while allowing component and utility layers to take precedence. Import the native stylesheet wherever its overrides are needed; `@reference` supplies definitions without delivering those rules.

The preset uses native `light-dark()` for adaptive colors and shadows. Both variable branches remain dependencies. Its native base CSS sets the root to `color-scheme: light dark`, with light/dark `data-theme` selectors for elements and shadow hosts. See [Colors](/guide/colors#native-color-scheme-and-manual-themes).

<StylesheetExample title="Scoped tokens in native CSS" source={"@theme { --color-brand: #4f46e5; }  .dark { --color-brand: #111827; } .card { color: var(--color-brand); }"} />

### Removing tokens \{#theme-removal\}
A theme declaration whose value is `initial` removes the token instead of declaring it. Every earlier definition of that name is dropped, including preset tokens and those of a base manifest, and neither the earlier value nor `initial` is delivered. Utilities no longer resolve the removed key. A later declaration of the same name defines the token again.

```css
@import "@master/css";
@theme { --duration-fast: initial; }

/* The project's own variable, unrelated to the preset token of the same name */
.panel { --duration-fast: 120ms; transition-duration: var(--duration-fast); }
```

Without the removal, the native `var(--duration-fast)` reference would retain the preset's `--duration-fast` at `:root, :host`, giving elements outside `.panel` a value they did not have before. Remove a token when native CSS uses its name for something else; keep it and override it natively when the project still wants the preset default.

## Query definitions \{#query-definitions\}
Name a reusable condition once, then use it in native CSS or a class suffix. Media names describe viewport or device conditions; container names describe a condition tested against a container selected at the use site. Definitions must be top-level and unconditional.

[Conditions](/reference/rules/conditions) owns class suffix syntax, [Named conditions](/reference/rules/named-conditions) lists every preset condition, and [Responsive design](/guide/responsive-design) teaches choosing a layout boundary.

<ReferenceIllustration id="container-condition-expansion" />

### `@custom-media` \{#custom-media\}
Define named media queries using the [CSS Media Queries specification](https://drafts.csswg.org/mediaqueries-5/#custom-mq):

```css
@custom-media --wide (width >= 60rem);
@custom-media --reading (--wide), print;
@custom-media --outside not (--reading);
@custom-media --enabled true;
@custom-media --disabled false;

@media (--reading) { .article { max-width: 70ch; } }
```

Names begin with `--`. CSS references use `(--name)`; markup uses `@name`, and a local named block uses `@media (--name)`. The same registry is used in native CSS, utility and mixin definitions, and markup queries.

Definitions support query lists, forward references, `true`, `false`, nested boolean expressions, negation, and media types. Expansion is logical: a list retains its disjunction, and negation applies to the complete referenced expression. Each query in a list becomes a separate branch, and the branches of every condition on a class multiply; a class that expands to more than 4,096 branches, such as one repeating `@reading` a dozen times, generates no rule. The compiler emits ordinary media queries, using nested blocks where a single query cannot express mixed media types. No browser custom-media API or JavaScript runtime registration is required.

Undefined, cyclic, and invalid references are compilation errors. A later same-name definition wins. Media and mixin names are independent: `@name` selects media, while `@apply(--name)` invokes a mixin. `--starting-style` is reserved because `@starting-style` is built in. The preset has no `--breakpoint-*` tokens. A project custom property with that prefix remains ordinary CSS and never implicitly declares a media condition. Use native lengths or independently named layout tokens for width caps. Imports that retain external URLs cannot contain unresolved custom-media queries; resolve those stylesheet imports before lowering or use ordinary native queries on the import.

<StylesheetExample title="A named media condition" source={"@custom-media --card (width >= 40rem); .card { @media (--card) { display: grid; } }"} />

### `@custom-container` \{#custom-container\}
Master CSS expands `@custom-container` definitions during compilation; browsers receive ordinary `@container` rules. A definition holds only the condition. Choose the container to measure where the condition is used.

```css
@custom-container --md (width >= 28rem);
@custom-container --max-md not (--md);
@custom-container --compact style(--density: compact);
@custom-container --dense (--md) and (--compact);

@container card (--md) { .title { font-size: 1.25rem; } }
```

Names begin with `--`. CSS references use `(--name)` after an optional container name, such as `@container card not (--md)`. Markup uses the same reference inside the container query: `@container(--md)` measures the nearest container and `@container(card|--md)` a named one. Native CSS, utility and mixin definitions, and markup share one registry.

A definition is any container condition: size and style queries, `not`, `and`, `or`, and references to other custom containers, including forward references. Expansion substitutes the referenced condition, parenthesized unless it is already one group or the whole condition, so `@container card (--dense)` emits `@container card (width >= 28rem) and style(--density: compact)`. A container condition always fits one prelude; expansion never adds branches. The compiler emits ordinary container queries and stores each expanded condition in the manifest's `customContainers`.

Undefined, cyclic, and empty references are compilation errors, as is a definition that starts with a container name. A later same-name definition wins, and definitions that reference it use the final one. Container names are independent of custom media and mixins: a bare `@md` always selects custom media, never a container condition. `--container-*` tokens size elements and never supply container thresholds.

<StylesheetExample title="A named container condition" source={"@custom-container --roomy (width >= 40rem); .card { @container (--roomy) { display: grid; } }"} />

## Utilities and native styles \{#managed-definitions\}
`@utility` registers classes generated on demand. `@mixin` names a reusable CSS body; `@apply` expands it where it is called. Native selectors remain ordinary CSS. [Reusing styles](/guide/reusing-styles) teaches which form to choose; this page defines their grammar and replacement rules.

### `@utility` \{#utilities\}
Declare the class form explicitly at the top level:

```css
@utility card-layout {
  display: grid;
  gap: var(--spacing-md);
  &:hover { outline: 1px solid currentColor; }
}

@utility col-gap-(--spacing) {
  column-gap: var(--spacing);
}

@utility grid-cols(--cols <integer>) {
  display: grid;
  grid-template-columns: repeat(var(--cols), minmax(0, 1fr));
}
```

Use `card-layout`, `col-gap-sm`, and `grid-cols(3)@sm` in markup. The header determines whether a definition registers a fixed class, a token pattern, or a function. Each form registers only that form. A token pattern does not also create a function call. Adding declarations or supported nested rules does not change the registration.

A utility name or token prefix cannot contain `_`, because `_` begins a descendant selector in classes; such a definition reports an error at its source. Token keys may contain `_`: they remain valid variables for `var()`, but they do not create bare token classes or completions. Mixin names, custom properties and native stylesheet classes may still use `_`.

### Registration and the preset \{#named-and-enumerated-classes\}
A theme supplies tokens; utility definitions determine which classes those tokens can produce. Import `"@master/css"` for the complete preset, or load `"@master/css/utilities.css"` alongside your own tokens when composing a stylesheet explicitly.

The [family index](/reference/tokens/families) owns the complete token-to-property mappings. [Fixed utilities](/reference/rules/declarations#fixed-utilities) and [Direct values](/reference/direct-values) list their corresponding registrations. All use the same definition forms described here.

### Token patterns \{#named-token-patterns\}
A pattern has one trailing placeholder. Its parameter names the token namespace; the fixed part names the class prefix. An untyped placeholder binds the token value:

```css
@utility p-(--spacing) { padding: var(--spacing); }
@utility m-(--spacing) { margin: var(--spacing); }
@utility fg-(--color) { color: var(--color); }
@utility size-(--spacing) {
  width: var(--spacing);
  height: var(--spacing);
}
```

`p-md` binds `var(--spacing-md)`; `size-md` uses that reference in both declarations. Ordinary tokens retain browser-evaluated references, while inline tokens substitute their declared value once. Unknown tokens do not create classes. Value patterns accept numeric and Unicode keys, including keys containing `--`.

A `<string>` placeholder binds the token key, allowing explicit companion references:

```css
@theme {
  --text-hero: var(--font-size-5xl);
  --text-hero--line-height: 1.15;
  --text-hero--letter-spacing: -.03em;
}
@utility text-(--text <string>) {
  font-size: var(ident("--text-" var(--text)));
  line-height: var(ident("--text-" var(--text) "--line-height"), normal);
  letter-spacing: var(ident("--text-" var(--text) "--letter-spacing"), normal);
}
```

`text-hero` binds the string `"hero"`. A matching primary token is required. Companion keys containing `--` do not create classes, and missing companions use the authored fallback. `ident()` folds statically into an ordinary CSS identifier. The namespace comes from the parameter, so `@utility type-(--text <string>)` uses the same tokens with a different class prefix. Token placeholders accept no defaults or other types.

A shared prefix can expose several namespaces explicitly:

```css
@utility font-(--font-family) { font-family: var(--font-family); }
@utility font-(--font-size) { font-size: var(--font-size); }
@utility font-(--font-weight) { font-weight: var(--font-weight); }
```

`font-sans`, `font-sm` and `font-bold` each select the one namespace containing that key. A key present in multiple branches reports `AMBIGUOUS_TOKEN` when used and produces no CSS. Use distinct keys or a native declaration such as `(font-size:var(--font-size-brand))`. This rule also applies to string-key recipes and bodies with multiple declarations. Negation and opacity are checked only after a unique branch is selected.

Fixed classes take priority over patterns: the complete class spelling is reserved, not the token key, so `text-center` sets `text-align` even when `--text-center` exists, while `fg-solid`, `b-solid/.5` and `-mx-auto` still reach tokens named `solid` or `auto`. Patterns use the longest prefix; an unknown token in the selected family reports an error without retrying a shorter prefix. Token patterns sharing a prefix coexist when their parameter namespaces differ. A later pattern replaces the entire definition with the same decoded prefix and namespace, including its parameter mode, body, source and dependencies. Static and function registrations replace the same form and name independently.

Negative values and opacity apply to the direct-value subset: one untyped placeholder and one native declaration whose entire value is `var(--parameter)`. `-m-md` negates a numeric spacing token; `-p-md` is invalid because padding does not support negative values. `fg-red/.5` applies opacity to a color token, with opacity between zero and one. These capabilities do not extend to general multi-declaration or string-key recipes.

### Static arguments \{#dynamic-values\}
Function utilities and mixins accept positional parameters: untyped, `<integer>`, `<number>`, `<string>`, or `<custom-ident>`. Static defaults use a colon, such as `--cols <integer>: 2`. Numbers must be numeric literals; grid counts and spans must be positive integers. String arguments require quotes.

```css
@utility pair(--size) {
  width: var(--size);
  height: var(--size);
}
```

Use `pair(2rem)`. General function arguments must be statically known. A function or mixin with exactly one untyped, default-free parameter and one native declaration whose complete value is `var(--parameter)` also accepts symbolic `var()` expressions. Its caller's reference remains intact for browser evaluation. Other functions reject external `var()`, `attr()`, and browser-dependent arguments. A known outer parameter may be forwarded through `var(--parameter)`.

### `@mixin` and `@apply` \{#reusing-a-matched-value\}
Master compiles a static subset of the experimental [CSS Mixins specification](https://drafts.csswg.org/css-mixins-1/#mixin-rule). Definitions have dashed names and must be unconditional stylesheet-level rules. A mixin supplies CSS reuse; it does not register a Master class.

```css
@mixin --caption {
  font-size: var(--font-size-sm);
  line-height: 1.5;
}
.caption {
  color: currentColor;
  @apply --caption;
  font-weight: 600;
}
@utility caption {
  @apply --caption;
}
```

`@apply` accepts one mixin call inside a native rule, utility, or another mixin. It does not accept utility names or class lists. Expansion occurs at the authored declaration position, preserving duplicates, importance, selectors, conditions and URL ownership.

Parameters can be used on the applying element, including `&:hover` and condition wrappers. Cross-element parameter use, reassignment, selector or condition interpolation, recursive definitions, overloads, `@private`, and unsupported types report compilation errors. The static subset does not implement browser-dependent parameter evaluation, private properties or general-purpose functions.

<ReferenceIllustration id="mixin-splice" />

### Contents and class wrappers \{#contents\}
Use `@contents` to mark where a caller’s declarations or nested rules enter a reusable wrapper.

```css
@mixin --card-wide() {
  @container card (width >= 40rem) { @contents { display: grid; } }
}
.card { @apply --card-wide { gap: 1rem; } }
```

`@contents;` inserts supplied content. `@contents { … }` supplies fallback content only when the call omits its block. An explicit empty `@apply --card-wide {}` suppresses fallback. Each contents position inserts the block once, preserving declarations, duplicates and nested rules. A mixin without `@contents` ignores the supplied block.

<ReferenceIllustration id="contents-default-vs-empty" />

Supplied content retains the caller's parameter bindings, including when forwarded through nested applications. Fallback uses the defining mixin's bindings. Ordinary custom properties retain native CSS cascade behavior. Finite nested calls are allowed; recursive definitions and expansion depth/node limit violations are errors.

```css
@mixin --hocus {
  &:is(:hover, :focus-visible) { @contents; }
}
@utility emphasis { color: red; display: block; }
```

```html
<button class="(color:red)@apply(--hocus)">Save</button>
<div class="grid-cols(3)@apply(--card-wide)"></div>
<div class="emphasis@apply(--hocus)!"></div>
```

`@apply(--name(...))` accepts static arguments. Multiple `@` wrappers nest from left to right: `(color:red)@apply(--a)@apply(--b)` puts `--a` outside `--b`. A utility supplies its declarations as one block, so a wrapper's own declarations are emitted once per class. Selector suffixes retain their existing placement; a final `!` marks every expanded declaration important. The class head and its condition suffixes other than `@apply` order the class: each outer condition branch is one rule that sorts on its own, while the mixins' inner selectors and conditions stay in the emitted text without moving the class to a later tier, and the expansion keeps its authored order. An expansion that adds no declaration, selector or condition sorts with single-declaration utilities, or with native declarations for a `(property:value)` head; any other expansion sorts as a recipe. Inspection and conflicts use the expanded rules.

Unused definitions, discarded contents and unused fallback blocks do not retain tokens or keyframes. Delivered native `@apply` remains a resource root through the emitted-globals contract. Declaration locations and relative URLs retain their defining or calling file.

<ReferenceIllustration id="contents-insertion" />

### Whole-definition replacement \{#whole-definition-replacement\}
A later definition replaces the complete body of the same registration; declarations are not merged. A static utility and a function utility with the same name are separate registrations. Token patterns replace only the branch with the same decoded prefix and namespace.

```css
@utility badge { color: red; padding: 1rem; }
@utility badge { color: blue; }
```

`badge` now emits only `color: blue`. The earlier padding and its dependencies are gone.

<ReferenceIllustration id="definition-replacement" />

A mixin name has one final definition, including its parameter list, body and dependencies. An empty definition remains registered. Forward nested calls resolve against the final registry; there is no parameter overloading.

<ReferenceIllustration id="independent-registrations" />

### Definition scope and imports \{#definition-scope-and-imports\}
`@theme`, `@utility`, `@mixin`, `@custom-media`, and `@custom-container` are top-level definitions. Registering them inside a layer or conditional wrapper is an error. Mixin bodies may contain declarations, nested selectors, supported native conditions, nested `@apply`, and `@contents`. Layer placement belongs at the call site.

Classes from source scanning, safelists, engine APIs and runtime DOM changes are usage roots. An `@apply` in delivered native CSS is also a root; one inside an unused utility or mixin or undelivered `@reference` stylesheet is not. Dependency collection occurs after parameter binding and `ident()` folding. Used tokens preserve ordered declarations and transitive dependencies. Static tokens remain roots without consumers. Removing the final root releases its resources; native CSS resources remain pinned through `emittedGlobals`.

Runtime manifests retain unused definitions for future DOM classes. On-demand generation concerns CSS and resource output. Native CSS pruning remains opt-in; keyframes share their declaring file’s native preservation and pruning policy. Qualified imports must contain native CSS only. Load definitions through an unqualified import or reference.

### Native property precedence \{#literal-and-raw-values\}
A native `(property:value)` class retains its CSS property meaning independently of utility registration. Under equal conditions, single-declaration utilities and native declaration classes can override part of a recipe. See [Declarations and values](/reference/rules/declarations#combining-declarations) for complete ordering and override rules.

### Native defaults \{#defaults\}
Write native defaults in `@layer defaults`.

### Native components \{#components\}
Write native component selectors in `@layer components`.

```css
@layer components {
  .button {
    display: inline-flex;
    padding: var(--spacing-md);
    &:focus-visible { outline: 2px solid currentColor; }
  }
}
```

Native rules are delivered according to the stylesheet import graph. Utility definitions register class names; mixin definitions provide CSS reuse through `@apply`. Both are consumed during compilation and emit CSS only when used.

### Sass interoperability \{#sass-interoperability\}

Place CSS mixin definitions in a `.css` file when using Sass. Current Dart Sass reserves `@mixin --name` for future CSS support and rejects it as a Sass mixin; see [Sass's compatibility notice](https://sass-lang.com/documentation/breaking-changes/css-function-mixin/). An SCSS file may emit the native at-rule through interpolation before Master CSS compiles it:

```scss
@#{'mixin'} --card {
  padding: 1rem;
}

.card { @apply --card; }
```

This is Sass interpolation, not additional Master CSS syntax. Sass `@include` and CSS `@apply` remain separate constructs.

### Theme selector wrappers \{#theme-wrappers\}
Native selectors and queries activate theme overrides. A mixin can provide a matching class condition:

```css
@mixin --ocean {
  &:where([data-theme="ocean"], [data-theme="ocean"] *) { @contents; }
}
```

Use `(color:white)@apply(--ocean)`. Add explicit `:host(...)` selectors when targeting a shadow host.

## Source boundaries \{#source-boundaries\}
File policy chooses where to read candidates; candidate policy chooses which complete class strings remain eligible. These directives do not change the parser or turn arbitrary source text into valid utilities. See [Scanning class names](/guide/scanning-and-pruning) for configuration and troubleshooting, and [Extraction](/reference/rules/extraction) for supported source syntax and lifecycle.

<ReferenceIllustration id="scanning-two-filters" />

### `@source` \{#source\}
Ordinary application sources use the integrations' and CLI's default discovery. Add explicit exceptions when needed:

```css
@source "../content/**/*.mdx";
```

### `@source not` \{#source-not\}
Exclude matching files from the source set:

```css
@source not "../content/drafts/**";
```

Brace groups such as `{a,b}` expand to separate patterns; one pattern may contain at most 64 brace groups and expand to at most 1,024 patterns.

Includes are combined as a union, then all excludes are subtracted. Every relative pattern resolves from the stylesheet that declares it, including bare `src/**`, `./src/**`, imported files, and `@source not`. A reference does not contribute scanning sources.

File-resolving APIs require a declaring file or explicit base file. Source-only directive inspection can return unresolved metadata; it must not invent a filesystem base. The scanner's programmatic `cwd` option retains its existing meaning for scanner options supplied directly through that API.

## Candidate policy \{#candidate-policy\}
### `@safelist` \{#safelist\}
Add complete class candidates that cannot appear literally in scanned source:

```css
@safelist "(opacity:1)";
@safelist "bg-blue-60@dark";
```

Candidates use the same matching and diagnostic policy as discovered classes. Keep dynamic alternatives bounded and explicit.

To retain named animation definitions without generating a class or animation declaration, use the explicit keyframe target:

```css
@safelist keyframes "fade" "pop";
```

Each quoted string is one complete CSS animation name. Names are case-sensitive and support CSS escapes; a space inside a string is part of its name. There is no wildcard expansion or class splitting. Missing names, unquoted names, commas and nested safelist directives are errors. A name absent from the complete import/reference graph produces a warning. Safelists merge within each entry's graph and are withdrawn when their source or directive is removed. `@reference` does not import safelist roots. There is no keyframe blocklist or separate keyframe prune/preserve target.

### `@blocklist` \{#blocklist\}
Remove unwanted complete candidates with exact strings or `*` and `?` wildcard patterns:

```css
@blocklist "debug-*";
@blocklist "example-token";
```

The stylesheet grammar does not interpret slash-delimited patterns as regular expressions. Wildcard policy belongs in the blocklist; a safelist supplies complete classes.

## Native CSS preservation \{#native-css-preservation\}
Native CSS pruning removes unused class-selector branches and makes keyframes available on demand. It is a stylesheet policy, separate from generating utility classes. [Optimizing CSS delivery](/guide/optimizing-css-delivery#native-pruning) teaches when to enable it; [Scanning directives](/reference/directives/scanning) owns the source and candidate filters.

<ReferenceIllustration id="pruning-file-boundary" />

Native CSS is preserved by default, even when a class list is supplied. Set
`pruneNativeCSS: true` in an integration or stylesheet API to prune project-owned
sources. Package CSS stays preserved unless its own source explicitly opts in.

### `@prune native` \{#prune-native\}

```css
@prune native;
.used { color: red; }
.unused { color: blue; }
```

This directive opts only its declaring file into pruning. It does not propagate
to imported stylesheets. `@preserve native;` takes precedence in the same file,
including when the integration enables project-wide pruning. The native-output
switch `preserveNativeCSS: false` is separate and suppresses native output
regardless of either directive.

### `@preserve native` \{#preserve-native\}
Use `@preserve native;` when a Master-managed stylesheet contains native CSS class rules that must not be removed by native CSS pruning.

```css
@import "@master/css";
@preserve native;

.injected-by-payment-widget {
  color: blue;
}
```

The stylesheet is still processed by Master CSS. Native class rules are retained even when no scanned source uses their classes; ordinary compiler normalization still applies. This policy does not force unused managed classes into the generated output and does not mean that the original CSS bytes are preserved.

<ReferenceIllustration id="preserve-wins" />

### Import graph \{#import-graph\}
Resolved CSS imports keep their own source boundaries, so each file's policy
applies to that file alone. An importing file cannot enable pruning in its
dependencies. Under `pruneNativeCSS: true`, project-owned dependencies participate
unless they declare `@preserve native;`; package and remote styles do not become
project-owned because the project imports them. Qualified imports keep their
media, supports and layer wrappers.

```css name=src/style.css
@prune native;
@import "@master/css";
@import "./cards.css";
```

```css name=src/cards.css
@prune native;
.card { border: 1px solid rgb(0 0 0 / 12%); }
.unused-card { color: red; }
```

With `card` in scanned source, the output keeps `.card` and removes `.unused-card`.
Without the directive in `cards.css`, both rules stay.

### Root scope \{#root-scope\}
Activation belongs to each source file; filtering uses the usage scope of the root
that imports it. An opted-in shared file can therefore keep different classes under
different roots. A file imported directly by JavaScript or a framework route
becomes its own root only when that import enters the Master CSS pipeline.

By default a root uses the global scanner scope. `@source`, `@source not`,
`@safelist` and `@blocklist` anywhere in the root's import graph narrow or widen
it; directives in an imported file merge into every root that imports it, and
relative patterns resolve from the declaring file.

```css name=app/a/a.css
@prune native;
@import "@master/css";
@source "./page.html";
@import "../shared.css";
```

```css name=app/shared.css
@prune native;
@blocklist "debug-*";
.shared-card { border: 1px solid rgb(0 0 0 / 12%); }
.only-used-in-b { color: blue; }
.debug-outline { outline: 1px solid red; }
```

If `app/a/page.html` uses only `shared-card`, the `a.css` output keeps
`.shared-card` and removes `.only-used-in-b` and `.debug-outline`. A sibling root
`b.css` whose page uses `only-used-in-b` keeps that rule from the same file.

### Rule filtering \{#rule-filtering\}
A class selector rule is kept when any class in one of its selector branches is
used; unused branches are removed from selector lists. The check is by class name,
not by DOM relationship: for `.card .title`, finding either `card` or `title`
retains the branch, so a retained rule can still match no element.

```css
@prune native;
body { margin: 0; }
.card, .unused:hover { border: 1px solid rgb(0 0 0 / 12%); }
@media (width >= 48rem) {
  .card .title { font-weight: 700; }
  .debug-card { outline: 1px solid red; }
}
```

With `card` and `title` used, the output keeps `body`, `.card` and
`.card .title`, and removes `.unused:hover` and `.debug-card`. Rules without class
selectors, such as `body`, `html` and `:root`, are always kept. At-rule blocks left
empty by pruning are removed.

<ReferenceIllustration id="pruning-selector-branches" />

### Manifest references \{#manifest-references\}
A kept native rule that reads `var(--*)` or names a manifest animation retains the
matching theme variables and keyframes from the project entry graph. A removed
rule keeps nothing alive. A [removed token](#theme-removal) is not a theme
variable, so reading its name retains nothing.

```css
@prune native;
@import "@master/css";
@theme { --color-primary: #175cff; }

.notice { color: var(--color-primary); }
.unused-notice { color: var(--color-primary); }
```

If only `notice` is used, `--color-primary` is emitted because `.notice` is kept;
`.unused-notice` is removed.

### Included classes \{#included-classes\}
`@safelist` marks native classes as used when they come from a bounded external
source, so pruning keeps their rules. It does not replace application classes
written in scanned source.

```css
@prune native;
@safelist "dialog-open dialog-closing";
.dialog-open { overflow: hidden; }
.dialog-closing { pointer-events: none; }
```

### Native keyframes \{#native-keyframes\}
Declare keyframes in native CSS, and opt into usage-based output in their owning file:

```css
@prune native;
@theme { --animate-reveal: reveal .2s ease-out both; }
@keyframes reveal {
  from { opacity: 0; }
  to { opacity: 1; }
}
@safelist keyframes "external-enter" "external-exit";
@keyframes external-enter { from { opacity: 0; } to { opacity: 1; } }
@keyframes external-exit { from { opacity: 1; } to { opacity: 0; } }
```

Keyframes follow the same file policy as native class rules. By default they are native CSS: they stay in the output in place and verbatim, and Master CSS never emits them again. `@prune native;` turns the file's keyframes into on-demand definitions, like tokens: they leave its native output, and the output that uses one emits it with the generated CSS. `@preserve native;` wins when both appear. The policy applies only to the declaring file and does not propagate through imports. The `pruneNativeCSS` option retains its project-owned file scope. Package CSS stays preserved unless it explicitly opts into pruning. `preserveNativeCSS: false` suppresses native delivery; on-demand definitions are still emitted where they are used.

### Keyframe usage roots \{#keyframe-usage-roots\}

Animation utilities, native animation declarations, static animation tokens and keyframe safelists use their matching definitions. Analysis follows shorthand values, animation-name lists, nested variables, fallbacks, scoped overrides and transitive token dependencies. A used definition also uses the tokens its frames read; a native definition supplies only those tokens, since its stylesheet delivers the frames. Unresolved dynamic names conservatively use all candidate definitions in the compilation graph and produce an information diagnostic.

<ReferenceIllustration id="keyframe-reachability" />

### Keyframe conditions and restrictions \{#keyframe-conditions-and-restrictions\}

An emitted on-demand definition is wrapped in the conditional and layer rules it was declared in, including the layer of a qualified import, and follows the generated layers. Definitions of one container share one wrapper. Same-name definitions remain separate, in declaration order; the browser determines which definition wins. Names are decoded and case-sensitive. An anonymous layer cannot be re-entered, so on-demand keyframes in one, or imported into one, are compilation errors; name the layer or preserve the file. Their frames are emitted away from their stylesheet, so a relative `url()` in them is a compilation error; use an absolute URL or preserve the file. Definition IDs derive from the declaring file's nearest named `package.json` and its package-relative path, so the same project emits identical CSS from any checkout or installation directory. Renaming that package changes the IDs; files outside any named package fall back to their absolute path.

### Keyframe resource ownership \{#keyframe-resource-ownership\}

Frames contain native declarations; nested directives and `@apply` inside frames are unsupported. Unused utilities and mixins, pruned native rules and undelivered reference styles do not create usage roots. `@reference` makes definitions available on demand without importing their preservation policy or safelists; native keyframes with relative URLs stay with their stylesheet. Native keyframes of a project or base manifest are likewise on demand in a stylesheet that does not deliver them. Emitted globals list the keyframes an output delivers, natively or on demand, so another output does not emit them again. For animation names introduced only by JavaScript, use `@safelist keyframes "reveal";`.

### Runtime keyframe lifetime \{#runtime-keyframe-lifetime\}

The runtime tracks definition IDs separately from names and inserts on-demand definitions into its own stylesheet. DOM removal releases a definition only when no native usage, static token or safelist still uses it. HMR replaces definitions and emitted globals together; SSR hydration uses the same IDs and resource order. Linked stylesheets stay ordinary CSS with no companion files or markers.
