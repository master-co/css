Preload a resource only when the first screen needs it and normal discovery starts it too late. Static pages use ordinary CSS delivery. Runtime-only pages need their engine and program before generating styles; progressive pages already have the first screen's CSS.

## Preload the default program \{#preload-runtime-engine\}
Start with the [matching runtime assets](/guide/installation/cdn#host-matching-assets) on your static host or CDN. The HTML already exposes the stylesheet and script. Preload the default program so its request can start before the runtime script executes.

<ResourceWaterfall />

When its engine starts, the CDN runtime fetches `default-program.bin`, the default preset compiled for the engine. Use `as="fetch"` and `crossorigin` to match that fetch, including when the files are served from the same origin.

(o) Expose the late-discovered program with `html <link rel="preload">`.
```html
<!DOCTYPE html>
<html lang="en" hidden>
<head>
  <link rel="preload" as="fetch" crossorigin href="/master-css/default-program.bin"> <!-- [!code highlight] -->
  <link rel="stylesheet" href="/master-css/base.css">
  <script src="/master-css/global.min.js"></script>
</head>
</html>
```
The program request can now start during document parsing, alongside the stylesheet and script. The runtime can reuse that response when it starts. The stylesheet link and script tag already appear in this document's head, so they use normal HTML discovery.

## Preload runtime project programs
Official runtime integrations compile the project manifest into a runtime program, which production builds emit as a hashed binary asset. The runtime must load that program before it can execute project tokens, utility definitions, mixins, named conditions, and keyframes from your CSS entry graph.

(o) Let runtime-only integrations preload the project program.
```html
<!DOCTYPE html>
<html lang="en" hidden>
<head>
  <link rel="preload" as="fetch" crossorigin href="/assets/master-css-program.<hash>.bin"> <!-- [!code highlight] -->
  <script type="module" src="/assets/main.<hash>.js"></script>
</head>
</html>
```

The preload starts the program request while the browser is still parsing the document. The runtime module later imports `virtual:master-css-program`, whose facade fetches the same program. Matching `as="fetch"` and `crossorigin` enables reuse; confirm it in the target browser with your deployed cache headers.

(i) This optimization applies to pure runtime rendering. Progressive rendering already has critical CSS in `style#master-css`, and its runtime requests the project program only when the engine starts, so do not preload either program on progressive pages.

### Choose the right runtime asset
Master CSS hands off different files at different points:

| File | Used by | Preload? |
| --- | --- | --- |
| CDN default program | CDN runtime-only pages that use the packaged default preset. | Yes, when using the CDN runtime. |
| Project program asset | Official runtime integrations that emit `master-css-program.<hash>.bin` for `virtual:master-css-program`. | Yes, in pure runtime mode when the integration injects the runtime. No on progressive pages. |
| Page hydration manifest | Progressive pages that hand `style#master-css` rules to a browser runtime. | No. The browser can paint without it. |

## Defer runtime engine
On a progressive page, the critical CSS is already in `style#master-css`. With default startup options, the runtime defers its engine and project program until a class outside the page hydration manifest appears. Explicit engine startup or idle prefetch changes that behavior.

(o) Load the runtime as an ordinary deferred module script.
```html
<!DOCTYPE html>
<html lang="en">
<head>
  <script type="module" src="/main.js"></script>
</head>
</html>
```

(x) Avoid explicitly preloading the deferred engine or project program on progressive pages. Those requests can otherwise run even when no new class needs the engine. Application-module preloads have their own purpose; inspect the dependency graph to keep the deferred engine out of that initial graph.
```html
<!DOCTYPE html>
<html lang="en">
<head>
  <link rel="preload" as="fetch" crossorigin href="/assets/master-css-program.<hash>.bin"> <!-- [!code --] -->
</head>
</html>
```

When new classes usually appear soon after load, start the runtime with `enginePrefetch: 'idle'`. The runtime then schedules engine startup for an idle callback. This can reduce a later interaction’s wait, but does not guarantee that startup follows first paint or finishes before the interaction.

## Do not preload page hydration manifests
Progressive rendering can externalize the page hydration manifest:

```html
<style id="master-css" data-master-css-hydration-manifest="/_master-css/hydration/master-css-hydration.<hash>.json">...</style>
```

(x) Do not add a preload hint for this JSON file.

The page hydration manifest is runtime handoff data. It lets the runtime adopt the rules that already exist in `style#master-css`, but it is not required for the browser to paint the first screen. Let `MasterCSSRuntime.start()` import it. If a referenced manifest cannot be imported or validated, startup rejects with `INVALID_HYDRATION_MANIFEST`; if the engine later finds that the manifest does not match the style block, the runtime warns and rebuilds from connected DOM classes.

This is different from runtime project programs. A runtime-only page needs its project program before it can interpret classes. A progressive page already has the first-response rules in `style#master-css`, so its page hydration manifest only describes CSS that was already rendered into that one HTML response.

## Verify the request waterfall \{#benefits\}

Compare a cold load with and without the hint in browser DevTools. Check that the critical request starts earlier and the later consumer reuses it. Match the URL, resource type and credentials mode, and inspect response caching when a second request remains. An unused preload can compete with resources the page actually needs. See the [browser preload contract](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/rel/preload).

Use [Rendering modes](/guide/rendering-modes) to choose delivery first. A preload changes request discovery; it does not reduce the asset's parsing or execution work.
