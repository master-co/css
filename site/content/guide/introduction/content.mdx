## What is Master CSS?
Master CSS is a CSS framework for styling interfaces in markup and defining shared styles in CSS.

Its class language combines native declarations such as `display:grid`, named values such as `p-lg`, and conditions such as `bg-blue-70:hover`. Master generates CSS for recognized classes and retains the resources they need. You can start with the supplied theme and write local styles without designing a complete system first.

As values and patterns become shared, define them in your project CSS. Theme tokens, native component classes and custom utilities give those decisions names that you can reuse. Your stylesheets can also contain ordinary selectors, media queries, cascade layers and keyframes.

Use Master when you want to compose styles close to an element while keeping shared definitions in CSS. Complex selectors and longer reusable styles can stay in native stylesheets alongside your classes.

## Define values that should change together \{#write-your-first-class\}
In the card, `p-lg` reads a spacing token and `bg-surface-raised` reads a surface color. These names come from the supplied theme. Add your own token when several elements should share a project decision, such as the brand color used by primary actions.

After [Installation](/guide/installation), your application loads a CSS entry containing:

```css name=app.css
@import '@master/css';
```

Add the following definitions after that import. The two links show alternative ways to give the card's action a brand background: `bg-brand` uses the theme token through a Master class, while `card-action` uses the same token in native CSS.

Both backgrounds reference `--color-brand`. Changing that definition updates both consumers wherever the value applies. Local layout classes can still differ, and a reusable component can collect more declarations as its role becomes clear.

Share a token because its consumers should change together. An informational color may initially have the same value as the brand color and still deserve a separate token. ## Understand the next change
Suppose the brand color changes. Before editing `--color-brand`, inspect the project definitions and their known uses. After the edit, compare project snapshots to see which classes, stylesheets and outputs are affected. A class such as `bg-brand` can be affected even when its generated declaration still reads `background-color:var(--color-brand)`.

The tools can also locate token references in project CSS and check configured policies, such as requiring tokens for selected properties. [Code Linting](/guide/code-linting) explains the checks; the [project review workflow](/guide/ai-coding#review-the-second-change) shows how to inspect and compare changes.

You and your coding agent can use the same project definitions and checks. The CLI and MCP server expose these capabilities for development workflows; see [AI Coding](/guide/ai-coding) for setup and examples.

These reports cover known project sources. Some native CSS relationships are reported conservatively; they do not simulate which selectors and inherited values apply to every element. Generating CSS, checking syntax or policies, and finding dependencies provide different evidence. Check the rendered page and its interaction states in a browser to verify appearance, behavior and accessibility.

## Choose how CSS is delivered
Use the recommended static setup for your framework. It scans complete class names at build time and delivers ordinary CSS, without a Master browser runtime or engine.

Changing state does not require compiling CSS in the browser. Toggle known classes, use native selectors, or update custom properties for coordinates, progress and other dynamic values. Choose runtime when a playground, visual editor or deployed content introduces previously unknown class names. [Rendering Modes](/guide/rendering-modes) explains static, runtime and progressive delivery, including server pre-rendering.
