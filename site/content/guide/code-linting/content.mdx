## Overview [sr-only]
Catch invalid classes, conflicting declarations and inconsistent syntax as you edit. The ESLint integration uses your project's theme and custom definitions, so diagnostics reflect the classes your project can generate.

Start with the recommended config below, or use the [installation integrations](/guide/installation/integrations) to add it with your framework setup.

---

## Install the recommended config
Install ESLint and the recommended config in the project. Keep framework parser configuration when the project needs it.

```bash
npm install -D eslint @master/eslint-config-css@rc
```

The recommended config enables these rules:

```js name=eslint.config.js
import { defineConfig } from 'eslint/config'
import masterCSS from '@master/eslint-config-css'

export default defineConfig([
  ...masterCSS
])
```

| Rule | Default | Fixable | Purpose |
| --- | --- | --- | --- |
| `@master/css/sort-classes` | `warn` | Yes | Sort classes into a stable generated-rule order. |
| `@master/css/no-invalid-classes` | `error` | No | Report invalid Master CSS syntax and invalid generated CSS. |
| `@master/css/no-conflicting-classes` | `warn` | Yes | Report full and partial declaration conflicts in the same variant scope. |
| `@master/css/prefer-canonical-classes` | `warn` | Yes | Suggest canonical forms only when token identity and generated-rule behavior are preserved. |

## Linting rules
### Sort classes
`@master/css/sort-classes` keeps class strings stable and reviewable. It sorts known Master CSS classes before unknown classes, follows generated layer and condition priority, and groups base classes by their generated CSS intent: position and layout, size, spacing, box, typography, paint, and effects.

```mcss
bg-white font-md flex px-md relative (width:100%) shadow-lg r-md (z-index:10) (gap:0.5rem) <!-- [!code --] -->
relative (z-index:10) flex (gap:0.5rem) (width:100%) px-md r-md font-md bg-white shadow-lg <!-- [!code ++] -->
```

Variants such as `:hover`, `@dark`, and `@sm` stay after the base class body in generated condition order.

```mcss
bg-black:hover flex p-sm (width:100%) block@dark (text-align:center) <!-- [!code --] -->
flex (width:100%) p-sm (text-align:center) bg-black:hover block@dark <!-- [!code ++] -->
```

Sorting also removes duplicate class values in the same class string.

```mcss
inline-flex px-md inline-flex <!-- [!code --] -->
inline-flex px-md <!-- [!code ++] -->
```

Ordering is a formatting policy. It does not change generated CSS, but it makes class strings easier to review and keeps automated fixes deterministic across frameworks and editors.

### No invalid classes
`@master/css/no-invalid-classes` reports classes that match Master CSS syntax but generate invalid CSS.

```html
<button class="(font-size:16)">Save</button>
```

(x) `(font-size:16)` has a unitless nonzero length. Use a native length such as `(font-size:16px)` or a configured size token such as `font-md`.

By default, unmatched classes are ignored so teams can mix Master CSS with native global classes.

An unknown CSS value is a different case: the class can match the language while the validator cannot fully check its value. For example, the current validator reports `(display:banana)` as `unknown`, and this rule does not flag it. A clean lint result therefore does not establish browser support or the intended appearance.

Enable `disallowUnknownClass` when the project should only use classes known to the active Master CSS manifest. It rejects unmatched class names; it does not change unknown CSS-value diagnostics:

```js name=eslint.config.js
import { defineConfig } from 'eslint/config'
import masterCSS from '@master/eslint-config-css'

export default defineConfig([
  ...masterCSS,
  {
    rules: {
      '@master/css/no-invalid-classes': ['error', {
        disallowUnknownClass: true
      }]
    }
  }
])
```

```html
<button class="btn">...</button>
```

(x) `"btn" is not a valid or known class.`

Define project classes in the CSS entry when they are intentional:

```css name=index.css
@layer components {
  .btn {
    display: inline-flex;
    padding-inline: var(--spacing-md);
  }
}
```

### Prefer canonical classes
`@master/css/prefer-canonical-classes` checks for equivalent canonical forms while preserving token identity, value source, condition nesting and generated-rule ordering.

These classes remain unchanged:

```mcss
(margin:16px) block@dark@sm
```

The rule does not replace a literal with a token that currently has the same value, convert units, or reorder the authored conditions. Choose semantic tokens deliberately, and use the raw-value policy below when the team requires them.

### No conflicting classes
`@master/css/no-conflicting-classes` reports classes that emit the same declaration properties in the same variant scope.

```mcss
(margin:0.625rem) (margin:1.25rem) <!-- [!code --] -->
(margin:1.25rem) <!-- [!code ++] -->
```

(!) `"(margin:0.625rem)" is overridden by "(margin:1.25rem)".`

Variant scope matters. Classes with different selectors, modes, or conditions do not conflict with each other.

```mcss
(margin:2.5rem)@sm (margin:3.125rem)@md
```

A fully overridden class can be removed automatically. The winner follows generated CSS ordering, not the order of class names in the HTML. Reversing the two margin classes above still leaves `(margin:1.25rem)` as the winner.

Partial declaration overlaps need review. For example, the top border override below is reported, but the rule does not split the shorthand or remove the other three borders:

```mcss
(border-style:solid) (border-top-style:dashed)
```

Use the generated CSS preview to decide whether the override is intentional before changing it.

## Supported sources
The default config checks class strings in common markup and JavaScript locations.

| Setting | Default | Use |
| --- | --- | --- |
| `classAttributes` | `['class', 'className']` | Markup attributes that contain class strings. |
| `classFunctions` | `clsx`, `cva`, `ctl`, `cv`, `class`, `classnames`, `classVariant`, `styled`, `classList.add/remove/toggle/replace` | JavaScript callees and tagged templates whose arguments can contain class strings; `styled` also accepts member forms such as `styled.button`. |
| `classDeclarations` | `[]` | Project-specific variables or object properties that should be treated as class declarations. |
| `ignoredKeys` | `['compoundVariants', 'defaultVariants']` | Object keys ignored while traversing variant config objects. |

Customize settings under the `@master/css` settings key. Arrays replace their defaults, so include every helper or attribute you want ESLint to inspect:

```js name=eslint.config.js
import { defineConfig } from 'eslint/config'
import masterCSS from '@master/eslint-config-css'

export default defineConfig([
  ...masterCSS,
  {
    settings: {
      '@master/css': {
        classAttributes: ['class', 'className', 'containerClass'],
        classFunctions: ['clsx', 'cva'],
        classDeclarations: ['classes']
      }
    }
  }
])
```

## Team policy
Use stricter validation when the team wants every class to come from Master CSS syntax or the project manifest:

```js name=eslint.config.js
import { defineConfig } from 'eslint/config'
import masterCSS from '@master/eslint-config-css'

export default defineConfig([
  ...masterCSS,
  {
    rules: {
      '@master/css/no-invalid-classes': ['error', {
        disallowUnknownClass: true
      }]
    }
  }
])
```

Enable raw value policy when the team wants token-backed utilities to use tokens unless a value is explicitly allowed:

```js name=eslint.config.js
import { defineConfig } from 'eslint/config'
import masterCSS from '@master/eslint-config-css'

export default defineConfig([
  ...masterCSS,
  {
    rules: {
      '@master/css/no-unapproved-raw-values': ['warn', {
        allowProperties: ['width', 'height'],
        allowedPatterns: ['^var\\(', '^calc\\(']
      }]
    }
  }
])
```

```mcss
(font-size:15px) (margin:17px) (color:#123456)
```

(!) Unexpected raw value `"15px"` in `"(font-size:15px)"`. Use a token or allow it explicitly.

To regulate selected native properties, set `requireProperties: ['color', 'background-color']`. Omit it or use an empty array to check every token-backed property. `allowProperties` and `allowedPatterns` remain explicit exceptions; `allowRawValues` disables this policy. Native custom-property references remain valid.

The shared diagnostic identifies `no-unapproved-raw-values`, the applicable property scope and canonical token families in its `data`. The rule has no autofix: matching a token's current value cannot establish whether `brand`, `information` or another role is appropriate. This policy checks vocabulary use, not visual or design correctness.

## Native component CSS

Use `master-css inspect --design-system` for token references and naming collisions
in the project's managed CSS graph. Add `--design-system-options <file>` to supply
versioned token descriptions, deprecations and optional raw-value policy. See
[the native CSS review workflow](/guide/ai-coding#review-the-second-change).

This inspection is separate from ESLint's class-list rules. It keeps native CSS
declarations and duplicate declarations intact, reports source ranges, and offers
no automatic token replacement. Unmanaged or package CSS is outside its declaration
policy scope; browser cascade and visual behavior remain unchecked.
Native policy uses each token family's declared CSS properties. A shared class
prefix such as `font-*` does not make the native `font` shorthand token-backed.

## Editor feedback
The Master CSS extension provides completions, hover previews, color tools, highlighting and directive diagnostics. The VS Code ESLint extension adds class sorting, canonical syntax, conflict checks and invalid-class diagnostics. Use both when you want those checks while editing; the Master CSS extension avoids duplicating ESLint's class warnings by default.

Use editor sort-on-save for low-friction cleanup:

```json name=.vscode/settings.json
{
  "editor.codeActionsOnSave": {
    "source.fixAll.eslint": "explicit"
  },
  "eslint.codeActionsOnSave.rules": [
    "@master/css/sort-classes"
  ]
}
```

The first setting enables ESLint fixes on an explicit save. The rule list restricts that save action to class sorting; it does not enable save actions by itself. Keep `eslint.codeActionsOnSave.mode` at its default `all` so the rule filter applies. See the [ESLint extension's save settings](https://github.com/microsoft/vscode-eslint#settings-options).

See [Visual Studio Code setup](/guide/installation/vscode) for the full editor flow.

## Lint from scripts and AI tools
Keep `eslint .` in the project's development and CI scripts for JavaScript and framework projects. When a script needs machine-readable diagnostics without loading an ESLint parser, use the CLI. It is a separate dependency: [install it locally](/guide/installation/cli) with the same Master CSS release as the project, then run:

```bash name=Terminal
npx @master/css-cli lint --format json
```

With no source paths, the CLI follows the scanner's source policy: generated output and files excluded by project or workspace `.gitignore` rules are skipped. Pass a path or glob explicitly to lint an ignored build artifact.

The [Master CSS MCP server](/guide/mcp-server) exposes the same policy through `mastercss_lint_project` and can preview safe fixes.

Use `npx @master/css-cli inspect --format json` for scanner state, stylesheet entries, generated CSS size and missing-CSS checks. Use lint for class sorting, canonical classes, conflicts and raw-value policy.
