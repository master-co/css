## Overview [sr-only]
Give the application one place to load the styles every page needs. That entry can import several source files: keep shared values, document defaults and component rules with their owners, then assemble them through the same app stylesheet.

Complete the [framework installation](/guide/installation#integrations) first. The examples below extend its existing CSS entry; they do not require a second Master CSS installation.

## Start from one app entry \{#entry-stylesheet\}

Keep the default import at the beginning of the stylesheet your app already loads:

```css name=styles/app.css
@import '@master/css';
```

The import brings in the preset definitions and base styles, including the order `theme, base, defaults, components, utilities`. The integration uses this entry to deliver the project's generated CSS. Import it from the framework's app root, root layout or build entry as described in its installation guide.

A source file split does not need another full entry. Import your own files from `app.css`:

```css name=styles/app.css
@import '@master/css';
@import './theme.css';
@import './defaults.css';
@import './components.css';
```

<GlobalIllustration />

These files form one entry graph. A shared definition remains available whether you write it directly in `app.css` or in one of its imports. Avoid importing the full Master CSS entry again from every route stylesheet: that makes each file an entry and can repeat global native CSS.

## Set document defaults \{#base-layer\}

Keep the preset reset in `base`. Put your product's document defaults in `defaults`, where normal component and utility declarations can override them:

```css name=styles/defaults.css
@layer defaults {
  body {
    background-color: var(--color-surface-base);
    color: var(--color-text-body);
  }
}
```

Use native selectors for elements that should receive a default without an extra class. Keep the selector's reach intentional: a global `button` rule also reaches buttons inside every feature. Use a component class when the rule belongs to one product role.

The preset base styles already apply the font tokens to the document. To choose a typeface, change those tokens as described in [Typography](/guide/typography#site-typeface). See [Cascade layers](/guide/cascade-layers) when declarations compete; loading a rule later does not move it into a stronger layer.

## Decide what belongs in the shared graph \{#shared-vocabulary\}

| Shared decision | Where to define it | Where to continue |
| --- | --- | --- |
| A value whose consumers should change together | `@theme` in `theme.css` | [Theme tokens](/guide/theme) |
| A default every page needs | Native selectors in `@layer defaults` | The example above |
| A recurring product element | A native class in `@layer components` | [Reusing styles](/guide/reusing-styles#keep-a-components-shared-appearance-together) |
| A class capability generated when used | `@utility` in an imported stylesheet | The helper example below |
| Repeated CSS declarations or nested styles | `@mixin`, expanded with `@apply` | [CSS reuse](/guide/reusing-styles) |
| A named viewport or container condition | `@custom-media` or `@custom-container` | [Responsive design](/guide/responsive-design) |

For the imported `theme.css`, start with a value your project needs:

```css name=styles/theme.css
@theme {
  --spacing-card: 1.5rem;
}
```

The token registers `p-card`, `gap-card` and the other spacing families that accept the key. Its declaration is emitted when the project needs it; placing it in the entry graph does not make an ordinary token static.

Share a definition because its meaning is shared. Two features using the same number today can still need separate tokens; one element using several classes does not by itself need a component abstraction.

### Keep component ownership explicit \{#component-classes\}

A shared notification, for example, can live in `components.css`:

```css name=styles/components.css
@layer components {
  .notice {
    padding: var(--spacing-md);
    border: 1px solid var(--color-line-divider);
    border-radius: var(--radius-md);
    background-color: var(--color-surface-raised);
    color: var(--color-text-body);
  }
}
```

```html
<aside class="notice">Your changes are saved locally.</aside>
```

This native selector styles `.notice`; it does not register a utility named `notice`. Write shared states and conditions in the component rule. For a class recipe that accepts Master CSS modifiers, use `@utility` instead. [Reusing styles](/guide/reusing-styles) compares those choices with working examples.

Native CSS in the entry graph is emitted by default, including unused component rules. Native pruning is an explicit choice; see [Scanning and pruning](/guide/scanning-and-pruning). Do not move a large route-only stylesheet into the global graph simply to make its definitions visible.

## Add a shared helper \{#custom-utilities\}

A global definition can describe behavior needed in several features without generating a rule for every possible class. These helpers arrange related links, allow off-screen content to skip rendering work, and exclude the group from print:

<DemoConfiguredExample name="global-related-guides" title="Shared helpers, one group of links" source={`@utility flow {
  display: grid;
  gap: var(--spacing-md);
}

@utility content-auto {
  content-visibility: auto;
  contain-intrinsic-size: auto 32rem;
}

@utility print-hidden {
  @media print {
    display: none;
  }
}`} html={`<section class="content-auto flow print-hidden p-md b-solid b(1) b-line-divider r-md bg-surface-raised">
  <h2 class="m(0) text-lg font-regular">Related guides</h2>
  <a class="text-sm fg-text-body underline" href="/guide/theme" target="_top">Choose shared theme values</a>
  <a class="text-sm fg-text-body underline" href="/guide/responsive-design" target="_top">Adapt a layout to its available space</a>
</section>`} caption="flow supplies the grid and gap. print-hidden removes the group in print media. content-auto can skip off-screen rendering; its 32rem intrinsic size is a fallback estimate, not a fixed section height." />

Put these definitions after the existing Master CSS import, or import a `utilities.css` file from the app entry. The classes generate CSS when discovered in markup. In your app, open print preview to check `print-hidden`; remove the class when the links should appear in print too. Choose the [intrinsic-size estimate](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/contain-intrinsic-size) for the content in your own layout.

## Keep local delivery local \{#organize-global-files\}

Keep the app entry focused on styles shared across pages. The integration supplies project definitions to a route stylesheet without another full Master CSS import. Use `@reference` for additional definitions outside that graph; it does not deliver the referenced native CSS. The route's loader still owns delivery of its local rules.

Use [Route-level styles](/guide/route-level-styles) for that setup and [Monorepo](/guide/monorepo) when separate apps need separate entry graphs. After splitting a global file, check a page that consumes its definitions and one that does not: shared styles should still arrive through the app entry, and route-only rules should retain their local owner.
