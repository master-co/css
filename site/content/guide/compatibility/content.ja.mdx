Master CSS は CSS を生成し、適用できるプロパティ、値、セレクターはブラウザーが決めます。使える基盤を作り、それを改善する新しい機能を加え、既存のスタイルがカスケードでどう働くか確認してください。

以下の例は、[インストール](/guide/installation)を完了し、アプリが `@import '@master/css';` を読み込んでいることを前提とします。

## ブラウザーの基盤要件を確認する \{#overview\}

既定のプリセットは、カスケードレイヤー、OKLCH 色、適応する値のための `light-dark()` を使います。拡張機能にフォールバックを用意しても、これらの基盤要件はなくなりません。対象ブラウザーに対して、[ブラウザーの基盤要件とベンダープレフィックス](/reference/rules/declarations#vendor-prefixes)を確認してください。

クラスを認識できても、ブラウザー互換性の保証にはなりません。Master は一部のプロパティに互換プレフィックスを出力しますが、すべての新機能をポリフィルしません。同様に、ツールの `unknown` はその検査で CSS を未検証という意味であり、無効であるとも出荷可能であるとも証明しません。

## フォールバックを保って機能を追加する \{#new-css-features\}

### ネイティブの宣言 \{#native-declarations\}

自動サイズ調整が使えなくても、ノート欄は編集できる必要があります。通常の textarea のサイズと縦方向のサイズ変更を設定し、拡張として [`field-sizing: content`](https://drafts.csswg.org/css-forms/#field-sizing) を加えます。このネイティブプロパティは内容に合わせてコントロールの大きさを変え、最小・最大高さが実用的な範囲を保ちます。

`(field-sizing:content)` はネイティブの宣言を供給します。`@supports(field-sizing:content)` 接尾辞が、その宣言を [CSS 機能クエリー](https://www.w3.org/TR/css-conditional-3/#at-supports)内に置きます。一致しなければ、ベーススタイルと通常の textarea の動作が残ります。

<CompatibilityIllustration />

プレビューは現在のブラウザーの構文対応を確認します。対象ブラウザーで実際の編集動作もテストしてください。対応ブラウザーでフォールバックを調べるには、条件付きクラスを一時的に削除します。欄の自動伸長が止まり、スクロールですべてのテキストにアクセスできるはずです。これは拡張を切り離す操作で、古いブラウザーの再現ではありません。

**生成された CSS** で出力条件を確認します。クラスの構文は[条件](/reference/rules/conditions#supportsfeature)に記載しています。ネイティブ CSS ではさらに複雑な機能クエリーを表せます。

セレクターによる拡張にも同じ方法を使えます。ここでは [`:has(:checked)`](https://www.w3.org/TR/selectors-4/#relational) が、チェック時にラベルの境界線を青くします。未対応でも、ネイティブのチェックボックスは選択を記録します：

ベーススタイルを新しいセレクターから独立させます。不可欠なコントロールや内容を拡張に依存させないでください。セレクターの表記と組み合わせは[セレクター](/reference/rules/selectors)を参照します。

## サードパーティ CSS をカスケードに配置する \{#third-party-styles\}

通常のユーティリティでライブラリーの通常スタイルを上書きしたい場合、その CSS を先の `defaults` レイヤーにインポートします。Master インテグレーションが処理するアプリの CSS エントリーで、それらのインポートより前にレイヤー順序を宣言してください。

[Swiper のコア、ナビゲーション、ページネーションのスタイル](https://swiperjs.com/get-started)を使うプロジェクトでは、このエントリーから読み込み、別の場所でレイヤー外のコピーを追加でインポートしないでください：

```css name=app.css
@layer theme, base, defaults, components, utilities;
@import 'swiper/css' layer(defaults);
@import 'swiper/css/navigation' layer(defaults);
@import 'swiper/css/pagination' layer(defaults);
@import '@master/css';

@layer components {
  .swiper-slide {
    background-color: var(--color-surface-raised);
  }
}
```

スライダーの既存マークアップで、一方のスライドはコンポーネントの面を保ち、もう一方にローカルなユーティリティを加えられます：

```html
<div class="swiper-slide">Default surface</div>
<div class="swiper-slide bg-blue-60 fg-white">Featured slide</div>
```

`utilities` の通常の背景宣言は `components` より優先され、後者は `defaults` より上です。HTML のクラス名を並べ替えても結果は変わりません。

より強い上書きを加える前に、ブラウザーの開発者ツールで競合する宣言を確認します。同じ作成者オリジンとコンテキストでは、レイヤー外の通常スタイルが、レイヤー内の通常スタイルより優先されます。ベンダーの `!important` 宣言も通常のユーティリティに優先し、重要宣言ではレイヤー順序が逆になります。これは Master 固有の優先順位ではなく、[ネイティブのカスケード規則](https://www.w3.org/TR/css-cascade-5/#layer-order)です。[カスケードレイヤー](/guide/cascade-layers)で診断手順を説明しています。

Master 管理のスタイルシートでは、ネイティブセレクターは既定で保持されます。ネイティブの枝刈りを有効にする場合は、自分が管理するスタイルシートで [`@preserve native`](/reference/directives/pruning#preserve-native) を使い、ベンダー、CMS、外部から挿入するセレクターを保護するか、それらを枝刈り対象外にしてください。サードパーティのウィジェットが使うセレクターは、アプリの走査対象マークアップに現れない場合があります。
