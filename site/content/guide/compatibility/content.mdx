## Overview [sr-only]
Master CSS works alongside new CSS features, existing stylesheets and third-party CSS. Any valid declaration can be written as a class, and external styles keep their place in the cascade through the preset's layer order. Browser support follows the generated CSS; the [browser baseline and vendor prefixes](/reference/rules/declarations#vendor-prefixes) lists what the preset relies on and which compatibility declarations Master emits.

---

## New CSS features

### Native declarations
Write a property-like class when the declaration is already valid CSS:

```html
<!-- @MARK (field-sizing:content) --><!-- @MARK (interpolate-size:allow-keywords) --><!-- @MARK (view-transition-name:card) --><!-- @MARK (transition-behavior:allow-discrete) -->
<article class="(transition-behavior:allow-discrete) (field-sizing:content) (interpolate-size:allow-keywords) (view-transition-name:card)">…</article>
```

<Class2CSS>
  {['(field-sizing:content)', '(interpolate-size:allow-keywords)', '(view-transition-name:card)', '(transition-behavior:allow-discrete)']}
</Class2CSS>

Custom properties can use the same direct declaration form:

```html
<!-- @MARK (--card-gap:1rem) -->
<section class="(--card-gap:1rem)">…</section>
```

<Class2CSS>
  {['(--card-gap:1rem)']}
</Class2CSS>

Each class holds one declaration; repeat the selector or query suffix on each class that needs it. A token class such as `mt-md` still selects a theme value, while `(margin-top:1rem)` keeps the native value as written. Tooling may report the newest CSS grammar as `unknown` until its syntax data catches up; treat that as unverified rather than invalid. Runtime generation preserves direct native declarations without using `CSS.supports()` as an acceptance filter; the browser decides which declarations it can apply.

### New selectors
Selector suffixes can use native CSS selector syntax as long as the browser supports the selector.

```html
<!-- @MARK :has(:checked) -->
<form class="outline(2):has(:checked) outline-solid:has(:checked) outline-red:has(:checked)">…</form>
```

<Class2CSS>
  {['outline(2):has(:checked) outline-solid:has(:checked) outline-red:has(:checked)']}
</Class2CSS>

## Third-party styles
Put vendor styles in a lower cascade layer when you want normal Master CSS components and utilities to override normal vendor declarations. Declare the shared layer order before importing them into `defaults`, after the base reset and before components and utilities:

```css name=index.css
@layer theme, base, defaults, components, utilities;
@import 'swiper/css' layer(defaults);
@import 'swiper/css/navigation' layer(defaults);
@import 'swiper/css/pagination' layer(defaults);
@import '@master/css';
```

Unlayered vendor rules and `!important` vendor declarations still outrank normal layered utilities; moving them to `defaults` does not change that. Keep these imports in the project CSS entry processed by Master CSS, so they share its layer order and extraction context.

Then define your application overrides in the `components` layer or use utilities in markup:

```css name=index.css
@layer components {
  .swiper {
    max-width: var(--container-4xl);
  }

  .swiper-wrapper {
    background-color: var(--color-red-60);
  }

  .swiper-slide {
    background-color: var(--color-surface-raised);
  }
}
```

```html
<!-- @MARK bg-blue-60 -->
<div class="swiper-slide">Default surface</div>
<div class="swiper-slide bg-blue-60 fg-white">Featured slide</div>
```

The first slide keeps the component's surface color. The second uses a blue background and white text from its utilities. This keeps vendor defaults below product components and utilities, reducing the need for forceful overrides.

Native vendor, CMS and externally injected selectors in a Master-managed stylesheet are preserved by default. If you enable native pruning, keep those selectors outside pruned sources or protect the file with [`@preserve native`](/reference/directives/pruning#preserve-native). [Cascade layers](/guide/cascade-layers) covers the complete layer order.
