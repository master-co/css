Master CSS generates CSS; the browser decides which properties, values and selectors it can apply. Build a usable baseline, add newer features where they improve it, and check how existing styles participate in the cascade.

These examples assume [Installation](/guide/installation) is complete and your app loads `@import '@master/css';`.

## Check the browser baseline \{#overview\}

The default preset uses cascade layers, OKLCH colors and `light-dark()` for adaptive values. An enhancement fallback does not remove those baseline requirements. Check the [browser baseline and vendor prefixes](/reference/rules/declarations#vendor-prefixes) against the browsers you need to support.

A recognized class is not a browser-compatibility guarantee. Master emits compatibility prefixes for selected properties; it does not polyfill every new feature. Likewise, a tooling result of `unknown` means the CSS has not been verified by that check, rather than proving it invalid or safe to ship.

## Add a feature without losing the fallback \{#new-css-features\}

### Native declarations

A note field should remain editable even when automatic sizing is unavailable. Give it an ordinary textarea size and allow vertical resizing, then add [`field-sizing: content`](https://drafts.csswg.org/css-forms/#field-sizing) as an enhancement. The native property can size the control from its contents; minimum and maximum heights keep it within a useful range.

`(field-sizing:content)` supplies the native declaration. Its `@supports(field-sizing:content)` suffix places that declaration inside a [CSS feature query](https://www.w3.org/TR/css-conditional-3/#at-supports). If the query does not match, the base styles and normal textarea behavior remain.

The preview checks syntax support in your current browser. Test the actual editing behavior in your target browsers too. To inspect the fallback in a supporting browser, temporarily remove the conditional class: the field should stop growing automatically while keeping all its text accessible by scrolling. This isolates the enhancement; it does not emulate an older browser.

Use **Generated CSS** to inspect the emitted condition. [Conditions](/reference/rules/conditions#supportsfeature) documents the class syntax; native CSS can express more complex feature queries.

### New selectors

The same approach applies to selector-based enhancements. Here, [`:has(:checked)`](https://www.w3.org/TR/selectors-4/#relational) gives the label a blue border when its checkbox is checked. The native checkbox still records the choice if that selector is unsupported:

A supporting browser also changes the label border; the checkmark is the primary indication of the choice." html={`<label class="flex items-center gap-sm w-fit mx-auto p-sm r-md b(1) b-solid b-line-divider bg-surface-raised text-sm fg-text-strong b-blue-60:has(:checked)">
  <input type="checkbox" name="updates" class="m(0) shrink(0) (accent-color:currentColor)">
  <span>Send me release notes</span>
</label>`} />

Keep the base styling independent of the new selector. Do not make essential controls or content depend on the enhancement. For selector spelling and composition, see [Selectors](/reference/rules/selectors).

## Fit third-party CSS into the cascade \{#third-party-styles\}

When normal utilities should override a library's normal styles, import its CSS into the earlier `defaults` layer. Declare the layer order before those imports, in the app CSS entry processed by your Master integration.

For a project that already uses [Swiper's core, navigation and pagination styles](https://swiperjs.com/get-started), load them through this entry instead of also importing unlayered copies elsewhere:

```css name=app.css
@layer theme, base, defaults, components, utilities;
@import 'swiper/css' layer(defaults);
@import 'swiper/css/navigation' layer(defaults);
@import 'swiper/css/pagination' layer(defaults);
@import '@master/css';

@layer components {
  .swiper-slide {
    background-color: var(--color-surface-raised);
  }
}
```

Within the slider's existing markup, one slide can keep the component surface while another adds a local utility:

```html
<div class="swiper-slide">Default surface</div>
<div class="swiper-slide bg-blue-60 fg-white">Featured slide</div>
```

The normal background declaration in `utilities` wins over the one in `components`, which in turn sits above `defaults`. Reordering the class names in HTML does not change that result.

Check competing declarations in browser devtools before adding stronger overrides. Within the same author origin and context, normal unlayered styles outrank normal layered styles. A vendor `!important` declaration also beats a normal utility; important declarations reverse the layer order. These are [native cascade rules](https://www.w3.org/TR/css-cascade-5/#layer-order), not a Master-specific priority system. [Cascade layers](/guide/cascade-layers) walks through diagnosis.

Native selectors in Master-managed stylesheets are preserved by default. If you enable native pruning, protect vendor, CMS and externally injected selectors with [`@preserve native`](/reference/directives/pruning#preserve-native) in a stylesheet you control, or keep those sources outside pruning. A selector used by a third-party widget may not appear in your app's scanned markup.
