Migrating a product to Master CSS is a styling change, not a one-to-one syntax rewrite: add Master CSS beside the existing system, convert one reviewable slice at a time, and remove old dependencies only after the migrated UI is validated.

## Migration strategy
Start with an audit, then migrate incrementally. The first milestone is a working vertical slice: one component or route generates the intended CSS, preserves its interactions and still matches the design, while the rest of the application keeps its legacy styles.

### Plan an external-system conversion with MCP

With the [Master CSS MCP server](/guide/ai-coding#connect-the-mcp-server) connected, the `migrate-to-mastercss` prompt asks the agent to inspect the active manifest, stylesheet entries, extraction coverage and existing vocabulary first, then return a rendering mode, a first reviewable batch, validation commands and visual risks. It is a planning workflow and does not edit files.

```text
Use the Master CSS MCP prompt migrate-to-mastercss for this workspace.

Inspect the external styling system, framework, CSS entries, tokens, source discovery and available checks. Do not edit yet.

Return an incremental plan with the rendering mode, first conversion batch, CSS output risks, validation commands and visual checks.
```

### Without MCP \{#migration-prompt\}

Paste this into your local coding agent from the project root:

```text
You are migrating this project to Master CSS.

Use the official Master CSS documentation as the source of truth:
Documentation: https://rc.css.master.co

Do not invent Master CSS classes, APIs, directives, or package names.

First inspect the repository and identify:
- the framework, build tool, package manager, and current styling systems
- the app CSS entry point and component/template files that contain styles
- any design tokens, theme variables, CSS modules, utility classes, styled components, preprocessors, or third-party stylesheets
- the available formatter, lint, type-check, test, and build commands

Then migrate incrementally:
1. Choose the rendering mode, then install and configure the appropriate Master CSS integration.
2. Import `@master/css` from the project CSS entry.
3. Check cascade layers, resets and overlapping class names while the old and new CSS coexist. Keep each compiler responsible for its own source directives.
4. Convert repeated visual styles into Master CSS classes in markup where that improves clarity.
5. Move shared design values into `@theme` tokens.
6. Use native CSS in `@layer components` for reusable component classes when markup classes would become hard to maintain.
7. Keep vendor CSS, generated CSS, complex animation CSS, and hard-to-read one-off CSS in regular CSS unless converting it improves maintainability.
8. Remove the old styling dependency only after the migrated screens build and match the previous UI.

Work in small migration batches. After each focused batch, show me the changed files, explain the conversion decisions, and run the project’s formatter, type check, tests, and build if available. Call out anything that needs manual review, especially visual differences, removed CSS, changed tokens, old styling dependencies, or unsupported syntax.
```

## Checklist
- Start from a clean git working tree and identify every existing styling system, including component-library CSS.
- Choose a [rendering mode](/guide/rendering-modes) and add `@import '@master/css';` to the CSS entry your app already loads.
- Review each batch's diff and run the project's formatter, type check, tests and production build.
- Compare important screens in the browser, including responsive states and dark mode if the app supports them.
- Keep the old styling system, and regular CSS for vendor or generated styles, until the converted paths no longer rely on it.
