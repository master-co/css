Tailwind CSS v4 and Master CSS both generate CSS from class names and CSS directives, but they are not drop-in replacements for each other. Treat the migration as a change of styling implementation: install Master CSS beside Tailwind, convert one route or component family at a time, and remove Tailwind only after the migrated surfaces build and visually match the intended design.

This guide focuses on Tailwind CSS v4's CSS-first workflow: `@import "tailwindcss"`, `@theme`, `@utility`, `@variant`, `@custom-variant`, `@source`, and `@apply`. For Tailwind behavior, use the official references for [functions and directives](https://tailwindcss.com/docs/functions-and-directives), [theme variables](https://tailwindcss.com/docs/theme), [detecting classes in source files](https://tailwindcss.com/docs/detecting-classes-in-source-files), and [states and variants](https://tailwindcss.com/docs/hover-focus-and-other-states).

---

## Migration strategy \{#migration-strategy\}
For agent-assisted work, use the official `master-css` skill with one static HTML
or JSX component, its stylesheet entry and the original Tailwind version. Ask
the agent to preserve appearance and interactions, and to report retained CSS
and remaining Tailwind dependencies. The skill provides a reviewed workflow,
not an automatic project-wide converter.

Build the source with its installed Tailwind toolchain before translating class
names. Compiled CSS supplies the actual values, variants and variable dependencies.
For a snippet without its theme or plugin configuration, establish that context
before claiming a faithful conversion. Use `mastercss_suggest_classes` only for
isolated declaration blocks; keep complex selectors and unresolved dynamic
expressions in native CSS. Inspect `tailwind-merge` or other Tailwind-specific
class processing before passing Master classes through it.

Compare both versions with the same reset, fonts, theme and browser state.
Tailwind v4's `hover:` also requires the `(hover: hover)` media condition; copying
only the pseudo-class changes its behavior. `mastercss_css_compare` compares
Master outputs; use the browser to compare the original component with its
converted result.

Use the [shared migration workflow](/guide/migration#migration-strategy) for coexistence, baseline captures and removal checks. During the first batch, inventory these Tailwind-specific contracts:

<DocumentComparison>

| Contract | What to preserve or replace |
| --- | --- |
| Compiler input | Keep Tailwind directives with Tailwind’s compiler; import ordinary generated CSS into the Master entry. |
| Theme and variants | Resolve actual token values and conditions before choosing Master classes. |
| Preflight, plugins and global CSS | Retain the rules that untouched screens still need. |
| Class processing | Replace Tailwind-specific merging and fragment assembly with deliberate class maps. |
| Component internals | Keep vendor CSS and complex selectors until the component itself is migrated. |

</DocumentComparison>

Avoid global search-and-replace. The two systems have different resets, scales, ring models and directive contracts. Even an identical keyword can mean a different operation.

## Install Master CSS beside Tailwind \{#install-master-css-beside-tailwind\}
Keep Tailwind’s compiler responsible for its own entry. Compile that entry to ordinary CSS, then load the result beside the Master CSS entry. Both systems use directive names such as `@theme`, `@utility` and `@apply` with different contracts; do not pass unprocessed Tailwind definitions through the Master CSS compiler.

```css name=app.css
@import "./legacy-tailwind.generated.css";
@import "@master/css";
```

Keep the existing Tailwind build producing `legacy-tailwind.generated.css` before this entry is compiled. Both systems can define the same class name; compare cascade layers, resets and overlapping names during coexistence.

For most integrations, no Master CSS source directive is needed here. The integration or CLI scanner discovers ordinary app files; add `@source` only for migrated markup outside that default scope.

Then follow [Installation](/guide/installation) for the project’s framework or build tool. React uses its bundler’s guide; Laravel and Blazor use the host-specific sections in [Server-rendered apps](/guide/installation/server-rendered).

Do not remove Tailwind at this point. The first milestone is a project that still looks the same while Master CSS can generate rules for new or converted markup.

## Choose a rendering mode \{#choose-a-rendering-mode\}
Start with [static rendering](/guide/rendering-modes): most Tailwind projects already keep complete class strings in source. Toggling those classes and updating per-element CSS variables work without a browser runtime.

Use runtime or progressive rendering only when the app genuinely creates new class names after the build. Before choosing a mode, replace fragment assembly with complete class maps and inspect the source boundaries that the existing build relies on.

## Translate CSS-first theme values \{#translate-css-first-theme-values\}
Tailwind v4 `@theme` variables create utility classes and variants. Master CSS `@theme` variables define design tokens for Master CSS namespaces. The shape is similar, but the generated class syntax is different.

```css name=tailwind.css
@import "tailwindcss";

@theme {
  --color-brand: oklch(0.62 0.2 265);
  --spacing-card: 1.5rem;
  --radius-card: 1rem;
  --breakpoint-dashboard: 72rem;
}
```

```css name=app.css
@import "@master/css";

@theme {
  --color-brand: oklch(0.62 0.2 265);
  --spacing-card: 1.5rem;
  --radius-card: 1rem;
}

@custom-media --dashboard (width >= 72rem);
```

```html
<article class="grid r-card grid-cols(3)@dashboard bg-brand p-card">
  ...
</article>
```

Master CSS resolves token names by namespace. A token like `--color-brand` becomes available to color utilities such as `bg-brand`, `fg-brand`, and border color utilities. A token like `--spacing-card` becomes available to spacing utilities such as `p-card`, `gap-card`, and `m-card`.

| Tailwind v4 theme concept | Master CSS equivalent | Notes |
| --- | --- | --- |
| `--color-*` | `--color-*` | Use color tokens with `bg-*`, `fg-*`, border and outline color utilities. `text-*` is a typography recipe, not a color alias. |
| `--spacing-*` or base spacing | `--spacing-*` | Use named spacing tokens for product decisions and explicit native units for direct values. |
| `--radius-*` | `--radius-*` | Use with named radius utilities such as `r-card`, or write a full `border-radius` declaration class. |
| `--shadow-*` | `--shadow-*` | Use with named shadow utilities such as `shadow-card`, or write a full `box-shadow` declaration class. |
| `--font-*`, `--text-*`, `--leading-*`, `--tracking-*` | Font, text, leading, and tracking namespaces | Prefer `text-*` when the complete type treatment should be shared. |
| `--breakpoint-*` | `@custom-media --md (width >= 48rem);` | Defines viewport suffixes such as `@md`; custom properties do not register conditions. |

`@theme inline` substitutes token values once in generated declarations; `@theme static` retains tokens and their dependencies without a consumer. Both modifiers can be combined. Only custom-property declarations belong inside a theme block. Put keyframes in native CSS and use `@prune native;` in their owning file for usage-based output.

Put explicit `.light` and `.dark` selectors outside `@theme` for a manual theme switch. Define selector mixins separately when markup uses `@apply(--manual-light)` or `@apply(--manual-dark)` suffixes.

```css name=app.css
@import "@master/css";

@mixin --manual-light { &:where(.light, .light *) { @contents; } }
@mixin --manual-dark { &:where(.dark, .dark *) { @contents; } }

@theme {
  --color-panel:#fff;
  --color-text-body:#111827;
}

.light {
  --color-panel: #fff;
  --color-text-body: #111827;
}

.dark {
  --color-panel: #111827;
  --color-text-body: #f9fafb;
}

```

```html
<section class="fg-text-body bg-panel">
  ...
</section>
```

Tailwind's default theme and Master CSS's default theme are not the same. Convert custom product tokens first, then review default palette and scale replacements intentionally.

## Translate utilities \{#translate-utilities\}
Start with explicit Master CSS declarations, then shorten them where the local vocabulary is obvious.

| Tailwind v4 pattern | Master CSS pattern | Notes |
| --- | --- | --- |
| `p-6`, `px-4`, `mt-8` | `(padding:1.5rem)`, `(padding-inline:1rem)`, `(margin-top:2rem)` | These values assume Tailwind’s default .25rem scale; check the original project configuration. Use a defined token such as `p-card` for product spacing. |
| `-mt-4` | `(margin-top:-1rem)` | Use a negative raw value, or `-mt-card` for a defined numeric token. |
| `w-full`, `h-screen`, `min-w-0` | `w-full`, `(height:100vh)`, `min-w(0)` | Pixel and zero values use direct-value functions; other units stay native. |
| `rounded-lg` | `r-lg` | Both defaults are .5rem; confirm any project overrides before reusing the name. |
| `bg-blue-600`, `text-white` | `bg-blue-60`, `fg-white` | Master CSS preset color steps differ from Tailwind's default palette. |
| `bg-zinc-50`, `text-zinc-500` | `bg-zinc-5`, `fg-zinc-60` | The scales differ. This darker text step keeps the fixed light surface readable; compare actual values instead of dividing Tailwind steps by ten. |
| `text-lg`, `font-semibold`, `leading-7` | `font-lg`, `font-semibold`, `(line-height:1.75rem)` | Use `text-*` only when the full type treatment is intended. |
| `flex`, `items-center`, `justify-between` | `flex`, `items-center`, `justify-between` | These fixed utilities have the same names and declarations. Check the [fixed utility catalog](/reference/rules/declarations#fixed-utilities) before falling back to `(property:value)`. |
| `grid-cols-3`, `gap-4` | `grid-cols(3)`, `(gap:1rem)` | Use the explicit grid recipe and the native `gap` property. |
| Arbitrary value such as `w-[min(100%,72rem)]` | `(width:min(100%,72rem))` | Write native CSS function values directly. |
| Arbitrary property such as `[scroll-margin-top:4rem]` | `(scroll-margin-top:4rem)` | Master CSS writes every native declaration in parentheses. |
| Important modifier such as `mt-0!` | `mt(0)!` | The important marker goes at the end of the class in current Tailwind v4 and Master CSS. |

A Master CSS layout using preset values (not a pixel-equivalent conversion of an unspecified Tailwind layout):

```html
<section class="grid gap-lg w-full max-w-5xl mx-auto px-md py-2xl grid-cols(3)@md">
  <article class="p-lg r-lg bg-surface-base shadow-sm">
    <h2 class="m(0) font-2xl font-regular fg-text-neutral">Account</h2>
    <p class="mt-xs fg-text-muted">Review profile settings.</p>
  </article>
</section>
```

When a Tailwind class does not have a short Master CSS alias, use the CSS property directly:

{ }
```html
<div class="(scroll-margin-top:4rem) (text-wrap:balance)">
  ...
</div>
```
{ }

## Translate variants and states \{#translate-variants-and-states\}
Tailwind writes variants before the utility. Master CSS appends selectors and conditions after the declaration.

| Tailwind v4 pattern | Master CSS pattern | Notes |
| --- | --- | --- |
| `hover:bg-blue-700` | `bg-blue-70:hover@media(hover:hover)` | Keep Tailwind v4’s hover-capability condition. The color is a new preset choice; copy the original token for exact color fidelity. |
| `focus-visible:outline-2` | `outline(2):focus-visible` | This maps the width. Retain an outline style and color; width alone does not establish the same focus treatment. |
| `disabled:opacity-50` | `(opacity:.5):disabled` | Attribute and pseudo-class selectors are supported. |
| `md:grid-cols-3` | `grid-cols(3)@tailwind-md` | Preserve the original threshold with an explicit condition; the two presets use different `md` values. |
| `dark:bg-slate-950` | `bg-slate-95@apply(--manual-dark)` | Output follows the explicit `--manual-dark` selector mixin. |
| `motion-safe:animate-spin` | `animate-rotate@motion-safe` | The preset rotation is 1s, linear and infinite; `@motion-safe` respects reduced motion. |
| `supports-[display:grid]:grid` | `grid@supports(display:grid)` | Use raw `@supports()` for local conditions. |
| `data-[state=open]:...` | `bg-blue-5[data-state=open]` | Native attribute selectors are appended directly. |
| `has-[:checked]:...` | `bg-blue-5:has(:checked)` | Native `:has()` is supported. |

```html
<button type="button" class="inline-flex items-center (min-height:2.5rem) px-md r-md bg-blue-60 fg-white bg-blue-70:hover@media(hover:hover) (opacity:.5):disabled">
  Save
</button>
```

Tailwind’s default `md` starts at 48rem; Master CSS’s preset `md` starts at 64rem. The responsive row above keeps the Tailwind threshold through a named condition:

```css name=app.css
@custom-media --tailwind-md (width >= 48rem);
```

Preserve Tailwind's `max-md:` threshold with `@custom-media --max-tailwind-md not (--tailwind-md);` and the `@max-tailwind-md` suffix. Master’s preset `@max-md` instead complements its own 64rem threshold. Use `@custom-media` for reusable media queries and a mixin with `@contents` for other wrappers. Keep selector states as selector suffixes or nested selectors.

```css name=app.css
@import "@master/css";

@custom-media --compact (width < 48rem);

```

{ }
```html
<button type="button" class="bg-blue-70:hover@media(hover:hover) fg-white:hover@media(hover:hover) px-sm@compact">
  Save
</button>
```
{ }

For Tailwind `group-*` and `peer-*` patterns, prefer native selectors when possible. Master CSS can target descendants, children, siblings, attributes, and `:has()`, but it does not implement Tailwind's group and peer variant naming.

```html
<article class="bg-blue-5:hover_h2@media(hover:hover) fg-blue-60:hover_h2@media(hover:hover)">
  <h2 class="fg-text-neutral">Project</h2>
</article>
```

## Replace utility composition with native CSS \{#replace-utility-composition-with-native-css\}
Rewrite Tailwind utility composition as native declarations and selectors, preserving token references and states. Use Master utilities directly in markup. Master CSS `@apply` expands one named `@mixin`; it does not accept utility class lists. `@compose` is unsupported.

```css name=tailwind.css
.btn {
  @apply inline-flex items-center gap-2 rounded-md bg-blue-600 px-4 py-2 text-white shadow-sm;
}
```

```css name=app.css
@import "@master/css";

.btn {
  display: inline-flex;
  border-radius: var(--radius-md);
  gap: var(--spacing-xs);
  padding-block: var(--spacing-xs);
  padding-inline: var(--spacing-md);
  background-color: var(--color-blue-60);
  box-shadow: var(--shadow-sm);
  color: oklch(100% 0 none);
  align-items: center;
}
```

The example adopts Master’s preset palette and shadow; it is not an exact visual match to Tailwind’s defaults. For a faithful conversion, retain the original resolved colors and shadow values until the project explicitly changes its design.

When the declaration group needs reuse inside CSS, give it a mixin name. This is the Master CSS meaning of `@apply`:

```css name=app.css
@mixin --control {
  padding-inline: 1rem;
  padding-block: .5rem;
}

.btn {
  @apply --control;
}
```

For component-specific styles, native declarations can express the entire rule:

```css name=app.css
.form-panel {
  border-radius: var(--radius-lg);
  padding: var(--spacing-lg);
  background-color: oklch(100% 0 none);
  box-shadow: var(--shadow-sm);
  border: 1px solid color-mix(in oklab, currentColor 12%, transparent);
}
```

CSS Modules and framework style blocks automatically receive project tokens, mixins, and custom media in the Vite, Next.js, and Webpack integrations. Use `@reference` only for additional definition files or standalone compilation.

```css name=Button.module.css
.button {
  display: inline-flex;
  border-radius: var(--radius-md);
  padding-inline: var(--spacing-md);
  background-color: var(--color-blue-60);
  color: oklch(100% 0 none);
  align-items: center;
  height: 2.5rem;
}
```

Keep quoted strings, complex content values, and unusual selectors as ordinary CSS declarations or nested CSS.

## Migrate custom utilities and components \{#migrate-custom-utilities-and-components\}
Tailwind `@utility` creates custom utilities that work with variants. In Master CSS, use `@utility` for class recipes, `@mixin` to reuse CSS declarations, and `@layer components` for product roles.

```css name=tailwind.css
@utility content-auto {
  content-visibility: auto;
  contain-intrinsic-size: auto 32rem;
}
```

```css name=app.css
@import "@master/css";

@utility content-auto {
  content-visibility: auto;
  contain-intrinsic-size: auto 32rem;
}
```

```html
<section class="content-auto">
  ...
</section>
```

Use `@layer components` when the name describes a product UI role rather than a low-level primitive.

```css name=app.css
@layer components {
  .btn {
    display: inline-flex;
    border-radius: var(--radius-md);
    gap: var(--spacing-xs);
    padding-block: var(--spacing-xs);
    padding-inline: var(--spacing-md);
    font-size: var(--font-size-sm);
    font-weight: var(--font-weight-medium);
    align-items: center;
    justify-content: center;
    background-color: var(--color-blue-60);
    color: oklch(100% 0 none);

    &:disabled {
      opacity: .5;
      pointer-events: none;
    }

    @media (--md) {
      padding-inline: var(--spacing-lg);
    }
  }
}
```

```html
<button class="btn">
  Submit
</button>
```

Keep complex third-party overrides as native CSS when utility composition would make the rule harder to read.

## Handle dynamic classes \{#handle-dynamic-classes\}
Tailwind and Master CSS static rendering both depend on class names that can be found before the page runs. Complete strings are the safest migration target.

(x) Avoid fragment assembly.

```ts
const className = '(background:' + tone + ')'
```

(o) Use complete class maps.

```ts
const toneClasses = {
  neutral: 'bg-surface-base fg-text-neutral',
  success: 'bg-green-80 fg-white',
  danger: 'bg-red-70 fg-white'
}
```

When only the value is dynamic, keep the class static and pass the runtime value through a CSS variable.

```tsx
function Progress({ value }: { value: number }) {
  const percent = Number.isFinite(value) ? Math.max(0, Math.min(100, value)) : 0
  return (
    <div role="progressbar" aria-label="Progress" aria-valuemin={0} aria-valuemax={100} aria-valuenow={percent}
      className="overflow-hidden (height:1rem) pill bg-surface-inset">
      <div
        className="h-full (width:var(--progress)) bg-text-muted (transition-property:width) (transition-duration:var(--duration-fast))@motion-safe (transition-timing-function:var(--easing-smooth))"
        style={{ '--progress': `${percent}%` } as React.CSSProperties}
      />
    </div>
  )
}
```

Most Tailwind `@source` boundaries can be deleted when switching to Master CSS. Keep or add Master CSS `@source` only for source the integration or CLI would not otherwise scan, such as shared workspace packages or external content.

```css name=app.css
@import "@master/css";

@source "../content/**/*.mdx";
@source "../packages/ui/**/*.{ts,tsx}";
@source not "../packages/ui/**/*.stories.tsx";
```

Use `@safelist` for bounded classes that do not exist in scanned source, and `@blocklist` for false positives.

```css name=app.css
@import "@master/css";

@safelist "bg-blue-60 bg-red-60@dark";
@blocklist "debug-*";
```

Tailwind `@source inline()` can generate classes from inline strings and brace expansion. Master CSS `@safelist` is explicit: list the classes the project needs.

## Validate the migration \{#validate-the-migration\}
Review each batch as code and UI.

- Run the project's formatter, linter, type check, tests, and production build.
- Use [Code linting](/guide/code-linting) to validate Master CSS class strings and catch conflicts.
- Compare migrated pages against the previous Tailwind version in light mode, dark mode, responsive breakpoints, hover/focus states, and print if relevant.
- Check routes that depended on Tailwind Preflight, default theme values, ring utilities, `container`, official plugins, or group/peer variants.
- Keep Tailwind loaded until converted pages no longer rely on Tailwind classes or plugin output.

After a batch passes checks, remove only the Tailwind utilities that are no longer used. A gradual migration can keep Tailwind and Master CSS side by side for as long as the product needs.

---

## Remove Tailwind \{#remove-tailwind\}
Remove Tailwind only after the converted paths build and visually match the intended design.

1. Remove the generated Tailwind CSS import from the app entry, then retire its separate Tailwind build input.
2. Remove Tailwind-specific `@theme`, `@utility`, `@custom-variant`, `@variant`, `@apply`, `@source inline()`, and `@plugin` usage that has been replaced.
3. Remove Tailwind packages and PostCSS or Vite integration code when no stylesheet imports Tailwind.
4. Run the full project validation suite.
5. Re-check important pages in the browser.

If a third-party plugin or vendor stylesheet still supplies useful CSS, keep it as regular CSS until there is a product-specific replacement.

## Tailwind CSS capabilities without a direct Master CSS equivalent \{#tailwind-css-capabilities-without-a-direct-master-css-equivalent\}
| Tailwind capability | Master CSS status | Migration path |
| --- | --- | --- |
| Tailwind class syntax and drop-in compatibility | Master CSS does not read Tailwind class syntax. | Rewrite classes to Master CSS syntax or keep Tailwind loaded until each area is migrated. |
| Tailwind CSS plugin loading through `@plugin` | Master CSS does not execute Tailwind plugins. | Recreate needed output with native CSS, `@theme`, `@mixin`, or `@layer components`; keep plugin CSS temporarily when needed. |
| Tailwind CSS-first theme resolver behavior | Master CSS has its own token namespaces and utility matching. | Move shared values into Master CSS `@theme` directives and review generated class names. |
| Tailwind `prefix(...)` | Master CSS has no class-prefix mode. | Use Master CSS syntax directly; use native selectors to scope styles to an app root. |
| Tailwind `@source inline()` brace-expansion safelisting | Master CSS does not provide an equivalent brace-expansion directive. | Use explicit `@safelist` entries and complete class strings. |
| Exact Tailwind Preflight | Master CSS base styles are not Tailwind Preflight. | Compare UI and add native CSS where the project relies on Tailwind reset details. |
| Official plugin outputs such as typography or forms | Master CSS does not automatically recreate Tailwind plugin CSS. | Keep plugin CSS temporarily or author product-specific components and utilities. |
| Tailwind `container` utility semantics | Master CSS uses native `container-type` declarations for a query boundary. | Use `w-full (max-width:72rem) mx-auto (padding-inline:1rem)` for page wrappers and `container-inline` for an ancestor query container. |
| Tailwind ring utility model | Master CSS does not provide the same ring utility family. | Use `(outline:*)`, `(outline-offset:*)`, `(box-shadow:*)`, or custom utilities. |
| Tailwind group and peer variant syntax | Master CSS does not implement `group-*` or `peer-*` variants. | Use native selectors, `:has()`, and combinators. |
