## Overview [sr-only] \{#overview\}
Make each page receive the CSS it needs, including the states that appear after interaction. Start by tracing delivery, move feature styles to their owners, and prune native rules only where the build knows their possible uses. Prerender pages whose classes are all in their HTML. Compare the resulting assets and behavior before setting a regression budget.

This guide follows an overview page and a reports page with the same navigation. Only Reports renders a report panel. The desired result is that Overview never downloads the panel's rules, while Reports keeps its ready and keyboard-focus states.

Complete your framework's [installation](/guide/installation) first. [Route-level styles](/guide/route-level-styles) explains local style ownership and definitions; [Scanning class names](/guide/scanning-and-pruning) explains discoverable class strings and source exceptions. Use those Authoring guides for everyday component work; use this workflow when investigating delivery cost or missing assets.

Record the installed Master CSS version, CSS entry, rendering mode and pruning policy. Keep the existing mode during a delivery refactor. The reproducible example below uses Vite with progressive rendering to show that initial CSS, later utilities and native pruning are separate concerns. It uses only public packages and preset tokens.

## Establish what each page receives \{#baseline\}

Build the current source and keep the output with its lockfile and tool versions. Choose both a page that uses the feature and a page that does not. Include direct loads and navigation between them; a shared asset already in the cache can change the cost of the second page.

Trace each HTML stylesheet link through its CSS imports, counting each resolved asset once per page. Record inline style blocks separately. Inspect module imports as well: a component imported through a shared registry can load CSS even when its markup is absent. Record runtime scripts, programs and hydration data separately from stylesheets.

Use three different kinds of evidence:

| Evidence | What to record | What it establishes |
| --- | --- | --- |
| Build output | Unique external files, import depth, raw and gzip/Brotli bytes, inline CSS | Which assets the build delivers and their deterministic size under the recorded compression settings |
| Browser requests | Responses, encoding, transferred bytes, cache reuse and initiators | What this navigation actually fetched |
| Browser behavior | Paint and interaction timing, computed styles and relevant states | Whether the page works, and how it performs under the tested conditions |

The [Network panel](https://developer.chrome.com/docs/devtools/network/reference) exposes requests and their dependencies. Measure a cold load and a warm navigation separately, using the same browser, viewport, content and throttling settings before and after. Repeat timing runs and keep the samples as well as a median. Compressed file size alone does not establish a faster paint.

[Coverage](https://developer.chrome.com/docs/devtools/coverage) can suggest a feature to investigate. A rule unused during one recording may still serve a closed dialog, focus state, another viewport or externally supplied content. Establish ownership and possible states before removing it.

## Give feature rules a local owner \{#ownership\}

Suppose the common JavaScript entry imports both navigation and report styles:

```js name=src/main.js
import './style.css'
import './reports.css'
```

Both pages now receive the report rules. Their absence from Overview's DOM does not change the import. Move that second import to the reports entry, which only Reports loads. Keep the shared navigation in the common stylesheet.

The common entry imports the one full Master CSS entry. Its navigation rule uses a public spacing token:

```js name=src/main.js
import './style.css'
```

```css name=src/style.css
@import '@master/css';

@layer components {
  .site-nav { display: flex; gap: var(--spacing-md); }
}
```

The reports module imports its own stylesheet. Complete class strings describe the finite status alternatives; the attribute selector and focus rule stay with the panel too:

```js name=src/reports.js
import './reports.css'

const states = { idle: 'report-idle', ready: 'report-ready' }
const report = document.querySelector('#report')
document.querySelector('#refresh').addEventListener('click', () => {
  report.classList.replace(states.idle, states.ready)
  report.dataset.state = 'ready'
  report.textContent = 'Report ready'
})
```

```css name=src/reports.css
@prune native;

@layer components {
  .report { padding: var(--spacing-lg); border: 1px solid currentColor; }
  .report[data-state="ready"] { border-width: 3px; }
  .report:focus-visible { outline: 2px solid currentColor; outline-offset: 4px; }
  .report-idle { opacity: .65; }
  .report-ready { opacity: 1; }
  .report-debug { outline: 8px solid red; }
}
```

</DocumentDisclosure>

Open `/` and `/reports/` directly. Trace their emitted CSS imports: only Reports should receive `.report`. Refresh the report, then focus its panel using the keyboard. Its border becomes 3px, opacity becomes 1, and keyboard focus has an outline.

The `@prune native` marker opts this file in, but removal also requires a build path that supplies class usage. In the current Vite local-stylesheet transform, the report rules are compiled with project definitions without a usage set for pruning; `.report-debug` therefore remains in that local output. The ownership improvement still works. The next section verifies pruning separately through the public CLI rather than treating a directive in source as proof of a smaller production file.

### Share definitions without importing the feature \{#share-definitions-without-importing-the-feature\}

A local stylesheet can use project tokens and mixins without importing the full entry again. The integration supplies that definition context. When definitions live outside the entry graph, use [`@reference`](/guide/route-level-styles#reference-definitions-without-loading-their-native-rules); it supplies definitions without loading the referenced file's native rules.

Native selectors keep their ordinary document scope after loading. Route ownership controls delivery, not selector matching or whether the framework retains CSS after navigation. Keep shared values in tokens, shared roles in native classes, repeated declarations in mixins, and independent local choices in utilities. [Reusing styles](/guide/reusing-styles) covers those design decisions.

## Prune only a known usage set \{#native-pruning\}

Native CSS is preserved by default. First remove unnecessary imports. Then consider files whose classes and states you can account for. Keep project-wide `pruneNativeCSS` off while establishing these boundaries, and opt individual sources in with `@prune native;`.

Pruning applies to the declaring file and uses its root's class usage scope. It does not automatically spread into imported files. Package CSS needs its own opt-in; a consumer's project-wide setting does not make all package styles prunable. Only consider `pruneNativeCSS: true` when pruning all project-owned stylesheets is intentional and their possible uses are covered. The [pruning Reference](/reference/directives/pruning#import-graph) owns the full scope rules.

In this example, the markup contains `report` and `report-idle`, and the JavaScript map also contains `report-ready`. Those complete names allow a scanner-backed build to retain both status rules. Finding `report` retains its attribute and focus selector branches even before the ready or focus state is active. Class scanning does not prove that a selector matches a reachable DOM relationship; a retained rule may still never match.

```sh
cd pruning-check
```

### Keep external and uncertain sources safe \{#keep-external-and-uncertain-sources-safe\}

For a finite class added by a widget, list its complete name in the pruned file:

```css
@prune native;
@safelist "report-exported";

@layer components {
  .report-exported { border-style: double; }
}
```

A safelist supplies candidates; it does not add classes to the DOM. For an open-ended CMS or vendor source, preserve its native rules in their owning file instead of guessing at a complete list:

```css name=src/cms.css
@preserve native;

@layer components {
  .cms-callout { border-inline-start: 3px solid currentColor; }
}
```

Load that file wherever the CMS content can appear. `@preserve native` overrides native pruning in its file. It preserves native delivery, not byte-for-byte source formatting, and does not force every unused utility into the output.

Review animations and variables alongside selectors. In an opted-in file, managed keyframes become on-demand definitions. A retained animation declaration and its variable dependencies can keep the required definitions alive. Names supplied only by external JavaScript may need exact `@safelist keyframes "report-enter";` entries. Follow the [keyframe contract](/reference/directives/pruning#native-keyframes), including conditional/layer wrapping and restrictions on anonymous layers and relative URLs. Arbitrary hand-written native selectors are not runtime definitions.

## Keep rendering mode and pruning separate \{#rendering-and-pruning\}

Rendering mode answers when classes become CSS and whether the browser can generate new rules. Native pruning answers which eligible native rules survive a stylesheet build. Progressive rendering can use a pruned native stylesheet while still delivering the initial page CSS and supporting later utility classes.

<DeliveryIllustration id="dimensions" />

Static extraction needs complete class names in its source set. Native pruning needs the native names that may be used. Full literal maps make finite alternatives auditable in both cases. Runtime and progressive modes can also handle new valid utility names constructed after startup; their validity and generation cost still matter. Use CSS variables for continuously changing values when one stable rule suffices.

Runtime generation cannot reconstruct an arbitrary native selector that pruning removed. Adding `report-ready` later only works if that native rule was retained and loaded. Managed keyframes have their own definition and dependency contract; do not infer their behavior from the treatment of ordinary selectors.

For the example, verify these separately:

1. View the response source before JavaScript: `style#master-css` contains the initial `p-lg` utility. The native report stylesheet is linked only on Reports.
2. Refresh Reports: the retained native state rules apply without needing newly generated utilities.
3. Reload Reports for an independent runtime check. Before refreshing the report, add a new valid utility absent from the page's hydration manifest in DevTools:

```js
const report = document.querySelector('#report')
report.classList.add('(letter-spacing:0.123em)')
```

Inspect the computed letter spacing and `document.querySelector('style#master-css').sheet.cssRules`. With the default progressive startup policy and valid hydration data, a missing class triggers the deferred engine/program path. A class already covered by the page manifest does not establish that this path works. Do not use the style element's text content as a live CSSOM snapshot.

Keep HTML, CSS, hydration data and runtime resources from the same build. Test production as well as development; integrations can use different development behavior. See [Rendering modes](/guide/rendering-modes) for startup options, hydration failures and framework support.

## Prerender pages whose classes are in their HTML \{#prerender\}

When every route is rendered at build or request time, `prerender` delivers each page's rules in `style#master-css` and ships no Master CSS runtime, engine, program or hydration data. It suits documentation, marketing and content sites whose interactive islands only switch between states the server renders. In a 384-page documentation build, switching from `progressive` to `prerender` left every page's initial CSS unchanged and removed a 38 KB runtime script and a hydration manifest from each page.

The cost moves to authoring. A class that first appears after hydration has no rule, and `@safelist` does not add one: prerendering generates CSS from page HTML only. Before switching, keep the progressive build and find the rules its runtime generates. Install this recorder before the page's scripts run, for example with Playwright's `page.addInitScript()`, then scroll each page and exercise its controls:

```js
// Each call is a rule the runtime made for a class absent from the HTML.
window.generatedRules = []
for (const prototype of [CSSStyleSheet.prototype, CSSGroupingRule.prototype]) {
  const insertRule = prototype.insertRule
  prototype.insertRule = function (rule, index) {
    window.generatedRules.push(rule)
    return insertRule.call(this, rule, index)
  }
}
```

Most pages record nothing. Rewrite each class that does appear so the server HTML already contains it:

| Source of the late class | Prerender-safe form |
| --- | --- |
| A state appends it, such as `invisible` while a dialog is open | Keep `invisible[data-open]` in the markup and toggle `data-open` |
| It is built from a value, such as `` `items-${align}` `` | List each finite option, such as `items-center[data-align=center]`, and set `data-align`; pass unbounded values through CSS variables |
| It belongs to a view rendered only after an interaction | Render that view on the server with the `hidden` attribute and toggle the attribute |

The `hidden` attribute relies on the base `[hidden]` rule, so a display utility such as `grid` on the same element overrides it. Put `hidden` on an element without one. Hidden elements take no part in view transitions, so a hidden view can share a `view-transition-name` with the visible one.

Verify the switch with both builds. Compare each page's `style#master-css` after removing the hydration attribute: only the rewritten pages should change, by the rules that previously came from the runtime. Repeat the recording on the prerender build, and list classes on elements that match no rule. Raise the style budget only for the pages whose rules moved into the HTML.

## Compare cost and behavior, then set a budget \{#verify-and-budget\}

Keep one change under review at a time: first delivery ownership, then pruning where supported, then asset grouping if measurements justify it. For this example, compare the version with `reports.css` imported in `main.js` against the version above. Overview should lose report rules; Reports should keep both its appearance and interaction states.

<DeliveryIllustration id="verification" />

<DocumentComparison>

| Check | Overview | Reports |
| --- | --- | --- |
| Direct production load | Navigation and page typography remain; no report rules | Panel and all required native states arrive |
| Interaction | Navigation still works | Refresh and keyboard focus retain their intended styles |
| Navigation and cache | Count newly fetched and reused CSS assets separately | Test arrival from Overview and a fresh direct load |
| Progressive output | Initial utility CSS exists before runtime | Initial CSS plus a genuinely new utility both work |

</DocumentComparison>

Record unique external CSS bytes, gzip/Brotli bytes, inline CSS, file count and import depth using the same method as the baseline. Inspect theme variables, conditional rules, pseudo-elements and animation dependencies as well as selectors. Explain each output difference: moved delivery, removed unused rules, deduplication, or a necessary dependency repair.

A local file can produce several output fragments; source file count is not request count. In this small example, moving the import reduces Overview’s delivered CSS but increases Reports’ fragments in the tested build. That proves a narrower owner, not a performance win for every route. Compare the tradeoff before accepting it as an optimization. Smaller route bundles can reduce a cold load while giving the next page more new bytes to fetch. Sharing stable assets can improve reuse, while excessive splitting adds requests and import chains. Compare the whole navigation sequence as well as each page. Let the applicable bundler or integration assemble assets with correct URLs, conditions, layers and cache identity; do not concatenate arbitrary CSS files to chase a lower count.

Only after behavior passes, save the measured per-page ceilings in your project's existing checks. Include the feature page and the page that must not receive it. There is no fixed KB limit that suits every application. A new feature may justify a changed budget, but the review should name the added behavior and its measured cost. Keep timing samples separate from deterministic byte ceilings, and do not turn a small timing fluctuation into a speed claim.

For agent-assisted work, give the agent this guide, the target routes, existing mode and allowed scope. Ask for the baseline, source change, production output and exercised states. A manifest inspection or clean lint result is useful source evidence; neither replaces a build or browser verification.
