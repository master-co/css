## Overview [sr-only]
Choose a rendering mode by when your application knows its complete class names. Start with static rendering when those names are visible in source. Use pre-rendering to generate CSS from finished page HTML, runtime rendering for new classes created in the browser, or progressive rendering to combine page CSS with runtime support.

Complete your framework's [installation guide](/guide/installation) first. Official integrations load the CSS entry and configure the selected mode; the examples below explain what each mode does and how to verify it. Framework support and the HTML available for processing depend on that integration.

## Choose a rendering mode \{#comparisons\}

| Mode | Classes come from | Initial CSS | Master CSS in the browser |
| --- | --- | --- | --- |
| [Static](#static-rendering) | Complete strings in source files | A generated stylesheet | No runtime or engine |
| [Pre-render](#pre-rendering--ssg-ssr) | Rendered page HTML | Rules delivered with that page | No runtime or engine |
| [Runtime](#runtime-rendering) | Connected DOM elements | Rules generated after runtime startup | Runtime and engine |
| [Progressive](#progressive-rendering) | Rendered HTML, then later DOM changes | Rules delivered with that page | Runtime tracks usage; the engine can wait until a class is missing |

An interactive application can use static CSS. Switching among known classes, changing CSS variables, and using native selectors do not require a runtime engine. Runtime generation matters when a complete class name first becomes available after the build.

Pre-rendering requires actual page markup. An empty root element in a client-rendered app gives the server renderer no application classes to process. Also check the integration's boundary: the [Next.js progressive adapter](/guide/installation/nextjs#rendering-modes) processes build-time HTML, so request-time dynamic SSR responses rely on the browser runtime for generated rules.

## Static rendering
The build scans source text for complete class strings and generates CSS from the project's definitions. It does not execute application code or observe the DOM. The browser loads the resulting stylesheet without a Master CSS runtime.

### Generated stylesheet entry
Import Master CSS from the stylesheet your application already loads:

```css name=src/style.css
@import '@master/css';
```

This import is the insertion point for generated utilities, their required resources, and the preset's base styles. Use one entry for each generated stylesheet root. Keep it in the top-level import block, before ordinary style rules; other CSS imports in that block are emitted before generated Master CSS.

To see the source-to-CSS process, add this utility definition after the import and use the button in a scanned source file:

<ConfiguredExample source={`@utility btn {
  display: inline-flex;
  padding-inline: var(--spacing-md);
}`} html={'<button class="btn text-center">Save</button>'} />

The scanner finds `btn` and `text-center`. The engine resolves the project recipe and the preset's fixed utility, then generates their rules and referenced resources. Defining `btn` alone does not emit its rule: a scanned class or explicit safelist must request it.

Integrations discover ordinary application sources and update CSS during development. Keep complete class names in source and pass changing values through CSS variables; [Scanning and pruning](/guide/scanning-and-pruning) covers both, plus `@source` and safelist exceptions.

### Native CSS entries
Native selectors in the CSS entry are preserved by default, even when their classes are absent from scanned source. Their `var(--*)` and animation references can retain the matching theme variables and keyframes.

Use `pruneNativeCSS: true` when you intend to prune project-owned native CSS, or `@prune native;` for one file. `@preserve native;` excludes a file from integration-level pruning. See [pruning unused native CSS](/guide/scanning-and-pruning#prune-native-css).

## Runtime rendering
Use runtime rendering when class names become known in the browser, such as in a visual editor or content loaded after the build. The runtime uses [MutationObserver](https://developer.mozilla.org/en-US/docs/Web/API/MutationObserver) to track connected elements and their class changes, then inserts or reuses the matching CSS rules.

<DeliveryFlow name="runtime" />

Select runtime mode through your integration, for example the [Vite runtime setup](/guide/installation/vite#rendering-modes). Once it is running, execute these snippets one at a time in the browser console:

<StepSection>
  <Step>
    #### Insert an element
    ```js
    const h1 = document.createElement('h1')
    h1.className = 'text-center'
    h1.textContent = 'Hello World'
    document.body.append(h1)
    ```
    The connected heading becomes centered when the runtime generates its rule.
  </Step>
  <Step>
    #### Add a class
    ```js
    h1.classList.add('(font-size:3rem)')
    ```
    The heading grows to `3rem`. Its existing alignment rule remains in use.
  </Step>
  <Step>
    #### Remove a class
    ```js
    h1.classList.remove('text-center')
    ```
    The heading stops matching the alignment rule. It returns to its inherited alignment, even if the runtime temporarily retains the unused rule.
  </Step>
  <Step>
    #### Remove the element
    ```js
    h1.remove()
    ```
    Neither class is used by this heading anymore. If no other connected element uses them, their rules can be removed during idle cleanup.
  </Step>
</StepSection>

These are the rules used while both classes are present:

<Class2CSS>{['text-center', '(font-size:3rem)']}</Class2CSS>

Runtime generation depends on JavaScript startup. Use pre-rendered CSS when the page's initial rules must already be available in the response, and runtime support only when later class names require it.

### Hide the page until the runtime starts \{#prevent-premature-rendering\}
A runtime-only page has no rules until the runtime generates them. Add `hidden` to the root element so it is not painted unstyled:

```html
<html lang="en" hidden>
  <!-- Load the stylesheet and runtime using your integration's setup. -->
</html>
```

The runtime removes `hidden` after startup; its handled startup error path also unhides the root. If JavaScript is disabled, or the runtime script is blocked or fails to download, the page stays hidden. Use static or pre-rendered CSS for content that must remain readable then. Progressive pages already carry the first screen's CSS and stay visible.

### Preload the runtime program \{#preload-runtime-engine\}
The engine needs its program before it can generate the first rules. On a runtime-only page, preload the program so its request starts while the document is parsed. Match the runtime's request with `as="fetch"` and `crossorigin`, also on the same origin:

```html
<!DOCTYPE html>
<html lang="en" hidden>
<head>
  <link rel="preload" as="fetch" crossorigin href="/master-css/default-program.bin"> <!-- [!code highlight] -->
  <link rel="stylesheet" href="/master-css/base.css">
  <script src="/master-css/global.min.js"></script>
</head>
</html>
```

| File | Preload? |
| --- | --- |
| CDN `default-program.bin` | Yes, on CDN runtime-only pages that use the packaged default preset. |
| Project program `master-css-program.<hash>.bin` | Yes, on runtime-only pages; official runtime integrations add the hint. No on progressive pages, where the engine and program wait until a class needs them. |
| Page hydration manifest | No. It is handoff data the browser does not need to paint. |

Confirm in DevTools that the runtime reuses the preloaded response instead of requesting it again. See [`rel="preload"`](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Attributes/rel/preload) for the matching rules.

## Pre-rendering — SSG, SSR
Use pre-rendering when your build or server has the final page HTML and you do not need browser generation for later classes. The server renderer reads that HTML, generates its rules, and inserts them into `style#master-css`. It generates CSS from markup; it does not render your application components into HTML.

Official integrations perform this step for their supported HTML outputs. For a custom server or build pipeline, this example uses `virtual:master-css-manifest` supplied by a build integration. That virtual module must be resolved by the build tool before the server code runs.

```html name=index.html
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
</head>
<body>
  <h1 class="font-5xl">Hello World</h1>
</body>
</html>
```

```ts name=server.ts
import { readFileSync } from 'node:fs'
import { createServerRenderer } from '@master/css-server'
import manifest from 'virtual:master-css-manifest'

const indexHTML = readFileSync('./index.html', 'utf-8')
const renderer = createServerRenderer({ manifest, maxCachedClasses: Infinity })

const { html } = renderer.renderHTML(indexHTML)

renderer.dispose()
```

Write or serve the returned `html`. Its `style#master-css` contains the heading's rule and the font-size token it needs:

<Class2CSS>{'font-5xl'}</Class2CSS>

No Master CSS runtime or hydration manifest is needed for this output. A class that only appears later needs CSS supplied separately, or a mode with runtime support.

The renderer can reuse cached rules across a finite static build while producing page-specific CSS. Recreate it when the manifest changes and dispose it when the build ends. For a long-lived server, choose a bounded `maxCachedClasses` instead of the build example's `Infinity`; see the [server API](/reference/packages#css-server).

## Progressive rendering
Use progressive rendering when the server or build can generate the initial page CSS and the browser may later introduce new classes. The response carries that CSS in `style#master-css`; the runtime reads a page hydration manifest to distinguish covered classes from those that need the engine.

<DeliveryFlow name="progressive" />

A typical output points the style element to an external manifest:

```html
<style id="master-css" data-master-css-hydration-manifest="/_master-css/hydration/master-css-hydration.<hash>.json">...</style>
```

The integration supplies the actual asset URL. Custom SSR hosts that cannot publish a stable JSON asset can use inline `script#master-css-hydration-manifest` instead. Pages without generated rules or managed resources do not need a manifest pointer.

The browser can apply the inline CSS before the runtime or manifest loads. This describes when CSS is available; actual paint timing still depends on the page's other resources. Do not preload the page hydration manifest or the deferred project program; see [preloading](#preload-runtime-engine).

A class listed in the manifest can be reused without starting the engine. This includes ordinary authored classes and rule-free state or theme classes referenced by generated or project selectors. Changing an attribute used by an already-rendered selector also needs no new class rule. A complete class absent from the manifest starts the engine, even if it appeared elsewhere in the project's source.

<GuideStudy id="progressive-known-class" />

### CSS hydration
Hydration lets the runtime adopt existing CSS rules. At startup it reads the explicit `hydrationManifest` option, or discovers the inline manifest or the URL on `style#master-css`. With the engine deferred, it tracks usage without rebuilding the stylesheet.

<DeliveryFlow name="hydration" />

When a new class or `cssRuntime.ready()` starts the engine, the browser engine replays the manifest's classes in server rule order, validates resources, and compares the generated result with the existing CSSOM. Matching rules become runtime-managed rules; new classes can then generate additional CSS. Removed classes may keep their pre-rendered rules until this handoff, then enter the normal retained-rule cleanup path.

The manifest carries resource order and the globals already emitted by the page's stylesheets. It does not repeat the CSS text or replace the project program. Keep it with the HTML and assets from the same build.

## Integration support \{#integration-support\}

Static rendering is the default for these official adapters. Runtime generation is an explicit choice for classes that are unknown at build time. `pre-render` generates CSS from HTML without a client runtime; `progressive` combines HTML rendering with a runtime for later classes. The HTML each adapter can process depends on its host:

| Adapter | Static | Runtime | `pre-render` and server HTML | `progressive` |
| --- | --- | --- | --- | --- |
| [Vite](/guide/installation/vite) | Build-time extraction | Injected through Vite's HTML pipeline | HTML processed by Vite hooks; custom SSR needs a server integration | Vite HTML rendering plus runtime; custom SSR needs its own HTML rendering |
| [Webpack](/guide/installation/webpack) | Build-time extraction | Injected into compilation HTML assets | Your HTML host must call `@master/css-server`; the plugin has no request-time server hook | Runtime delivery is provided; your host supplies rendered HTML and hydration data |
| [Next.js](/guide/installation/nextjs) | Build-time extraction | Client instrumentation | HTML outputs processed after the build; dynamic request-time SSR is not transformed | Build-rendered HTML plus runtime; dynamic SSR has no automatic server CSS injection |
| [Astro](/guide/installation/astro) | Build-time extraction through Vite | Injected page script | Astro middleware processes prerendered pages and server HTML responses | Middleware rendering plus runtime |
| [Nuxt](/guide/installation/nuxtjs) | Build-time extraction through Vite | Nuxt client plugin | Nitro HTML responses with string bodies; streaming bodies are not transformed | Nitro HTML rendering plus client runtime |
| [SvelteKit](/guide/installation/svelte) | Build-time extraction through Vite | Requires the documented client hook | Requires the Master CSS server handle; it processes page chunks during SSR and prerendering | Requires both the server handle and client hook |

Vite and Webpack cannot add server behavior to a framework merely because it uses that bundler. Webpack's HTML injection also does not rewrite files served directly from a development server's static directory. Astro middleware reads the complete HTML response before returning it; SvelteKit uses its page-chunk hook. Follow the framework guide when choosing the delivery path. PHP, Rails, CMS and .NET hosts build the asset with Vite and load it from their templates; see [Server-rendered apps](/guide/installation/server-rendered).


## Verify the selected mode
Test a production build as well as development: an integration may use runtime generation during development even when production pre-renders CSS.

| Mode | What to verify |
| --- | --- |
| Static | The generated HTML loads the stylesheet, and representative complete source classes have rules in it. Those styles remain with JavaScript disabled. |
| Pre-render | The response source contains `style#master-css` with the page's rules. Verify before running JavaScript; the live DOM alone cannot prove pre-rendering occurred. |
| Runtime | Insert a class absent from the initial DOM and check its computed style and generated CSS rule after the runtime observes it. |
| Progressive | Verify pre-rendered CSS first, then introduce a class absent from the page manifest and check that its rule is generated. Test dynamic SSR routes separately if the adapter only processes build-time HTML. |

### Inspect the running stylesheet \{#running-style-sheet\}
The runtime owns `style#master-css` and updates its CSSOM. The element's text content is not a reliable live view after startup. Inspect the stylesheet's [cssRules](https://developer.mozilla.org/en-US/docs/Web/API/CSSStyleSheet/cssRules) instead:

```js
const sheet = document.querySelector('style#master-css').sheet
console.log(sheet.cssRules)
```

### Diagnose progressive startup

| Observation | Meaning and next check |
| --- | --- |
| CSS is rebuilt after a warning | The existing rules do not match the hydration data, or the style has no manifest pointer. Check that HTML, CSS and manifest assets belong to the same build. |
| Startup rejects with `INVALID_HYDRATION_MANIFEST` | A referenced inline or external manifest could not be loaded or validated. Check the asset URL, response and deployed files. |
| Initial CSS works but new classes do not | The deferred engine may have failed to load. Inspect `onDiagnostic`, the program request and `cssRuntime.snapshot().engine`. Existing pre-rendered CSS is retained; `refresh()` or a new `start()` can retry. |

When new classes are likely soon after load, `enginePrefetch: 'idle'` starts the engine during idle time. Use `engine: 'eager'` to start it during `start()`. Both change the default deferral tradeoff and should be chosen for the page's actual interactions.

### Interaction-heavy screens
An interaction that adds many first-time classes asks the browser to process both DOM changes and new stylesheet rules. For editors, data grids, builders, or other large dynamic views:

- Keep stable layout, typography and component states in shared classes.
- Warm predictable runtime classes before inserting the view, after the engine is ready.
- Use CSS variables or inline styles for volatile per-element values such as coordinates or user-generated colors.
- Use native selectors for repeated states that do not need a distinct generated class for every value.

To warm the predictable classes for a view, use the handle returned by `MasterCSSRuntime.start()`:

```js
await cssRuntime.ready()
cssRuntime.ensureClassRules(['grid', 'gap-md'])
```

Measure runtime JavaScript, program delivery, initialization, DOM observation, and CSSOM work together. Compressed JavaScript size alone does not describe interaction cost. See [Benchmarks](/benchmarks) for measurements and their conditions.

For runtime state, delivery artifacts, custom startup entries and engine hosts, see the [runtime](/reference/packages#css-runtime), [server](/reference/packages#css-server) and [engine](/reference/packages#css) packages.
