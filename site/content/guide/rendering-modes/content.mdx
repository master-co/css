## Overview [sr-only]
Choose a rendering mode by when your application knows its complete class names. Start with static rendering when those names are visible in source. Use pre-rendering to generate CSS from finished page HTML, runtime rendering for new classes created in the browser, or progressive rendering to combine page CSS with runtime support.

Complete your framework's [installation guide](/guide/installation) first. Official integrations load the CSS entry and configure the selected mode; the examples below explain what each mode does and how to verify it. Framework support and the HTML available for processing depend on that integration.

## Choose a rendering mode \{#comparisons\}

| Mode | Classes come from | Initial CSS | Master CSS in the browser |
| --- | --- | --- | --- |
| [Static](#static-rendering) | Complete strings in source files | A generated stylesheet | No runtime or engine |
| [Pre-render](#pre-rendering--ssg-ssr) | Rendered page HTML | Rules delivered with that page | No runtime or engine |
| [Runtime](#runtime-rendering) | Connected DOM elements | Rules generated after runtime startup | Runtime and engine |
| [Progressive](#progressive-rendering) | Rendered HTML, then later DOM changes | Rules delivered with that page | Runtime tracks usage; the engine can wait until a class is missing |

An interactive application can use static CSS. Switching among known classes, changing CSS variables, and using native selectors do not require a runtime engine. Runtime generation matters when a complete class name first becomes available after the build.

Pre-rendering requires actual page markup. An empty root element in a client-rendered app gives the server renderer no application classes to process. Also check the integration's boundary: the [Next.js progressive adapter](/guide/installation/nextjs/progressive) processes build-time HTML, so request-time dynamic SSR responses rely on the browser runtime for generated rules.

## Static rendering
The build scans source text for complete class strings and generates CSS from the project's definitions. It does not execute application code or observe the DOM. The browser loads the resulting stylesheet without a Master CSS runtime.

### Generated stylesheet entry
Import Master CSS from the stylesheet your application already loads:

```css name=src/style.css
@import '@master/css';
```

This import is the insertion point for generated utilities, their required resources, and the preset's base styles. Use one entry for each generated stylesheet root. Keep it in the top-level import block, before ordinary style rules; other CSS imports in that block are emitted before generated Master CSS.

To see the source-to-CSS process, add this utility definition after the import and use the button in a scanned source file:

<ConfiguredExample source={`@utility btn {
  display: inline-flex;
  padding-inline: var(--spacing-md);
}`} html={'<button class="btn text-align:center">Save</button>'} />

The scanner finds `btn` and `text-align:center`. The engine recognizes the registered utility and the direct declaration, then generates their rules and referenced resources. Defining `btn` alone does not emit its rule: a scanned class or explicit safelist must request it.

Integrations discover ordinary application sources and update CSS during development. Use `@source` when you need to include files outside the normal scan path or define a scoped source set. See [Scanning latent classes](/guide/scanning-latent-classes) for discovery and safelist controls.

### Native CSS entries
Native selectors in the CSS entry are preserved by default, even when their classes are absent from scanned source. Their `var(--*)` and animation references can retain the matching theme variables and keyframes.

Use `pruneNativeCSS: true` when you intend to prune project-owned native CSS, or `@prune native;` for one file. `@preserve native;` excludes a file from integration-level pruning. Follow [Native CSS pruning](/guide/native-css-pruning) for a complete example and the limits of source-based usage detection.

### Dynamic class limitations
Static scanning cannot infer the results of string concatenation, helper functions, or remote content. Keep complete alternatives in source:

(x) Do not construct partial class names.
```tsx
const className = 'bg-' + (error ? 'red' : 'green')
```

(o) Map states to complete class names.
```tsx
const className = error ? 'bg-red' : 'bg-green'
```

For a changing value, keep the class fixed and update a CSS variable. This class remains discoverable even when application code changes `--size`:

```html
<div class="font-size:var(--size)@sm" style="--size: 2rem">Preview</div>
```

<Class2CSS>{'font-size:var(--size)@sm'}</Class2CSS>

## Runtime rendering
Use runtime rendering when class names become known in the browser, such as in a visual editor or content loaded after the build. The runtime uses [MutationObserver](https://developer.mozilla.org/en-US/docs/Web/API/MutationObserver) to track connected elements and their class changes, then inserts or reuses the matching CSS rules.

<DeliveryFlow name="runtime" />

Select runtime mode through your integration, for example the [Vite runtime setup](/guide/installation/vite/runtime). Once it is running, execute these snippets one at a time in the browser console:

<StepSection>
  <Step>
    #### <StepNum />Insert an element
    ```js
    const h1 = document.createElement('h1')
    h1.className = 'text-align:center'
    h1.textContent = 'Hello World'
    document.body.append(h1)
    ```
    The connected heading becomes centered when the runtime generates its rule.
  </Step>
  <Step>
    #### <StepNum />Add a class
    ```js
    h1.classList.add('font-size:3rem')
    ```
    The heading grows to `3rem`. Its existing alignment rule remains in use.
  </Step>
  <Step>
    #### <StepNum />Remove a class
    ```js
    h1.classList.remove('text-align:center')
    ```
    The heading stops matching the alignment rule. It returns to its inherited alignment, even if the runtime temporarily retains the unused rule.
  </Step>
  <Step>
    #### <StepNum />Remove the element
    ```js
    h1.remove()
    ```
    Neither class is used by this heading anymore. If no other connected element uses them, their rules can be removed during idle cleanup.
  </Step>
</StepSection>

These are the rules used while both classes are present:

<Class2CSS>{['text-align:center', 'font-size:3rem']}</Class2CSS>

Runtime generation depends on JavaScript startup. Use pre-rendered CSS when the page's initial rules must already be available in the response, and runtime support only when later class names require it.

## Pre-rendering — SSG, SSR
Use pre-rendering when your build or server has the final page HTML and you do not need browser generation for later classes. The server renderer reads that HTML, generates its rules, and inserts them into `style#master-css`. It generates CSS from markup; it does not render your application components into HTML.

Official integrations perform this step for their supported HTML outputs. For a custom server or build pipeline, this example uses `virtual:master-css-manifest` supplied by a build integration. That virtual module must be resolved by the build tool before the server code runs.

```html name=index.html
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
</head>
<body>
  <h1 class="font-5xl">Hello World</h1>
</body>
</html>
```

```ts name=server.ts
import { readFileSync } from 'node:fs'
import { createServerRenderer } from '@master/css-server'
import manifest from 'virtual:master-css-manifest'

const indexHTML = readFileSync('./index.html', 'utf-8')
const renderer = createServerRenderer({ manifest, maxCachedClasses: Infinity })

const { html } = renderer.renderHTML(indexHTML)

renderer.dispose()
```

Write or serve the returned `html`. Its `style#master-css` contains the heading's rule and the font-size token it needs:

<Class2CSS>{'font-5xl'}</Class2CSS>

No Master CSS runtime or hydration manifest is needed for this output. A class that only appears later needs CSS supplied separately, or a mode with runtime support.

The renderer can reuse cached rules across a finite static build while producing page-specific CSS. Recreate it when the manifest changes and dispose it when the build ends. For a long-lived server, choose a bounded `maxCachedClasses` instead of the build example's `Infinity`; see the [server API](/reference/packages#css-server).

## Progressive rendering
Use progressive rendering when the server or build can generate the initial page CSS and the browser may later introduce new classes. The response carries that CSS in `style#master-css`; the runtime reads a page hydration manifest to distinguish covered classes from those that need the engine.

<DeliveryFlow name="progressive" />

A typical output points the style element to an external manifest:

```html
<style id="master-css" data-master-css-hydration-manifest="/_master-css/hydration/master-css-hydration.<hash>.json">...</style>
```

The integration supplies the actual asset URL. Custom SSR hosts that cannot publish a stable JSON asset can use inline `script#master-css-hydration-manifest` instead. Pages without generated rules or managed resources do not need a manifest pointer.

The browser can apply the inline CSS before the runtime or manifest loads. This describes when CSS is available; actual paint timing still depends on the page's other resources. Do not preload the page hydration manifest or the deferred project program. See [Critical resources](/guide/preload-critical-resources) for delivery timing.

A class listed in the manifest can be reused without starting the engine. This includes ordinary authored classes and rule-free state or theme classes referenced by generated or project selectors. Changing an attribute used by an already-rendered selector also needs no new class rule. A complete class absent from the manifest starts the engine, even if it appeared elsewhere in the project's source.

### CSS hydration
Hydration lets the runtime adopt existing CSS rules. At startup it reads the explicit `hydrationManifest` option, or discovers the inline manifest or the URL on `style#master-css`. With the engine deferred, it tracks usage without rebuilding the stylesheet.

<DeliveryFlow name="hydration" />

When a new class or `cssRuntime.ready()` starts the engine, the browser engine replays the manifest's classes in server rule order, validates resources, and compares the generated result with the existing CSSOM. Matching rules become runtime-managed rules; new classes can then generate additional CSS. Removed classes may keep their pre-rendered rules until this handoff, then enter the normal retained-rule cleanup path.

The manifest carries resource order and the globals already emitted by the page's stylesheets. It does not repeat the CSS text or replace the project program. Keep it with the HTML and assets from the same build.

## Verify the selected mode
Test a production build as well as development: an integration may use runtime generation during development even when production pre-renders CSS.

| Mode | What to verify |
| --- | --- |
| Static | The generated HTML loads the stylesheet, and representative complete source classes have rules in it. Those styles remain with JavaScript disabled. |
| Pre-render | The response source contains `style#master-css` with the page's rules. Verify before running JavaScript; the live DOM alone cannot prove pre-rendering occurred. |
| Runtime | Insert a class absent from the initial DOM and check its computed style and generated CSS rule after the runtime observes it. |
| Progressive | Verify pre-rendered CSS first, then introduce a class absent from the page manifest and check that its rule is generated. Test dynamic SSR routes separately if the adapter only processes build-time HTML. |

### Inspect the running stylesheet \{#running-style-sheet\}
The runtime owns `style#master-css` and updates its CSSOM. The element's text content is not a reliable live view after startup. Inspect the stylesheet's [cssRules](https://developer.mozilla.org/en-US/docs/Web/API/CSSStyleSheet/cssRules) instead:

```js
const sheet = document.querySelector('style#master-css').sheet
console.log(sheet.cssRules)
```

### Runtime state
For application code or deeper debugging, keep the handle returned by `MasterCSSRuntime.start()` as `cssRuntime`; the [custom startup example](#project-manifest-delivery) below shows how. A snapshot distinguishes active DOM usage from cached generated rules:

```js
const snapshot = cssRuntime.snapshot()
console.log(snapshot.usageCounts['text-align:center'])
console.log(snapshot.classRules['text-align:center']?.retained)
console.log(snapshot.classRules['text-align:center']?.rules)
```

`usageCounts` tracks connected DOM usage. `classRules` can also include warmed, hydrated, or temporarily retained rules, so a cached rule does not imply that a connected element still uses its class. `engine` reports `'deferred'`, `'loading'`, `'ready'`, or `'failed'`. Before a deferred engine starts, snapshots have usage counts but no generated rule entries in their class snapshots, and `layers` is empty.

Direct rule APIs operate separately from DOM usage: `ensureClassRules([...])` generates or reuses rules, while `deleteClassRules([...])` removes them synchronously and bypasses retention. Calls made before the engine is ready throw `RUNTIME_ENGINE_NOT_READY` and start it; await `cssRuntime.ready()` before deliberately warming classes. See the [runtime API](/reference/packages#css-runtime) for the source of the snapshot and method contracts.

### Diagnose progressive startup

| Observation | Meaning and next check |
| --- | --- |
| CSS is rebuilt after a warning | The existing rules do not match the hydration data, or the style has no manifest pointer. Check that HTML, CSS and manifest assets belong to the same build. |
| Startup rejects with `INVALID_HYDRATION_MANIFEST` | A referenced inline or external manifest could not be loaded or validated. Check the asset URL, response and deployed files. |
| Initial CSS works but new classes do not | The deferred engine may have failed to load. Inspect `onDiagnostic` and the program request. Existing pre-rendered CSS is retained; `refresh()` or a new `start()` can retry. |

When new classes are likely soon after load, `enginePrefetch: 'idle'` starts the engine during idle time. Use `engine: 'eager'` to start it during `start()`. Both change the default deferral tradeoff and should be chosen for the page's actual interactions.

### Interaction-heavy screens
An interaction that adds many first-time classes asks the browser to process both DOM changes and new stylesheet rules. For editors, data grids, builders, or other large dynamic views:

- Keep stable layout, typography and component states in shared classes.
- Warm predictable runtime classes before inserting the view, after the engine is ready.
- Use CSS variables or inline styles for volatile per-element values such as coordinates or user-generated colors.
- Use native selectors for repeated states that do not need a distinct generated class for every value.

To warm the predictable classes for a view:

```js
await cssRuntime.ready()
cssRuntime.ensureClassRules(['display:grid', 'gap-md'])
```

Measure runtime JavaScript, program delivery, initialization, DOM observation, and CSSOM work together. Compressed JavaScript size alone does not describe interaction cost. See [Benchmarks](/guide/benchmarks) for measurements and their conditions.

## Shared rendering pipeline
All modes use the same project CSS definitions and cascade layers. `@import '@master/css'` loads the preset through the CSS entry graph; its base stylesheet declares `@layer theme, base, defaults, components, utilities;`. Generated rules use those layers without redeclaring their global order. Use `@reference` when you need definition context without loading the referenced file's native CSS.

The delivery artifacts have different roles:

| Artifact | Role |
| --- | --- |
| Project CSS entry graph | Authoring source for tokens, utilities, mixins, conditions, native styles and source directives. |
| `MasterCSSManifest` | Compiled definitions for the Node engine, server renderer and tooling. Build integrations expose it as `virtual:master-css-manifest`. |
| `virtual:master-css-program` | Compiled executable bytes for the browser engine. Production browser builds can fetch a hashed `.bin` asset. |
| `virtual:master-css-emitted-globals` | Variables and keyframes already emitted by the CSS entry, so runtime generation does not duplicate them. |
| Page hydration manifest | Rendered classes, resource order and page-emitted globals used to adopt one page's existing CSS. |

The project manifest and program define what can be generated. The page hydration manifest describes what a particular response already covers. A framework's build report is separate from all three.

### Project program delivery \{#project-manifest-delivery\}
Official integrations handle runtime startup. A custom bundled entry can use a loader so the project program is requested only when the engine needs it:

```js name=src/runtime.js
import { MasterCSSRuntime } from '@master/css-runtime'
import emittedGlobals from 'virtual:master-css-emitted-globals'

const cssRuntime = await MasterCSSRuntime.start({
  program: () => import('virtual:master-css-program').then(module => module.default),
  emittedGlobals
})
cssRuntime.observe()
```

This example assumes a build integration resolves both virtual modules and the application loads its CSS entry. Do not add a second startup entry to an integration that already injects one. On runtime-only pages the engine needs the program during startup; progressive pages with a valid manifest can defer it.

Let the integration supply hashed program URLs and any runtime-mode preload. Development and server builds may inline program bytes. The `emittedGlobals` object applies to every page using the runtime bundle; integrations with separate page-CSS and runtime builds must account for the CSS those pages deliver. Progressive pages additionally provide their page-specific globals through hydration data.

## Shared execution contract
Build-time and server generation use Rust semantics. The browser's JavaScript engine executes compiled programs and must produce the same CSS for the same definitions and classes. Transport and hydration metadata can differ without changing the styling language.

### Manifest compatibility
Compile project CSS with matching compiler, server and runtime packages. Unsupported execution or language versions are rejected; changing version fields by hand does not make a manifest compatible.

For stored manifests, use `MasterCSSManifest` and `serializeMasterCSSManifest` from the [schema API](/reference/packages#css-schema). Serialization normalizes derived fields; it does not replace engine validation or preserve comments and editable CSS source formatting. Unknown fields are not a general extension mechanism: retention in an outer envelope does not imply that nested fields are accepted or that the engine executes a new capability.

## Engine state for custom hosts
Most applications can use the integrations above. A custom engine host that tracks rule ownership can query stored rule references after ensuring its classes:

```ts
import { createEngine } from '@master/css'
import manifest from 'virtual:master-css-manifest'

using engine = await createEngine({ manifest })
engine.ensureClassRules(['block', 'hidden'])
const state = engine.executionState(['block', 'missing'])
// state.classes[0].references: [{ layer: 'utilities', key: 'block' }]
// state.classes[1].references: []
// state.resources: current theme, variable and animation state
```

`executionState()` preserves request order, including repeated names, and reads stored references without generating rules. Unknown or never-ensured classes have empty references. Use `snapshot()` for complete rules and CSS; use Node inspection or tooling when you need class diagnostics. Recognition alone does not establish that a CSS value or browser feature is supported. The browser engine does not provide inspection or render sessions.

Hosts must synchronize resource state even when a transition contains no CSS mutations. Follow the [engine source links](/reference/packages#css) and [schema source links](/reference/packages#css-schema) for current types rather than maintaining a separate copy of those interfaces in application code.

### Forward the public engine surface

A wrapper around an official engine must forward state queries as well as rule changes. This example keeps disposal with the owning engine:

```ts
import type { MasterCSSEngine } from '@master/css'

function wrapEngine(inner: MasterCSSEngine): MasterCSSEngine {
  return {
    binding: inner.binding,
    ensureClassRules: names => inner.ensureClassRules(names),
    deleteClassRules: names => inner.deleteClassRules(names),
    registerEmittedGlobals: globals => inner.registerEmittedGlobals(globals),
    replaceEmittedGlobals: globals => inner.replaceEmittedGlobals(globals),
    refresh: manifest => inner.refresh(manifest),
    executionState: names => inner.executionState(names),
    inspect: name => inner.inspect(name),
    snapshot: () => inner.snapshot(),
    dispose: () => inner.dispose(),
    [Symbol.dispose]: () => inner.dispose()
  }
}
```

Read stored references through `executionState()` instead of regenerating a class to inspect ownership. Keep compiler and binding artifacts compatible; their version checks remain part of loading.

### Animation resource placement
Keyframes retain their original stylesheet position and native containers. Native preservation and pruning determine which definitions remain; see the [keyframe contract](/reference/directives/theme#native-keyframes) and [Native CSS pruning](/guide/native-css-pruning). Runtime and server rendering track each definition independently, including same-name definitions in different layers or conditions.

Deploy `.master-css.json` companions and rendered CSS import assets with the build output. Official adapters provide their locations. Runtime uses compiled companions to manage writable stylesheets at the original link positions; cross-origin JSON needs CORS access, and qualified imports can require blob stylesheet URLs allowed by the site's CSP. Disposing runtime ownership restores the original linked stylesheet.

Custom browser hosts can supply `stylesheets: () => [{ sheet, ownerIds }]` for already-writable sheets, including adopted stylesheets in a ShadowRoot. Custom server hosts supply compiler-prepared `stylesheets`, `documentURL`, and `stylesheetImportSource(css, source)` when owned imports need published URLs. Pre-render and progressive adapters prepare those styles before JavaScript runs so hydration can reuse their CSSOM and anonymous layers. See the [runtime](/reference/packages#css-runtime) and [server](/reference/packages#css-server) APIs for the host options.
