## Foreword [sr-only]
Give each application its own project boundary, then share CSS vocabulary through imports. The [Language Service](/guide/language-service), [code linting](/guide/code-linting), and build integrations can use the same app-specific project context.

A project CSS entry importing `@master/css` or a package declaring Master CSS dependencies identifies a workspace. These boundaries are independent of the package manager's workspace list. Start each app's build from its project directory and keep its CSS entry there.

---

## One project, one workspace
Each `package.json` project has one Master CSS workspace: one project manifest graph, source-scanning context, and set of tool integrations.

For independent applications, use separate package projects such as `projects/admin` and `projects/shop`. Each owns its CSS entry and application setup:

This keeps each application's generated CSS, source scanning, diagnostics, and editor state aligned with the same project root. Shared design tokens can still live at the repository root and be imported by each project workspace.

### Share the project manifest source
In each workspace, import shared project CSS files and add workspace-specific definitions after them.
```css name=projects/admin/index.css
@import '@master/css';
@import '../../index.css';

@theme {
  --color-primary: #4f46e5;
}

@layer components {
  .app-shell {
    background-color: var(--color-surface-base);
    min-height: 100vh;
  }
}
```
Definitions after the shared import can override shared tokens and utilities. Native component rules in the same layer follow CSS source order.

Shared files define the vocabulary; each app's entry decides what to import. Keep separate entries for applications with independent scanning and output, while importing the same shared theme wherever it is needed.
