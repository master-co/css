## Overview [sr-only]
Give each application its own project boundary, then share CSS vocabulary through imports. The [Language Service](/guide/language-service), [code linting](/guide/code-linting), and build integrations can use the same app-specific project context.

A project CSS entry importing `@master/css` or a package declaring Master CSS dependencies identifies a workspace. These boundaries are independent of the package manager's workspace list. Start each app's build from its project directory and keep its CSS entry there. Package-manager workspace membership alone does not create a shared Master CSS configuration.

## One project, one workspace
Each `package.json` project has one Master CSS workspace: one project manifest graph, source-scanning context, and set of tool integrations.

For independent applications, use separate package projects such as `projects/admin` and `projects/shop`. Each owns its CSS entry and application setup:

Complete the appropriate [framework setup](/guide/installation#integrations) in each application. Start its development server and production build from that app's directory. This keeps generated CSS, source scanning, diagnostics and editor state aligned with its project root.

Keep shared definitions in a dedicated source file. In this example it supplies tokens, while each application imports the full Master CSS entry itself:

```css name=styles/shared.css
@theme {
  --color-primary: #123456;
}
```

### Share CSS definitions
In each workspace, import shared project CSS files and add workspace-specific definitions after them.
```css name=projects/admin/index.css
@import '@master/css';
@import '../../styles/shared.css';

@theme {
  --color-primary: #4f46e5;
}

@layer components {
  .app-shell {
    background-color: var(--color-surface-base);
    min-height: 100vh;
  }
}
```
Definitions after the shared import can override shared tokens and utilities. Native component rules in the same layer follow CSS source order.

The shop imports the same shared source and makes its own color choice:

```css name=projects/shop/index.css
@import '@master/css';
@import '../../styles/shared.css';

@theme {
  --color-primary: #0f766e;
}
```

Both applications can use the same class:

```html
<p class="flex items-center gap-xs text-sm">
  <span aria-hidden="true" class="h(8) w(8) pill bg-primary"></span>
  Workspace
</p>
```

The admin build emits its `#4f46e5` primary value; the shop build emits `#0f766e`. Changing the admin override should not change the shop output. Build both apps and inspect `--color-primary` in each generated stylesheet to check that the boundary is working.

Shared files define the vocabulary; each app's entry decides what to import. Keep app-specific scanning directives and delivery choices in the owning app rather than the shared stylesheet.

## Include shared component sources

A shared CSS import supplies definitions. Class strings inside a shared component still need to reach the consuming app's scanner. Vite can scan imported workspace modules, while a CLI build started inside an app does not follow JavaScript imports into sibling packages.

If components live in `packages/ui`, add `@source "../../packages/ui/**/*.{js,jsx,ts,tsx}";` to each consuming app's CSS entry. This explicit path includes the shared source in the app's build. It is relative to the CSS file that declares it, so adjust the path when the entry moves.

<ReferenceIllustration id="source-relative-base" />

Installed dependency directories are excluded from automatic scanning. A packaged component library may need a narrow `@source` pattern targeting its distributed source files. Check a class that appears only in that package against the app's production output. See [source boundaries](/reference/rules/extraction#source-boundaries) for exclusions and other source types.

## Verify the boundary before sharing more

From each application's directory, run its production build. Check both outputs after changing one local override: the admin value should change only in admin. Then add a complete class used only by a shared component and confirm the consuming app emits its rule.

If a token is missing, check the CSS import graph. If the definition is available but a shared component's utility is absent, check source selection. These are separate inputs: importing the shared CSS does not automatically include every sibling component file.

Use [Authoring packages](/guide/authoring-packages) when this vocabulary needs a versioned package contract. Use [Scanning class names](/guide/scanning-and-pruning) to define the files each app scans, and [Optimizing CSS delivery](/guide/optimizing-css-delivery#native-pruning) to decide which native rules it can remove.
