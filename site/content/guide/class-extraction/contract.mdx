<a id="overview"></a>

Extraction finds possible class names in source without running the application. These candidates, also called latent classes, are inputs to matching and candidate policy. Finding a string does not establish that it generates a rule, has a valid CSS value or works in a particular browser.

This page defines source boundaries, static extraction, candidate classification and source ownership. [Scanning class names](/guide/scanning-and-pruning) explains how to author discoverable classes and diagnose missing styles. [Scanning directives](/reference/directives/scanning) owns the path and class-pattern grammar.

## Complete static strings \{#candidate-scanning\}

Extractors use the source language's structure. JavaScript and TypeScript strings can contribute candidates even outside `className`: a class passed to a component as display text may still be discovered. The scanner does not infer which branch runs or what a function returns at runtime.

<a id="complete-classes"></a>

| Source form | What extraction can see |
| --- | --- |
| HTML `class="p-md shadow-md"` | Both complete classes |
| JSX `className="p-md"` | The complete class |
| `error ? 'bg-red-60' : 'bg-green-60'` | Both static branches |
| `{ compact: 'p-sm', roomy: 'p-lg' }` | The complete values in the object |
| A template literal with complete static class portions | Those complete portions |
| `'bg-' + tone` or a template interpolation inside a class name | No inferred `bg-red-60` or other completed result |
| A class returned only by an API at runtime | No source string to extract |

For example, the following source exposes both colors and the fixed padding and radius. The `tone` interpolation does not need to be evaluated to discover the complete classes already present in the object:

```js
const tones = {
  neutral: 'bg-surface-base fg-text-neutral',
  destructive: 'bg-red-70 fg-white'
}
const className = `px-md r-md ${tones.destructive}`
```

The extracted class set is `bg-surface-base`, `fg-text-neutral`, `bg-red-70`, `fg-white`, `px-md` and `r-md`. The scanner does not limit output to the destructive branch just because this example selects it.

## Candidate classification \{#validation\}

After extraction, the active manifest and stylesheet registrations determine a candidate's role. Unknown ordinary application classes are not automatically Master CSS errors.

| Candidate | Result |
| --- | --- |
| Registered preset utility such as `p-md` | Generates its matched utility rule and dependencies |
| Project-defined `@utility` class | Generates the rule registered by the project's compiled manifest |
| Registered native class such as `.card` | Records native usage; it does not generate a new utility |
| Unmatched application class | No Master-generated rule |
| Malformed Master class | No rule; inspection can report a syntax diagnostic |
| Matched class with an invalid or unknown CSS value | Can emit CSS; matching alone does not prove value validity or browser support |

<DocumentExample>

```html
<article class="card p-md shadow-md">Release notes</article>
```

<Class2CSS classes={['p-md', 'shadow-md']} />

</DocumentExample>

Here `p-md` and `shadow-md` resolve through the preset. `card` retains a native rule only if the project actually supplies one and its pruning policy considers usage. A native stylesheet is preserved by default; scanning does not opt it into pruning.

A compiler match, CSS syntax validation, CSS value validation and browser support are distinct checks. Use [class inspection](/reference/tools/mcp#mastercss_inspect_class) to distinguish them; a matching class still enters the browser's cascade and computed-value rules.

## Source boundaries \{#source-boundaries\}

Build integrations and CLI flows discover common source-like project files, including HTML, JavaScript, TypeScript, JSX, TSX, supported framework sources, Markdown, MDX and PHP. Ordinary application files do not need a broad `@source` directive.

Automatic discovery respects project and ancestor workspace `.gitignore` files, not global Git ignores. Ignore files apply from the nearest repository root, which may be a worktree, or, without one, from the workspace root. A project that its repository itself ignores, such as a copy in an ignored directory, applies only its own ignore files. Dependencies, declaration files, binary files, VCS data and generated output are excluded. Master output and the current bundler output are not scan inputs; Next.js uses its configured `distDir`.

| Directive | Effect on discovery |
| --- | --- |
| `@source` | Explicitly includes additional paths, including files excluded by automatic discovery or `.gitignore` |
| `@source not` | Excludes paths; takes precedence over inclusion |

Use these exceptions for shared workspace source, external content or a scoped pruning root. Their relative-path rules and supported forms belong to [Scanning directives](/reference/directives/scanning).

Framework integrations prefer original MDX, Vue and Svelte source to scanning compiled display strings a second time. Extraction reads the `<script>` blocks of Vue and Svelte component files as JavaScript, so only string and template literals there contribute candidates, as in other JavaScript sources; property access such as `items.length` is not a class. Only a component's own top-level `<script>` tags start a script block; `<script>` written in a template expression or attribute value is template text. A script block that does not parse as JavaScript or TypeScript is read as text instead, leaving the syntax error to the framework's compiler. `<style>` blocks are not class sources. An extractor's language kind matters: intentional plain-text input can use `kind: 'raw'`, but that is not a fallback for a source that failed to parse.

## Markdown and MDX \{#markdown-and-mdx\}

Markdown and MDX extraction uses the syntax tree. Actual HTML/JSX, ESM and expressions participate. Prose, inline code, ordinary code fences and frontmatter do not. A documentation fence showing a class is therefore not an implicit live example.

A host can register an executable example as a virtual source with `parentSource`, or explicitly safelist its bounded classes. Virtual inputs make the ownership of executable content explicit; the host supplies the actual example source and language kind.

A malformed source reports `SOURCE_PARSE_ERROR`. Development retains the previous successful contribution, while a production build fails. Parsing or reading failure is not equivalent to an empty-source update.

### Source locations \{#source-locations\}

Extraction can report candidate occurrences as well as strings: original UTF-16 ranges, extractor, content kind, owner and inclusion or exclusion reasons. Encoded attributes retain ranges in the original source. Complete URL literals are excluded; an unknown native declaration can remain a candidate for later validation.

## Source ownership \{#scanner-hosts\}

A scanner session tracks current source contributions, not every class it has ever encountered. Updating a source replaces its contribution. Removing one source does not remove a class that another current source or safelist still retains.

<ReferenceIllustration id="shared-source-class" />

These session operations are available through `MasterCSSScanner` from [`@master/css-tooling/scanner/node`](/reference/packages#css-tooling). They describe source ownership; integration users normally rely on their build plugin to perform them.

| Operation | Ownership effect |
| --- | --- |
| `collectCandidates` | Pure extraction; does not retain source contributions |
| `scanSource` | Replaces one source's content, including an empty string |
| `removeSource` | Removes that source and its virtual descendants |
| `reconcileSources` | Supplies the complete next source set for one owner |
| `registerNativeClasses` | Registers native class identities for a stylesheet source |
| `removeOwner` | Removes that owner's sources and native registrations |

```ts
await scanner.scanSource('page.mdx', content, { owner: 'pages' })
await scanner.scanSource('page.mdx#live', html, {
  owner: 'pages', parentSource: 'page.mdx', kind: 'html'
})
scanner.removeSource('page.mdx', { owner: 'pages' })
```

Removing `page.mdx` also removes its virtual example. References from another owner remain independent. A reconciliation retains only the inputs supplied for that owner; explicitly retained virtual inputs remain in that set even if their parent is managed externally.

`changed` indicates a change to generated output or pruning inputs. `sourceChanged` also captures provenance-only updates: a second source can add ownership without changing CSS. The `sources` view exposes the current successful source set, including empty inputs and virtual relationships.

## Runtime values \{#runtime-values\}

A value can change without changing its class name. A complete native declaration class can refer to a custom property supplied by markup or script:

```html
<h1 class="(font-size:var(--headline-size))" style="--headline-size: 2rem">Launch notes</h1>
```

The scanner sees one complete class. Updating `--headline-size` changes the browser's value without a new utility rule. See the [working value example](/guide/scanning-and-pruning#keep-changing-values-out-of-class-names).

The same contract applies to `(width:var(--progress))`: script can call `element.style.setProperty('--progress', '40%')` while the class stays unchanged.

If the class name itself first exists after startup, a static build cannot discover it. Supply a bounded safelist or use [runtime or progressive rendering](/guide/rendering-modes#comparisons).

## Candidate policy \{#included-and-excluded-classes\}

| Directive | Purpose | Limit |
| --- | --- | --- |
| `@safelist` | Retains bounded external classes, such as CMS states or widget classes | Does not bypass matching or define missing utilities |
| `@blocklist` | Prevents false-positive candidates from generating CSS | Does not rewrite the source or remove arbitrary native CSS |

For class patterns, precedence and native usage, see [Scanning directives](/reference/directives/scanning). For removal of native rules and keyframes, see [Native CSS pruning](/reference/directives/pruning). Candidate discovery and native preservation are separate policies.
