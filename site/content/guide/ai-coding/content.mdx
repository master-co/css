Give your coding agent the same styling context you use: the CSS entry, theme tokens, component classes and the project's checks. Connect the Master CSS MCP server so it can inspect that context, preview fixes and compare the impact of a change before you review the result in a browser.

---

## Set up the project first
The [installer](/guide/installation) prepares a project for agents by default. Alongside the framework integration, `npm create @master/css@rc` adds:

- `@master/eslint-config-css` and an `eslint.config.js` that spreads it, so agent output is checked by [Code linting](/guide/code-linting).
- `@master/css-mcp` as a dev dependency, and prints the stdio command for registering it in your MCP client.
- A `## Master CSS` rules block in `AGENTS.md` that points agents at the documentation, the project's vocabulary, MCP and ESLint.

Pass `--no-eslint`, `--no-mcp` or `--no-ai` to skip one of them, or `--minimal` for the framework setup only. Add the project's actual validation commands below the generated `AGENTS.md` block so the agent does not have to infer them.

Then give the project a vocabulary the agent can reuse. Theme tokens make repeated values explicit, and component classes give shared product patterns a stable name:

```css name=app.css
@import '@master/css';

@theme {
  --color-brand: #4f46e5;
  --spacing-card: 1.5rem;
}

@layer components {
  .btn {
    display: inline-flex;
    align-items: center;
    gap: var(--spacing-xs);
    padding-inline: var(--spacing-md);
    border-radius: var(--radius-md);
  }
}
```

## Connect the MCP server \{#connect-the-mcp-server\}
The MCP server runs locally over stdio and reads the workspace passed to `--root`. Clients that accept `mcpServers` JSON, such as Claude Desktop, Cursor, Windsurf, Gemini CLI and Cline, use this shape in their own configuration file:

```json name=mcp-client-config.json
{
  "mcpServers": {
    "master-css": {
      "command": "npx",
      "args": ["-y", "@master/css-mcp@rc", "--root", "/absolute/path/to/project"]
    }
  }
}
```

Clients with their own registration command use the same stdio command:

```bash name=Terminal
# Claude Code (add --scope project for a shared .mcp.json)
claude mcp add --transport stdio master-css -- npx -y @master/css-mcp@rc --root /absolute/path/to/project

# Codex
codex mcp add master-css -- npx -y @master/css-mcp@rc --root /absolute/path/to/project
```

Use an absolute `--root`; review a committed project-scoped config, because that path is machine-specific. Restart the client or open a new session, then ask the agent to call `mastercss_workspace_info` and confirm that the returned root and stylesheet entries belong to this project. A manifest load failure means the project context needs fixing; the server does not silently answer from the preset.

The [MCP tool catalog](/reference/tools/mcp) lists every tool, the built-in prompts such as `debug-missing-css`, and the machine-readable result envelope. When a client cannot use MCP, run the [CLI](/reference/tools/cli) from the project root instead, for example `master-css lint --format json --exit-code never` or `master-css inspect --format json --exit-code never`.

## Give the agent useful context
The official `master-css` skill provides a workflow for building, editing and
debugging UI with project tokens, utilities and native CSS. Install it from your
project directory and choose your coding agent:

```sh
npx skills add master-co/css --skill master-css
```

The [Skills CLI](https://github.com/vercel-labs/skills) supports selecting an agent
such as Codex, Claude Code or Cursor. Check the skill's compatibility metadata
against the installed Master CSS version. The skill reads relevant references
as needed; it does not install Master CSS or register an MCP server for you.
The installer's `--ai` option prints this command without running it.

Ask the agent to inspect the project before it edits, then make one focused change. Use a prompt like this from the project root:

```text name=prompt
You are working in a Master CSS project.

Read the installed package/language/binding versions and project manifest first. Use documentation that matches those versions.
Documentation: https://rc.css.master.co

Before editing, inspect the framework, package manager, CSS entry, theme tokens, component classes, nearby UI patterns, and available validation commands.

When styling markup:
- use valid Master CSS syntax
- prefer existing theme tokens and component classes
- use full native property names for direct declarations and canonical token families for project vocabulary
- do not invent Master CSS APIs, directives, package names, or Tailwind-style syntax
- keep semantic HTML and accessibility behavior unchanged
- explain any value that should become a shared token

Work in a small batch. After editing, show the changed files, explain the styling decisions, and run the relevant formatter, lint, type-check, test, or build command when available.
```

When reading an MCP class inspection, check `matchStatus`, `cssSyntaxStatus`, `cssValueStatus` and `browserSupport` separately: an unknown value is not a failed match, and `not-checked` browser support is not verified support.

When a class spelling is uncertain, the [CLI](/guide/installation/cli) can suggest
classes from an isolated CSS declaration block without an MCP connection. Run
the project's installed version from the app root:

```bash name=Terminal
master-css suggest 'display:flex; align-items:center; padding:16px; gap:1rem;'
```

Read `result.classes`, `result.remainingCss`, `validation` and `diagnostics` in the
JSON response. Check `manifest.entries` for the expected CSS entry; an empty list
means the preset was used. Use `--cwd` to select another project root or `--stdin`
to read declarations from standard input. See the [command contract](/reference/tools/cli#suggest)
for exit statuses and preserved blocks. If your installed CLI lacks `suggest`,
keep using its available checks instead of mixing package versions.

With MCP connected, `mastercss_suggest_classes` accepts the same declaration block:

```json name=tool-input
{
  "declarations": "display:flex; align-items:center; padding:16px; gap:1rem;"
}
```

With the default preset, this proposes `flex items-center p(16) (gap:1rem)`.
Project definitions can change those suggestions. The result includes generated
CSS, separate value-validation statuses, and `remainingCss` for blocks that need
to stay in native CSS. The tool preserves an entire uncertain block, including
duplicate declarations and potentially overlapping properties. It does not edit
files or convert a stylesheet's selectors.

Review the cascade before applying a suggestion: moving a declaration from a
selector or inline style into a utility can change which rule wins. The tool's
declaration check does not verify surrounding styles or browser rendering.

## Preview fixes safely \{#safe-write-previews\}
Read-only tools never write files. A fix goes through two calls, so the agent can show you the diff first:

1. `mastercss_preview_fixes` or `mastercss_preview_directive_format` returns a diff and a confirmation token without touching the workspace.
2. After you review the diff, `mastercss_apply_preview` writes it, but only if the token is valid, every path stays inside the workspace and each file still matches the hash it had at preview time.

For example, a class-order preview for one file:

```json name=mastercss_preview_fixes
{
  "mode": "lint-fixes",
  "patterns": ["src/button.html"],
  "rules": "sort-classes"
}
```

If a file changes after the preview, applying it fails instead of overwriting newer work. Tokens belong to one running server and expire after `--preview-ttl` milliseconds (300000 by default); a restart or an applied preview requires a new one.

## Review the second change
A first draft that looks right does not show what the next edit will affect. Before changing a shared definition such as `--color-brand`, save a project snapshot, then compare after editing, even when markup has not changed:

```bash name=Terminal
master-css inspect --snapshot > before.json
master-css inspect --compare before.json > impact.json
```

`impact.json` lists changed definitions, known class consumers and files, before/after generated rules, native stylesheet references and output delivery. Read its `coverage` even when nothing changed: dynamic sources, remote content and final browser behavior are not exhaustively checked. In MCP, call `mastercss_scan_project` with `includeSnapshot: true` before and after, and pass both snapshots to `mastercss_css_compare`.

For native component CSS, inspect token references across the managed stylesheet graph. Route and component stylesheets imported from JavaScript are outside that graph; name them as source paths:

```bash name=Terminal
master-css inspect --design-system --design-system-options design-system.options.json "app/**/*.css"
```

The report lists each `var()` token reference with its source range, selector and at-rule ancestry, importers and shared-prefix collisions. The optional [options file](/reference/tools/cli#design-system-options) adds token descriptions, deprecations with suggested replacements, and a raw-value policy for selected properties; the same object is accepted by `mastercss_scan_project.designSystem`, with route stylesheets in `routeStylesheets`, and the [Language Service](/guide/language-service) `designSystem` setting. These reports are authored-syntax evidence: check affected layouts and states in the browser.
