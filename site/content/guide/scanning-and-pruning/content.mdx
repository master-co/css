## Overview [sr-only]
Make class names available to static builds without making changing values into new classes. Write complete alternatives, use CSS variables for continuous values, and adjust source discovery only when an input falls outside the integration’s normal scope. Native CSS removal has its own [delivery workflow](/guide/optimizing-css-delivery#native-pruning).

## Keep complete classes in source

The scanner reads source text; it does not run your application. When a component selects a status color, write each complete class:

```js
const className = error ? 'bg-red-60' : 'bg-green-60'
```

For static extraction, fragments such as `'bg-' + tone` do not supply the complete result. Use a finite map when several states select a class:

```js
const statusClasses = { error: 'bg-red-60', success: 'bg-green-60' }
const className = statusClasses[status]
```

The scanner can find both alternatives without executing this lookup. Runtime and progressive rendering can generate new valid utility names first known in the browser; complete source strings are a static scanning requirement, not a ban on dynamic utilities. See [Rendering modes](/guide/rendering-modes#comparisons) for that choice.

## Keep changing values out of class names

Suppose a heading's size comes from an editor control. Keep its class complete and change the custom property on the element:

```html
<h1 id="headline" class="(font-size:var(--headline-size))" style="--headline-size: 2rem">
  Launch notes
</h1>
```

```js
document.getElementById('headline').style.setProperty('--headline-size', '3rem')
```

<Class2CSS classes={'(font-size:var(--headline-size))'} />

After a static build, run the JavaScript in the browser console. The heading grows without adding a class or generating a new rule. A local custom property needs no `@theme` registration or Master CSS runtime. If a class name itself first exists after startup, use [runtime or progressive rendering](/guide/rendering-modes#comparisons).

## Include sources outside normal discovery

Start with your integration or CLI’s ordinary source discovery. If a shared component directory is outside that scope, add an explicit source in the stylesheet that owns the scan. Paths are relative to the stylesheet:

```css name=src/style.css
@import '@master/css';
@source "../shared/**/*.tsx";
@source not "../shared/**/*.test.tsx";
```

This example includes a sibling `shared/` directory and excludes its tests. Keep the pattern as narrow as the required inputs. `@source` supplies class candidates; it does not import a stylesheet or decide cascade precedence. Do not add the whole repository merely because one component is missing.

For a bounded set of utility names supplied by external content, list the complete candidates:

```css
@safelist "bg-red-60" "bg-green-60";
```

A safelist makes these candidates available to generation; it does not add classes to elements or make an invalid name valid. Use variables for unbounded values instead of trying to enumerate them. [`@blocklist`](/reference/directives/scanning#blocklist) excludes candidates; inspect that policy when a discovered class still produces no CSS.

See [Scanning directives](/reference/directives/scanning) for path patterns, candidate filters and their precedence. Keep the distinction between a source file that was never read and a candidate removed by policy.

## Find why a style is missing

1. Inspect the complete class against the active project manifest with the [class inspection tool](/reference/tools/mcp#mastercss_inspect_class).
2. Confirm the source file is part of the scan. Ordinary app files use integration or CLI defaults; add [`@source`](/reference/directives/scanning) only for an explicit exception.
3. Check candidate policy. `@source not` can exclude a file, and `@blocklist` can remove a class. Use `@safelist` for a bounded set of known external classes.
4. If the rule was generated, check that its stylesheet is loaded on this page. If it is loaded, inspect selector matching and the winning cascade before changing source discovery.
5. For a missing native rule, follow the [native pruning checks](/guide/optimizing-css-delivery#native-pruning), including external classes and late states. Runtime utility generation cannot recreate an arbitrary removed native selector.

See [Extraction](/reference/rules/extraction) for source boundaries, candidate scanning and validation.

## Continue to native CSS delivery

### Prune unused native CSS \{#prune-native-css\}

Native CSS is preserved by default. To remove unused native class rules, follow [Prune only a known usage set](/guide/optimizing-css-delivery#native-pruning). It covers file opt-in, package boundaries, retained states and keyframe dependencies after delivery ownership is established.

### Preserve a vendor stylesheet \{#preserve-native-css\}

For externally supplied classes, choose a finite safelist or preserve the owning native file. [Keep external and uncertain sources safe](/guide/optimizing-css-delivery#keep-external-and-uncertain-sources-safe) contains the examples and policy limits.

### Verify the output \{#verify-pruning\}

A directive in source does not prove that the integration supplied a usage set. [Verify the pruning step independently](/guide/optimizing-css-delivery#verify-the-pruning-step-independently) provides the reproducible CLI check and explains what it establishes.
