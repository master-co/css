<a id="how-layers-control-the-cascade"></a>

Master CSS emits generated style rules into `utilities` unless a class explicitly selects another supported layer. Managed theme declarations use `theme`. Native CSS keeps its authored layer, including native rules that expand a mixin with `@apply`.

This page defines layer ownership and generated rule ordering. For a component override and a DevTools diagnosis workflow, see [Cascade layers in Guide](/guide/cascade-layers).

## Establishing the order \{#establishing-the-order\}

The base stylesheet, exposed as `@master/css/base.css` and included by the full `@master/css` import, declares:

```css
@layer theme, base, defaults, components, utilities;
```

Load it before other rules establish these layers. CSS determines layer order by first appearance; a later order statement cannot rearrange layers already established. Generated layer blocks do not insert this statement themselves.

### Normal and important declarations \{#normal-and-important-declarations\}

For competing normal declarations in these layers, `utilities` has the highest priority and `theme` the lowest. Normal unlayered author rules take precedence over all of them. `!important` reverses the order between layers and places important layered rules above important unlayered rules. This comparison is within author stylesheets; it is not the complete cascade across origins, inline styles, animations or transitions. See [CSS layer ordering](https://www.w3.org/TR/css-cascade-5/#layer-order).

<ReferenceIllustration id="layer-precedence" />

Layer precedence is considered before selector specificity. A more specific component selector therefore cannot defeat a normal utility declaration merely through specificity. Between declarations in the same layer, the remaining cascade criteria still matter; see [selector specificity](/reference/rules/selectors#specificity).

## Layer ownership \{#the-five-layers\}

| Layer | Generated content | Native CSS convention |
| --- | --- | --- |
| `theme` | Retained managed token declarations under `:root, :host` | Token defaults |
| `base` | Classes with `@layer(base)` | Normalization and document baselines |
| `defaults` | Classes with `@layer(defaults)` | Broad project or content defaults |
| `components` | Classes with `@layer(components)` | Reusable product classes |
| `utilities` | Ordinary utilities, recipes and native declaration classes; explicit `@layer(utilities)` | Local utility rules |

The native CSS column describes intended responsibilities, not a restriction on which properties CSS permits in a layer. `defaults` is a project layer, not the browser's user-agent stylesheet. Token dependency delivery is covered by [Variables and modes](/reference/rules/modes#variable-lifecycle).

## Selecting a generated layer \{#layer-checklist\}

The class suffix accepts exactly four layer names:

```txt
@layer(base)
@layer(defaults)
@layer(components)
@layer(utilities)
```

It selects the layer for the entire generated class. It does not create a sublayer or move the theme variables that class depends on. Place it with the other suffixes, before a trailing `!`.

| Form | Result |
| --- | --- |
| `block@layer(defaults)` | The display rule goes into `defaults` |
| `block@layer(base)@layer(base)` | One base-layer rule; repeating the same choice is allowed |
| `block@layer(base)@layer(utilities)` | `CLASS_SYNTAX_ERROR`: a class cannot select different layers |
| `block@layer(theme)` | `UNKNOWN_CONDITION`: `theme` is not a generated style-layer target |
| `block@layer(custom)` | `UNKNOWN_CONDITION`: arbitrary native layer names are not class suffix targets |

Use native `@layer` syntax for project-specific layers and sublayers. Their order follows native CSS; the class suffix does not register new layer names.

## Native rules and managed utilities \{#native-rules-and-managed-utilities\}

<a id="a-complete-flow"></a>
<a id="writing-regular-css"></a>

A native class inside `@layer components` remains native CSS. It is delivered by default and follows native source order within that layer; it does not gain Master selector or condition suffixes. [`@prune native`](/reference/directives/pruning) controls whether unused native selectors may be removed.

<a id="utilities-can-override-components"></a>

In this example `.btn` declares `inline-flex`, while `flex` generates a normal utility declaration. With the base order established, the button uses `display: flex`:

<ConfiguredExample source={'@layer components {\n  .btn { display: inline-flex; }\n}'} classes={['btn', 'flex']} element="button" label="Save" />

An on-demand `@utility` instead registers a managed class. Its ordinary output belongs to `utilities`, but a suffix can select another supported layer:

<ConfiguredExample source={'@utility flow {\n  display: grid;\n  gap: var(--spacing-md);\n}'} classes={['flow@layer(defaults)']} />

For utility definitions and native preservation, see [Utilities and mixins](/reference/directives/definitions).

### Mixin expansion keeps the surrounding layer \{#mixin-expansion-keeps-the-surrounding-layer\}

An `@apply` inside a native rule expands declarations where it appears. It does not move that rule into `utilities`:

<ConfiguredExample source={'@mixin --inset { padding: 1.5rem; }\n@layer components {\n  .card { @apply --inset; }\n}'} classes={['card', 'p(8)']} />

With the base order established, the utility's `8px` padding wins over the component's `1.5rem`. Without an enclosing layer, the native `.card` rule would remain unlayered and its normal padding would take precedence over the normal utility.

Keep layer blocks outside mixin bodies and `@apply` contents; those positions do not accept them. A layer selects ownership of the whole generated rule, rather than wrapping a fragment of declarations.

## Priority within a layer \{#priority-matrix\}

HTML class order does not choose the winner. Master CSS gives generated rules a stable order; the browser then applies the cascade to matching declarations. Within comparable layer, selector and condition contexts, generated rules are ordered as follows:

1. Recipes with multiple declarations or inner selectors and conditions.
2. Single-declaration utilities, including fixed, token-backed and direct-value utilities.
3. Native declaration classes.

Single-declaration utilities sort by property family and coverage: a side or axis follows the whole family. For the same property and scope, named token values precede direct values. Importance, selector specificity and conditions still participate; a direct value does not universally defeat a token in another scope or layer.

The examples below use the preset, the base layer statement and a `16px` root font size. Competing declarations target the same element and their conditions match.

| Competing classes or rules | Result | Reason |
| --- | --- | --- |
| `p-md p(8)`, in either order | `padding: 8px` | Direct value follows a token in the same property and scope |
| `p(8) (padding:2rem)`, in either order | `padding: 2rem` | Native declaration follows a single-declaration utility |
| `m-md mt(0)`, in either order | Top margin `0`; other margins `1rem` | Side follows the whole margin family |
| `b(2) bt(0) b-solid b-red-60` | Top width `0`; other widths `2px`; solid red border | Width, style and color are independent families |
| `p-md! p(8)` | `padding: 1rem` | Importance precedes value-source ordering |
| `p-md! p(8)!` | `padding: 8px` | Equal importance; direct value follows token |
| `p(8)@layer(base) p(12)` | `padding: 12px` | Normal utilities outrank base |
| `p(8)@layer(base)! p(12)!` | `padding: 8px` | Important declarations reverse layer precedence |
| Unlayered `.outside { padding: 32px; }` and `p(8)` | `padding: 32px` | Normal unlayered declaration outranks layered declaration |
| Component-layer `padding: 24px !important` and `p(8)!` | `padding: 24px` | Earlier layer wins between important declarations |

Native rules in a layer retain their authored order; the generated-utility ordering above does not reorder those rules. Inspect the emitted CSS when declarations overlap, and use [Code linting](/guide/code-linting#no-conflicting-classes) to catch conflicting classes during authoring.
