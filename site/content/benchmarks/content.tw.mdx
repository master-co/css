## 概覽 [sr-only] \{#overview\}
這些測量先回答兩個問題：文件頁面傳遞的 CSS 有多少符合該頁，以及相同 UI 使用 Master CSS 與 Tailwind CSS 時，各會生成多少 CSS。技術附錄涵蓋建置時間、Chromium 對 CSS 規模的反應，以及各種 Master CSS 渲染模式的成本。將結果套用到其他應用程式前，請先確認各節的條件與限制。

快照於 2026 年 11 月 4 日，在同一台機器（Apple M5 Max、macOS）上使用 Chromium 156 記錄。Master CSS 套件建置自修訂版 `add10eec6`。瀏覽器生命週期快照來自當天較早記錄的 `3fc239c6c`；`add10eec6` 修改編譯器與靜態建置主機，沒有修改執行階段、預設集或引擎。Master CSS 文件頁面取自同一份工作目錄的正式建置，其他文件網站則於同日擷取公開頁面。

## 文件頁面 CSS \{#page-css-size\}
回答的問題：從各文件頁面初始 HTML 找到的行內 style 內容與連結樣式表有多大？其中多少樣式規則符合該頁？

  <figcaption>每站五個文件頁面。符合的樣式規則，其選擇器會在 1280 × 800 檢視區中符合已載入頁面的某個元素。</figcaption>
</figure>

<figure>
  <BenchmarkChart chart={PageCSSSiteTable} />
  <figcaption>以相同方式測量 Master CSS 網站 sitemap 列出的每個文件頁面。</figcaption>
</figure>

Master CSS 文件頁面結合兩種 CSS。每頁的 `style#master-css` 內容保有該頁使用的 utility，所列頁面這部分小於 1 kB。連結樣式表包含網站設計系統元件、預設集基礎與其參照的 token，佔了大多數位元組。每份連結樣式表屬於一個元件，且會完整抵達，因此使用較多元件的頁面連結更多檔案，各頁總量也不同。只渲染元件部分內容的頁面，例如尚未開啟的搜尋對話框或少量文章元件，仍會收到該元件全部規則，這是多數不符合規則的來源。其他網站中，有幾站會在每頁傳遞相同樣式表。

符合規則的比例衡量頁面 CSS 與該頁的貼合程度，與大小無關。將選擇器的狀態偽類別與偽元素移除後，若能符合載入後的元素，就計為符合；其他檢視區、配色或後續互動的規則，只有在元素不存在時才計為不符合。此比例反映各站自己的樣式表，不單是 CSS 框架的特性。

限制：這些是蒐集到的 CSS 內容大小，不是瀏覽器傳輸或時間測量。蒐集器不追蹤 CSS 匯入相依圖，也不計 JavaScript 注入樣式。完整回應壓縮、快取重用、標頭、CDN 行為、字體、圖片與應用程式執行階段工作，都不在比較範圍內。各站 CSS 也反映自身設計與建置選擇，因此此樣本不能單獨隔離 CSS 框架成本；下方靜態 fixtures 才以相同 UI 比較框架。

## 相較七月快照的變更 \{#changes\}
前次快照日期為 2026 年 7 月 1 日，當時修訂版的引擎之後已移至 Rust，類別語法也已改變。為區分程式碼變更與機器、瀏覽器、基準測試框架的影響，七月修訂版 `cd5a3972a` 已重新建置，並在與目前測量相同的機器及 Chromium 版本上，重新執行該修訂版自己的測試執行器。正式建置在兩份工作目錄間交替執行三次，讓機器背景負載對雙方的影響相近。

重新執行後，七月的靜態 CSS 輸出逐位元組一致，因此較早的數據對當時修訂版有效。目前 fixtures 使用現行類別語法表達相同渲染值，其中每個類別都會生成 CSS，並通過 CLI 的 `--strict` 模式。

<figure>
  <BenchmarkChart chart={RevisionComparisonTable} />
  <figcaption>各修訂版自己的執行器，在相同機器與 Chromium 版本上的中位數。雙方正式建置使用相同 Node.js 版本；每個建置中位數彙整三輪交替執行、共 15 次命令。</figcaption>
</figure>

在此機器上，目前修訂版啟動瀏覽器執行階段較快，也用較少資料為漸進式頁面完成 hydration，但下載的執行階段更大，冷啟動正式環境建置命令耗時更久。`docs` fixture 的生成 CSS 約增加 5%，與七月一樣以單一檔案抵達。每份工作目錄安裝自己的 Tailwind CSS 與 Vite 版本，因此 Tailwind CSS 對照組同時反映升級及各次執行雜訊。

兩個修訂版中，各模式（包含 Tailwind CSS）的互動就緒時間都差不多。限制來自測試框架等待影格，不是 Master CSS 工作，因此讀值會以約一個影格（17 ms）為級距變動；七月修訂版較低的 Tailwind CSS 讀值，就是這樣的一級差異。

## 技術附錄 \{#current-results\}
這些測試組說明上述結果背後的成本：正式環境建置命令、Chromium 對 CSS 規模的反應，以及每種 Master CSS 渲染模式在瀏覽器傳送與執行的內容。選擇渲染模式或診斷建置時間時，可閱讀這些資料。

### 核心假說 \{#core-hypothesis\}
傳遞方面的問題是：載入較少 CSS 規則所節省的瀏覽器工作，能否抵銷執行階段生成規則的成本。請比較完整頁面生命週期：初始載入、後續互動與長時間工作階段清理。

執行階段與漸進式渲染增加 JavaScript 工作，從觀察到的類別生成規則。這組類別若少於從靜態來源推得的集合，就可能減少初始 CSS 與 CSSOM 規則量。減少的量能否抵銷啟動與變動處理，取決於工作負載。Tailwind CSS 在此作為零執行階段的靜態 CSS 對照：它不提供等效的執行階段實作，但能代表這項取捨中較大靜態 CSS 的一側。

目前證據應視為方向性結果。實測 fixtures 中，若執行階段／漸進式模式減少的 CSSOM／規則量與樣式重新計算，足以抵銷執行階段啟動、觀察與變動工作，就能支持假說；這不代表每個應用程式都會更快。

這些測試組沒有把選擇器比對直接測量為穩定的 Chromium 指標，而是從傳遞的選擇器、CSSOM 規則數、執行階段生成規則數，以及追蹤紀錄中的樣式重新計算推論。

### 如何閱讀結果 \{#how-to-read-these-results\}
基準測試在回答明確、範圍狹窄的問題時才有用。評估這項傳遞取捨時，請依下列順序閱讀測量：

1. 頁面 CSS 與靜態 CSS 輸出顯示頁面或靜態設定傳遞多少位元組、檔案、選擇器、宣告與規則。
2. 瀏覽器 CSS 成本校準 DOM 固定、CSS 規則量增長時，Chromium 的反應。
3. 傳遞模式顯示 Master 靜態、執行階段、漸進式，以及 Tailwind 靜態模式在首次載入傳送與執行的內容。
4. 互動成本測量載入後 DOM 與類別變更，包含執行階段規則工作。
5. 瀏覽器生命週期證據結合長時間工作階段的瀏覽器工作、CSSOM／規則量與執行階段檢測資料。

各圖表是針對實測 fixture 與命令的證據；套用到其他應用程式前，請先與完整表格及已提交快照交叉比較。

| 問題 | 主要證據 |
|----------|------------------|
| 從各文件頁面找到的 CSS 內容有多大，頁面使用多少？ | 頁面 CSS 大小快照 |
| 相同 UI 生成的靜態 CSS 有多大？ | 靜態 CSS 輸出與 CSS 結構快照 |
| 正式環境建置命令耗時多久？ | 正式建置 |
| Master CSS 建置時間花在哪裡？ | 建置路徑診斷 |
| CSS 規則量對 Chromium 有何成本？ | 瀏覽器 CSS 成本校準 |
| 各傳遞模式首次載入會傳送與執行什麼？ | Master CSS 傳遞模式 |
| 載入後，類別與 DOM 改變時會發生什麼？ | 互動成本 |
| 執行階段工作會改變長時間工作階段的瀏覽器成本嗎？ | 瀏覽器生命週期證據 |
| 修訂版之間改變了什麼？ | 修訂版比較 |

Tailwind CSS 不是等效執行階段實作的比較對象。在執行階段導向的測試組中，它是靜態瀏覽器對照基準，代表假說中零執行階段、較大靜態 CSS 的一側。

數字較低不代表在所有情境都較好。較小 CSS 產物可能將工作轉移到執行階段，較快冷啟動命令可能掩蓋較少的有效輸出，本地 Chromium 追蹤也不能取代真實正式環境遙測。

測量時間時也要檢查正確性：fixture 有渲染預期 UI，較小或較快的結果才有用。測試組有記錄時，表格會包含計算樣式與漸進式採用檢查。
