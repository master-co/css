## 개요 [sr-only] \{#overview\}
이 측정은 먼저 두 질문에 답합니다. 문서 페이지가 전달한 CSS 중 얼마나 페이지에 일치하는지, 같은 UI에서 Master CSS와 Tailwind CSS가 각각 얼마나 CSS를 생성하는지입니다. 기술 부록에서는 빌드 시간, CSS 규모에 대한 Chromium 반응, 각 Master CSS 렌더링 모드 비용을 다룹니다. 다른 앱에 결과를 적용하기 전에 각 절의 조건과 한계를 확인하세요.

스냅샷은 2026년 11월 4일 같은 기기(Apple M5 Max, macOS)에서 Chromium 156으로 기록했습니다. Master CSS 패키지는 리비전 `add10eec6`에서 빌드했습니다. 브라우저 수명 주기 스냅샷은 같은 날 앞서 기록한 `3fc239c6c`를 사용합니다. `add10eec6`는 컴파일러와 정적 빌드 호스트를 변경하며 런타임, 프리셋, 엔진은 변경하지 않습니다. Master CSS 문서는 같은 체크아웃의 프로덕션 빌드에서 측정했고 다른 문서 사이트는 같은 날 공개 페이지를 가져왔습니다.

## 문서 페이지 CSS \{#page-css-size\}
검증 질문: 각 문서 페이지의 초기 HTML에서 찾은 인라인 style 본문과 연결 스타일시트의 크기는 얼마이며 몇 개의 스타일 규칙이 페이지에 일치하는가?

<PageCSSSizeBenchmark />

차트는 각 사이트의 표시 페이지에서 인라인 `style` 본문과 연결 스타일시트를 합산합니다. Brotli 보기에서는 각 본문을 따로 압축합니다. 한 페이지가 사이트를 잘못 대표할 수 있어 표에는 사이트마다 문서 페이지 4개를 추가하고 범위를 표시합니다.

<figure>
  <BenchmarkChart chart={PageCSSSampleTable} />
  <figcaption>사이트마다 문서 페이지 5개를 측정합니다. 일치한 스타일 규칙은 1280 × 800 뷰포트에서 로드된 페이지 요소에 선택자가 일치하는 규칙입니다.</figcaption>
</figure>

<figure>
  <BenchmarkChart chart={PageCSSSiteTable} />
  <figcaption>Master CSS 사이트맵에 나열된 모든 문서 페이지를 같은 방식으로 측정합니다.</figcaption>
</figure>

Master CSS 문서 페이지는 두 종류의 CSS를 결합합니다. 페이지별 `style#master-css` 본문은 해당 페이지가 쓰는 유틸리티를 담으며 표시된 페이지에서는 1 kB 미만입니다. 연결 스타일시트는 사이트 디자인 시스템 컴포넌트, 프리셋 기반 스타일, 참조 토큰을 담고 대부분의 바이트를 차지합니다. 각 스타일시트는 컴포넌트에 속하며 전체가 전달되므로 컴포넌트가 많은 페이지는 더 많은 파일을 연결하고 총량도 페이지마다 다릅니다. 닫힌 검색 대화상자나 일부 글 컴포넌트처럼 컴포넌트 일부만 렌더링해도 모든 규칙을 받습니다. 이것이 일치하지 않는 규칙 대부분의 출처입니다. 다른 사이트 중 일부는 모든 페이지에 같은 스타일시트를 전달합니다.

일치 규칙은 크기와 별개로 페이지 CSS가 해당 페이지에 얼마나 정확히 맞는지 측정합니다. 상태 의사 클래스와 의사 요소를 제외한 선택자가 로드 후 요소에 일치하면 계산합니다. 다른 뷰포트, 색상 모드, 이후 상호작용 규칙도 대상 요소가 없을 때만 불일치로 계산합니다. 이 비율은 CSS 프레임워크만이 아닌 각 사이트 스타일시트의 특성입니다.

한계: 수집된 CSS 본문 크기이며 브라우저 전송량이나 시간 측정이 아닙니다. 수집기는 CSS import 그래프를 따라가거나 JavaScript 삽입 스타일을 계산하지 않습니다. 전체 응답 압축, 캐시 재사용, 헤더, CDN 동작, 글꼴, 이미지, 앱 런타임 작업은 비교에서 제외됩니다. 각 사이트 CSS는 자체 설계와 빌드 선택도 반영하므로 이 표본은 CSS 프레임워크 비용만 분리하지 않습니다. 아래 정적 픽스처가 같은 UI에서 프레임워크를 비교합니다.

측정한 모든 구성은 CSS 파일 하나를 출력합니다. Master CSS 정적 빌드는 프리셋을 포함해 진입점이 가져온 스타일시트를 인라인으로 합치므로 Tailwind CSS와 마찬가지로 한 요청으로 생성 CSS를 받습니다. 외부 import, 네임스페이스, 자체 import를 가진 파일의 조건부 import를 유지하는 스타일시트는 별도 파일로 남지만 이 픽스처에는 해당 경우가 없습니다.

한계: 브라우저 파싱, 스타일 재계산, 레이아웃, 페인트, 상호작용 비용, watch 모드, HMR은 측정하지 않습니다. 픽스처는 유틸리티 클래스만 사용합니다. [페이지 CSS](#page-css-size) 표본은 직접 작성한 컴포넌트 CSS가 얼마나 더해질 수 있는지 보여 줍니다.

## 7월 스냅샷 이후 변경 \{#changes\}
이전 스냅샷은 2026년 7월 1일의 리비전을 측정했으며 이후 엔진이 Rust로 이동하고 클래스 구문도 바뀌었습니다. 코드 변경을 기기, 브라우저, 벤치마크 하네스 영향과 분리하려고 7월 리비전 `cd5a3972a`를 다시 빌드하고 해당 버전의 러너를 현재 측정과 같은 기기 및 Chromium 빌드에서 다시 실행했습니다. 두 체크아웃의 프로덕션 빌드를 세 차례 교대로 실행해 기기 백그라운드 부하가 양쪽에 비슷하게 영향을 주게 했습니다.

재실행은 7월 정적 CSS 출력을 바이트 단위로 재현했으므로 이전 수치는 당시 리비전에 유효했습니다. 현재 픽스처는 현행 클래스 구문으로 같은 렌더링 값을 나타냅니다. 모든 클래스가 CSS를 생성하고 CLI의 `--strict` 모드를 통과합니다.

<figure>
  <BenchmarkChart chart={RevisionComparisonTable} />
  <figcaption>같은 기기와 Chromium 빌드에서 각 리비전의 자체 러너로 얻은 중앙값입니다. 양쪽 프로덕션 빌드는 같은 Node.js 버전을 사용했으며 각 빌드 중앙값은 세 차례 교대 실행의 명령 15개를 합쳐 계산했습니다.</figcaption>

이 기기에서 현재 리비전은 브라우저 런타임을 더 빨리 시작하고 더 적은 데이터로 점진적 페이지를 하이드레이션합니다. 반면 더 큰 런타임을 다운로드하고 콜드 프로덕션 명령은 더 오래 걸립니다. `docs` 픽스처 생성 CSS는 약 5% 늘었고 7월과 같이 파일 하나로 도착합니다. 각 체크아웃은 자체 Tailwind CSS와 Vite 버전을 설치하므로 Tailwind CSS 대조군에는 업그레이드와 실행 간 잡음도 반영됩니다.

두 리비전 모두 Tailwind CSS를 포함한 각 모드의 상호작용 준비 시간은 거의 같습니다. Master CSS 작업이 아닌 하네스의 프레임 대기가 하한을 정하므로 값은 약 한 프레임(17 ms) 간격으로 움직입니다. 7월 리비전에서 더 낮은 Tailwind CSS 값도 그 한 단계 차이입니다.

## 기술 부록 \{#current-results\}
이 테스트 모음은 앞선 결과의 비용을 설명합니다. 프로덕션 명령, CSS 규모에 대한 Chromium 반응, 각 Master CSS 렌더링 모드가 브라우저에서 전달하고 수행하는 내용입니다. 렌더링 모드를 고르거나 빌드 시간을 진단할 때 참고하세요.

### 핵심 가설 \{#core-hypothesis\}
전달의 질문은 더 적은 CSS 규칙을 로드해 절약한 브라우저 작업이 런타임 규칙 생성 비용을 상쇄할 수 있는지입니다. 초기 로드, 이후 상호작용, 장시간 세션 정리를 포함한 전체 페이지 수명 주기를 비교하세요.

런타임과 점진적 렌더링은 관찰한 클래스에서 규칙을 생성하는 JavaScript 작업을 더합니다. 클래스 집합이 정적 소스에서 얻은 집합보다 작으면 초기 CSS와 CSSOM 규칙량을 줄일 수 있습니다. 이 감소가 시작 및 변경 작업을 상쇄하는지는 워크로드에 달려 있습니다. Tailwind CSS는 런타임 없는 정적 CSS 대조군으로 유용합니다. 런타임 동등 구현은 없지만 이 절충에서 큰 정적 CSS 쪽을 대표합니다.

현재 근거는 방향을 보여 주는 결과로 읽어야 합니다. 측정 픽스처에서 런타임/점진적 모드가 CSSOM·규칙량과 스타일 재계산을 충분히 줄여 런타임 시작, 관찰, 변경 작업을 상쇄한다면 가설을 뒷받침할 수 있습니다. 모든 앱이 더 빨라진다는 뜻은 아닙니다.

이 테스트 모음은 선택자 매칭을 안정적인 Chromium 지표로 직접 측정하지 않습니다. 전달된 선택자, CSSOM 규칙 수, 런타임 생성 규칙 수, 추적에서 얻은 스타일 재계산으로 추론합니다.

### 결과 읽는 방법 \{#how-to-read-these-results\}
벤치마크는 좁고 명확한 질문에 답할 때 유용합니다. 전달 절충을 평가할 때 다음 순서로 측정을 읽으세요:

1. 페이지 CSS와 정적 CSS 출력은 페이지나 정적 구성이 전달하는 바이트, 파일, 선택자, 선언, 규칙 수를 보여 줍니다.
2. 브라우저 CSS 비용은 DOM이 고정되고 CSS 규칙량이 늘 때 Chromium 반응을 보정합니다.
3. 전달 모드는 Master 정적, 런타임, 점진적 및 Tailwind 정적이 초기 로드에서 보내고 수행하는 내용을 보여 줍니다.
4. 상호작용 비용은 런타임 규칙 작업을 포함해 로드 후 DOM과 클래스 변경을 측정합니다.
5. 브라우저 수명 주기 근거는 장시간 세션 브라우저 작업, CSSOM·규칙량, 런타임 계측을 결합합니다.

각 차트는 측정한 픽스처와 명령의 근거로 읽고 다른 앱에 적용하기 전에 전체 표 및 커밋된 스냅샷과 비교하세요.

| 런타임 작업이 장시간 세션 비용을 바꾸는가? | 브라우저 수명 주기 근거 |
| 리비전 사이 무엇이 바뀌었는가? | 리비전 비교 |

Tailwind CSS는 런타임 동등 비교 대상이 아닙니다. 런타임 지향 테스트 모음에서는 가설의 런타임 없음·더 큰 정적 CSS 쪽을 대표하는 정적 브라우저 대조 기준선입니다.

낮은 수치가 모든 상황에서 더 좋은 것은 아닙니다. 작은 CSS 산출물은 작업을 런타임으로 옮길 수 있고 빠른 콜드 명령은 덜 유용한 출력을 숨길 수 있습니다. 로컬 Chromium 추적은 실제 프로덕션 원격 측정을 대체하지 못합니다.

시간과 함께 정확성도 검사하세요. 픽스처가 의도한 UI를 렌더링해야 더 작거나 빠른 결과가 유용합니다. 테스트 모음이 기록한 경우 표에 계산 스타일과 점진적 채택 검사를 포함합니다.

### 브라우저 수명 주기와 장시간 세션 \{#browser-lifecycle-and-inp-style-interactions\}

수명 주기 테스트는 Master CSS 정적, 런타임, 점진적과 Tailwind CSS 정적 대조군을 비교합니다. 아래 차트는 5분 장시간 세션 시나리오를 사용합니다. 각 모드는 **실측 실행이 한 번뿐**입니다. 표본 하나의 중앙값은 그 단일 관찰이며 반복 가능성의 근거가 아닙니다.

표의 경과 시간은 전체 스크립트 세션과 마지막 안정화 프레임을 포함합니다. 원본 지표 이름은 `inp-style-interaction-ms`이지만 이 시나리오에서는 설계상 약 5분입니다. 개별 입력 지연이나 Web Vitals INP를 측정하지 않습니다.
