## Overview [sr-only]
These measurements first answer two questions: how much of the CSS a documentation page delivers matches that page, and how much CSS the same UI generates with Master CSS and with Tailwind CSS. A technical appendix covers build time, Chromium's response to CSS volume and the cost of each Master CSS rendering mode. Check each section's conditions and limits before applying a result to another application.

The snapshots were recorded on November 4, 2026 on one machine (Apple M5 Max, macOS) with Chromium 156. Master CSS packages were built from revision `add10eec6`. The browser lifecycle snapshots come from `3fc239c6c`, recorded earlier that day; `add10eec6` changes the compiler and the static build hosts, not the runtime, the preset or the engine. The Master CSS documentation pages were measured from the production build of the same checkout; the other documentation sites were fetched from their public pages on the same day.

<figure>
  <BenchmarkChart chart={PageCSSSampleTable} />
  <figcaption>Five documentation pages per site. Matched style rules have a selector that matches an element of the loaded page at a 1280 × 800 viewport.</figcaption>
</figure>

<figure>
  <BenchmarkChart chart={PageCSSSiteTable} />
  <figcaption>Every documentation page the Master CSS site lists in its sitemap, measured the same way.</figcaption>
</figure>

The Master CSS documentation pages combine two kinds of CSS. The per-page `style#master-css` body holds the utilities the page uses; on the listed page it is under 1 kB. The linked stylesheets hold the site’s design system components, the preset base and the tokens they reference; they make up most of the bytes. Each linked stylesheet belongs to a component and arrives whole, so pages that use more components link more files and the total varies from page to page. A page that renders only part of a component, such as the closed search dialog or a few of the article components, still receives all of that component’s rules; that is where most of its unmatched rules come from. Several of the other sites deliver the same stylesheet on every page.

Matched rules measure how precisely a page’s CSS fits that page, independently of its size. A rule counts when its selector, without state pseudo-classes and pseudo-elements, matches an element after load; rules for other viewports, color schemes or later interactions count as unmatched only when their element is absent. The share is a property of each site’s own stylesheets, not of the CSS framework alone.

Limits: these are collected CSS body sizes, not browser transfer or timing measurements. The collector does not follow CSS import graphs or count JavaScript-injected styles. Compression of complete responses, cache reuse, headers, CDN behavior, fonts, images and application runtime work are outside the comparison. Each site’s CSS also reflects its own design and build choices, so this sample does not isolate the cost of a CSS framework; the static fixtures below compare frameworks on the same UI.

## Changes since the July snapshots \{#changes\}
The previous snapshots, dated July 1, 2026, measured a revision whose engine has since moved to Rust and whose class syntax has since changed. To separate code changes from the machine, the browser and the benchmark harness, the July revision `cd5a3972a` was rebuilt and its own benchmark runner run again on the same machine and Chromium build as the current measurements. Production builds alternated between the two checkouts three times, so background load on the machine affected both sides alike.

That rerun reproduced the July static CSS output byte for byte, so the earlier figures were valid for their revision. The current fixtures express the same rendered values in the current class syntax; every class in them generates CSS, and the CLI's `--strict` mode accepts them.

<figure>
  <BenchmarkChart chart={RevisionComparisonTable} />
  <figcaption>Medians from each revision's own runner on the same machine and Chromium build. Production builds ran with the same Node.js version on both sides; each build median pools 15 commands from three alternating runs.</figcaption>
</figure>

On this machine, the current revision starts the browser runtime faster and hydrates progressive pages with less data, while downloading a larger runtime and taking longer for a cold production command. Generated CSS for the `docs` fixture grew by about 5% and, as in July, arrives as one file. Each checkout installs its own Tailwind CSS and Vite versions, so the Tailwind CSS controls reflect those upgrades as well as run-to-run noise.

Interaction readiness is about the same for every mode, including Tailwind CSS, on both revisions. It is bounded by the harness's frame waits rather than by Master CSS work, so readings move in steps of about one frame (17 ms); the lower Tailwind CSS reading on the July revision is one such step.

## Technical appendix \{#current-results\}
These suites explain the costs behind the results above: production commands, Chromium's response to CSS volume, and what each Master CSS rendering mode sends and does in the browser. Read them when choosing a rendering mode or diagnosing build time.

### Core hypothesis
The delivery question is whether the browser work saved by loading fewer CSS rules can offset the cost of generating rules at runtime. Compare the whole page lifecycle: initial loading, later interactions and long-session cleanup.

Runtime and progressive rendering add JavaScript work to generate rules from observed classes. When that class set is smaller than a static source-derived set, they can reduce initial CSS and CSSOM rule volume. Whether that reduction offsets startup and mutation work depends on the workload. Tailwind CSS is useful here as a zero-runtime static CSS control: it does not provide a runtime-equivalent implementation, but it does represent the large static CSS side of the tradeoff.

The current evidence should be read as directional. It can support the hypothesis in measured fixtures when runtime/progressive modes reduce CSSOM/rule volume and style recalculation enough to offset runtime bootstrap, observe, and mutation work. It does not establish that every application will be faster.

Selector matching is not directly measured as a stable Chromium metric in these suites. It is inferred from delivered selectors, CSSOM rule count, runtime-generated rule count, and trace-derived style recalculation.

### How to read these results
Benchmarks are useful when they answer a narrow question. Read the measurements in this order when evaluating that delivery tradeoff:

1. Page CSS and static CSS output show how many bytes, files, selectors, declarations, and rules a page or static setup delivers.
2. Browser CSS cost calibrates how Chromium responds when CSS rule volume grows while DOM is fixed.
3. Delivery modes show what Master static, runtime, progressive, and Tailwind static send and do on initial load.
4. Interaction cost measures post-load DOM and class changes, including runtime rule work.
5. Browser lifecycle evidence combines long-session browser work, CSSOM/rule volume, and runtime instrumentation.

Read each chart as evidence for the measured fixture and command, then compare it with the complete table and committed snapshot before applying the result to another app.

| Question | Primary evidence |
|----------|------------------|
| How large are the CSS bodies discovered from each documentation page, and how much of them does the page use? | Page CSS size snapshot |
| How large is generated static CSS for the same UI? | Static CSS output and CSS structure snapshots |
| How long does a production command take? | Production build |
| Where does Master CSS build time go? | Build path diagnostics |
| What does CSS rule volume cost in Chromium? | Browser CSS cost calibration |
| What does each delivery mode send and do on first load? | Master CSS delivery modes |
| What happens after load when classes and DOM change? | Interaction cost |
| Does runtime work change long-session browser cost? | Browser lifecycle evidence |
| What changed between revisions? | Revision comparison |

Tailwind CSS is not a runtime-equivalent comparison. In runtime-oriented suites, it is the static browser-control baseline for the zero-runtime, larger-static-CSS side of the hypothesis.

Lower numbers are not automatically better in every context. A smaller CSS artifact can shift work into runtime, a faster cold command can hide less useful output, and a local Chromium trace does not replace real production telemetry.

Check correctness alongside timing: a smaller or faster result is useful only if the fixture renders the intended UI. The tables include computed-style and progressive-adoption checks where the suite records them.

Interpretation: runtime and progressive modes should be read in two layers: user-visible mutation readiness, then runtime stylesheet work. The rule delta counts rules in the runtime’s public snapshot. Compare runtime mutation work and style recalculation for its CSSOM cost.

Limits: these numbers do not measure route transitions, HMR, dev workflow, CDN behavior, Firefox, WebKit, or public real-world application variance.
