## 概览 [sr-only] \{#overview\}
这些测量先回答两个问题：文档页面交付的 CSS 有多少匹配该页，以及相同 UI 使用 Master CSS 与 Tailwind CSS 时各会生成多少 CSS。技术附录涵盖构建时间、Chromium 对 CSS 规模的反应，以及各种 Master CSS 渲染模式的成本。将结果应用到其他应用前，请先确认各节的条件与限制。

  <BenchmarkChart chart={PageCSSSiteTable} />
  <figcaption>用相同方式测量 Master CSS 网站 sitemap 列出的每个文档页面。</figcaption>

Master CSS 文档页面结合两种 CSS。每页的 `style#master-css` 主体保有该页使用的工具类，所列页面中这部分小于 1 kB。链接样式表包含网站设计系统组件、预设基础样式及其引用的令牌，占了大多数字节。每份链接样式表属于一个组件，并且完整交付，因此使用较多组件的页面会链接更多文件，各页总量也不同。只渲染组件部分内容的页面，例如尚未打开的搜索对话框或少量文章组件，仍会收到该组件全部规则，这是大多数未匹配规则的来源。其他网站中，有几站在每页交付相同样式表。

匹配规则比例衡量页面 CSS 与该页的贴合程度，与大小无关。移除选择器的状态伪类与伪元素后，若能匹配加载后的元素，就计为匹配；其他视口、配色或后续交互的规则，只有在元素不存在时才计为未匹配。此比例反映各站自己的样式表，而不只是 CSS 框架的特性。

限制：这些是收集到的 CSS 主体大小，不是浏览器传输或时间测量。收集器不追踪 CSS 导入依赖图，也不计算 JavaScript 注入样式。完整响应压缩、缓存复用、头部、CDN 行为、字体、图片与应用运行时工作均不在比较范围内。各站 CSS 还反映自身设计与构建选择，因此此样本不能单独隔离 CSS 框架成本；下方静态测试用例才在相同 UI 上比较框架。

## 相较七月快照的变化 \{#changes\}
前次快照日期为 2026 年 7 月 1 日，此后该修订版的引擎已迁至 Rust，类名语法也已改变。为区分代码变化与机器、浏览器、基准测试框架的影响，七月修订版 `cd5a3972a` 已重新构建，并在与当前测量相同的机器及 Chromium 版本上，重新运行该修订版自己的测试执行器。生产构建在两份检出目录间交替执行三次，让机器后台负载对双方的影响相近。

重新运行后，七月的静态 CSS 输出逐字节一致，因此较早的数据对当时修订版有效。当前测试用例使用现行类名语法表达相同渲染值，其中每个类名都会生成 CSS，并通过 CLI 的 `--strict` 模式。

<figure>
  <BenchmarkChart chart={RevisionComparisonTable} />
  <figcaption>各修订版自己的执行器，在相同机器与 Chromium 版本上的中位数。双方生产构建使用相同 Node.js 版本；每个构建中位数汇总三轮交替执行、共 15 次命令。</figcaption>
</figure>

在此机器上，当前修订版启动浏览器运行时更快，也用较少数据为渐进式页面完成水合，但下载的运行时更大，冷启动生产命令耗时更久。`docs` 测试用例的生成 CSS 约增加 5%，与七月一样以单个文件交付。每份检出目录安装自己的 Tailwind CSS 与 Vite 版本，因此 Tailwind CSS 对照组同时反映升级及各次运行噪声。

两个修订版中，各模式（包括 Tailwind CSS）的交互就绪时间都差不多。限制来自测试框架等待帧，而不是 Master CSS 工作，因此读数会以约一帧（17 ms）为步长变化；七月修订版中较低的 Tailwind CSS 读数就是这样的一级差异。

## 技术附录 \{#current-results\}
这些测试组介绍上述结果背后的成本：生产命令、Chromium 对 CSS 规模的反应，以及每种 Master CSS 渲染模式在浏览器中发送与执行的内容。选择渲染模式或诊断构建时间时，可以阅读这些数据。

### 核心假设 \{#core-hypothesis\}
交付方面的问题是：加载较少 CSS 规则所节省的浏览器工作，能否抵消运行时生成规则的成本。请比较完整页面生命周期：初始加载、后续交互与长时间会话清理。

运行时与渐进式渲染会增加 JavaScript 工作，从观察到的类名生成规则。此类名集合若小于从静态源文件得到的集合，就可能减少初始 CSS 与 CSSOM 规则量。减少量能否抵消启动与变化处理，取决于工作负载。Tailwind CSS 在此作为零运行时的静态 CSS 对照：它不提供等效的运行时实现，但能代表这项权衡中较大静态 CSS 的一侧。

当前证据应视为方向性结果。在实测测试用例中，若运行时／渐进式模式减少的 CSSOM／规则量与样式重计算足以抵消运行时启动、观察与变化处理，就能支持假设；这并不代表每个应用都会更快。

这些测试组没有把选择器匹配直接测量为稳定的 Chromium 指标，而是根据交付的选择器、CSSOM 规则数、运行时生成规则数，以及跟踪记录中的样式重计算推断。

### 如何阅读结果 \{#how-to-read-these-results\}
基准测试在回答明确且范围狭窄的问题时才有用。评估这项交付权衡时，请按以下顺序阅读测量结果：

1. 页面 CSS 与静态 CSS 输出显示页面或静态配置交付多少字节、文件、选择器、声明与规则。
2. 浏览器 CSS 成本校准 DOM 固定、CSS 规则量增长时 Chromium 的反应。
3. 交付模式显示 Master 静态、运行时、渐进式，以及 Tailwind 静态模式在首次加载时发送与执行的内容。
4. 交互成本测量加载后 DOM 与类名变化，包括运行时规则处理。
5. 浏览器生命周期证据结合长时间会话的浏览器工作、CSSOM／规则量与运行时检测数据。

各图表是针对实测测试用例与命令的证据；应用到其他应用前，请先与完整表格及已提交快照交叉比较。

| 修订版之间改变了什么？ | 修订版比较 |

Tailwind CSS 不是等效运行时实现的比较对象。在面向运行时的测试组中，它是静态浏览器对照基线，代表假设中零运行时、较大静态 CSS 的一侧。

数值较低并不代表在所有情境下都更好。较小 CSS 产物可能把工作转移到运行时，较快冷启动命令可能掩盖较少的有效输出，本地 Chromium 跟踪也不能替代真实生产环境遥测。

测量时间时还应检查正确性：测试用例渲染了预期 UI，更小或更快的结果才有用。测试组有记录时，表格会包含计算样式与渐进式采用检查。

限制：这些数值仅测量本地测试用例的初始加载，加载后变化由交互测试组处理。Master 静态与 Tailwind 静态各加载一份 CLI 生成样式表，根据等效测试用例意图构建，而不是相同类名字符串。运行时与渐进式页面加载自包含的全局运行时包；打包器集成可以加载更小的渐进式入口，其测量见[运行时大小契约](https://github.com/master-co/css/blob/rc/.ai/contracts/runtime-bundle-size.json)。各模式启动方式请参阅[渲染模式](/reference/packages#css-runtime)。
