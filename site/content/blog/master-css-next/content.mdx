A component can construct a class name that is absent as a complete string in source. If Next.js renders that component during the build, the final HTML contains the class, even though a source scanner cannot infer it. Progressive Rendering in `@master/css-next` uses that HTML to generate the page's CSS, then lets the Master CSS runtime handle new classes in the browser.

Static Rendering remains the default. Use it when complete class names are visible in source and an ordinary generated stylesheet meets your needs. Choose progressive mode when static or pre-rendered pages need CSS from their final markup and runtime support for later class changes.

**The boundary is build-time HTML.** The adapter processes static and pre-rendered outputs from `next build`. It does not process dynamic SSR responses produced at request time; in progressive mode, those responses rely on the browser runtime for generated rules.

<a id="why-this-release-matters"></a>

## Why final HTML is useful

Next.js's [Adapter API](https://nextjs.org/docs/app/api-reference/config/next-config-js/adapterPath) exposes the completed build output. `@master/css-next` uses its `onBuildComplete` hook to locate static and pre-rendered HTML and pass each document to the Master CSS server renderer.

At that point, the page has already combined its layouts, components, and content into markup. Master CSS can read the class strings in that document without inferring how the application constructed them. This is useful for generated markup and component variants, provided that Next.js emits their HTML during the build.

---

## Progressive Rendering in Next.js

The handoff has three parts:

1. Next.js produces static and pre-rendered HTML during `next build`.
2. Master CSS reads each document and inserts its generated rules in `style#master-css`.
3. The browser runtime tracks classes already covered by the page manifest. An uncovered class starts the engine, which validates and adopts matching rules before generating new ones.

<a id="hydration-manifest-hydration"></a>

<DeliveryFlow name="nextjs" />

### CSS and the runtime handoff

A document with generated rules receives an external page hydration manifest. The style element points to that manifest through `data-master-css-hydration-manifest`, so the runtime can track covered classes while its engine is deferred. When the engine starts, it validates and adopts matching CSSOM rules. The runtime loads its engine when it needs to generate a class outside the page manifest.

The inline CSS is usable before that handoff. The manifest supports continued rule management; it is not required for the browser to apply the CSS already in the document. See [Rendering modes](/guide/rendering-modes) for the full delivery and hydration behavior.

## Install it

Use the [Progressive Rendering installation guide](/guide/installation/nextjs#rendering-modes) for the complete setup. In an existing Next.js App Router project, the official installer selects the integration and mode:

```bash
npm create @master/css@rc -- --framework nextjs --mode progressive --yes
```

The essential configuration is one adapter registration and a loaded CSS entry. Keep your other Next.js options when configuring the adapter:

```ts name=next.config.ts
import type { NextConfig } from 'next'
import withMasterCSS from '@master/css-next'

const nextConfig: NextConfig = {}

export default async () => withMasterCSS(nextConfig, { mode: 'progressive' })
```

Import Master CSS from the global stylesheet your application loads:

```css name=app/globals.css
@import '@master/css';
```

```tsx name=app/layout.tsx
import './globals.css'

export default function RootLayout({ children }: { children: React.ReactNode }) {
  return (
    <html lang="en">
      <body>{children}</body>
    </html>
  )
}
```

Add a page whose initial markup is rendered during the build:

```tsx name=app/page.tsx
export default function Page() {
  return <h1 className="font-6xl">Hello</h1>
}
```

Development uses runtime generation. To inspect the pre-rendered result, build and serve the production app:

```bash
npm run build
npm run start
```

View the page's response source. For this pre-rendered page, `style#master-css` contains the `.font-6xl` rule and the font-size token it uses. The style element also points to a hydration manifest asset. Check the response source rather than only the live DOM, where runtime-generated styles can otherwise hide a missing build-time result.

## Source scanning and rendered classes

Source scanning needs complete class strings. [Tailwind scans source files as plain text](https://tailwindcss.com/docs/detecting-classes-in-source-files); Master CSS static mode has the same practical constraint for constructed class names. An explicit map containing every complete class is suitable when the variants are known in advance.

Progressive Rendering can instead use the class names that appear in the pre-rendered document. Consider this component:

```tsx name=Badge.tsx
export function Badge({ tone }: {
  tone: 'blue' | 'neutral'
}) {
  return (
    <span className={`px-xs py-3xs r-sm bg-${tone}/.1 fg-text-${tone}`}>
      New
    </span>
  )
}
```

Rendering `<Badge tone="blue" />` produces:

```html name=blue.html
<span class="px-xs py-3xs r-sm bg-blue/.1 fg-text-blue">New</span>
```

Rendering `<Badge tone="neutral" />` produces:

```html name=neutral.html
<span class="px-xs py-3xs r-sm bg-neutral/.1 fg-text-neutral">New</span>
```

If either badge is present in the build-time HTML, the adapter generates CSS for that actual class list. The foreground classes resolve to `color: var(--color-text-blue)` and `color: var(--color-text-neutral)` respectively; the background classes use the corresponding color at 10% opacity. A page containing only the blue badge does not need the neutral variant's class rules in its initial generated CSS. If the neutral badge appears later, the runtime can generate its rules.

This choice trades source-based coverage for coverage of rendered HTML plus a browser runtime. Static mode remains appropriate when a finite class map provides all the variants you need.

<a id="what-improves"></a>

## What changes for the page

<a id="faster-first-paint"></a>

### CSS availability

A pre-rendered document carries its generated CSS in the response. Those rules can style the page without waiting for the Master CSS runtime to start. This removes runtime generation as a prerequisite for those styles; it does not establish a measured improvement in first paint. Images, fonts, other stylesheets, and scripts still affect rendering.

### Route-level CSS output

Each document receives the generated class rules needed by its own HTML. Shared native styles still follow the application's stylesheet setup. Pre-rendering does not imply that every style on the page is a generated utility or that all application CSS is unique to a route.

### Runtime flexibility stays available

Client-only components and later class changes remain supported. Progressive mode adds runtime and hydration-manifest delivery, so compare that cost with the simpler static stylesheet when choosing a mode.

<a id="same-authoring-model"></a>

The authoring syntax stays the same. The mode changes when classes are read and how their generated rules reach the page.

---

## Current boundary

A route that only exists as a request-time SSR response has no completed HTML for the build-time adapter to process. Progressive mode does not supply pre-rendered CSS for that response. Test a representative dynamic route separately from pre-rendered pages, especially if styling before JavaScript starts is a requirement.

If another integration already owns Next.js `adapterPath`, the Master CSS integration composes the adapters. Master CSS runs first by default; `adapterOrder: 'external-first'` lets the external adapter process the build output first. Check that integration's output as part of the production build.

<a id="static-rendering"></a>

## When to keep Static Rendering

Use the [default Next.js setup](/guide/installation/nextjs) when source scanning can find your complete class strings. Static mode produces a stylesheet without requiring the Master CSS browser runtime. Verify the selected bundler independently; the [installation guide](/guide/installation/nextjs#verify-the-loaded-configuration) includes the current generated-asset limitation and Webpack build path. Interactive components can still switch among classes already included in that stylesheet.

<a id="a-better-foundation-for-nextjs"></a>

Choose progressive mode for a concrete need: CSS based on final build-time HTML with runtime support for new classes. Verify both a pre-rendered page and any dynamic routes before applying that choice across an application.
