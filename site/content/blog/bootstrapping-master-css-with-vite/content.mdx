A Vite app can know its class names at different times: in source files, in generated HTML, or only after a user interacts with the page. Choose a Master CSS rendering mode based on when that information becomes available.

Start with `static`, the default in `@master/css-vite`, when complete class names are visible in source. It produces ordinary CSS without a Master CSS browser runtime. Use another mode when you need to generate rules from final HTML or interpret new class names in the browser.

## What each mode produces

The same plugin supports four modes. This table describes their production behavior; “runtime” means the Master CSS runtime, not your application's JavaScript.

<div className="overflow-x-auto (min-width:40rem)>figure whitespace-nowrap>figure>table>tbody>tr>td:first-child" role="region" aria-label="Rendering mode comparison" tabIndex={0}>

| Mode | Use it when | CSS output | Master CSS in the browser |
| --- | --- | --- | --- |
| `static` (default) | Complete class names are discoverable in source | A generated stylesheet loaded by the application | No runtime required |
| `runtime` | New class names are created in the browser | Rules generated from connected DOM elements | Runtime generates and manages rules |
| `pre-render` | Emitted HTML contains the classes the page needs | Matching rules inline in `style#master-css` | No runtime; classes absent from the HTML need another CSS source |
| `progressive` | Emitted HTML covers the initial page, and new classes may appear later | Initial rules inline in `style#master-css`, with later rules generated in the browser | Runtime adopts the rendered rules and handles new classes |

</div>

Pre-rendering needs actual page markup. If a client-rendered SPA emits only an empty root element, there are no application classes in that HTML to pre-render. Use static mode for discoverable source classes, or runtime support for classes created later.

## Install it

From an existing Vite project root, run the official installer:

```bash
npm create @master/css@rc -- --framework vite --yes
```

For project creation and framework-specific steps, follow the [Vite installation guide](/guide/installation/vite). The installer adds the integration and configures static mode by default. Keep existing framework plugins when reviewing the generated configuration. A minimal vanilla Vite configuration is:

```js name=vite.config.js
import { defineConfig } from 'vite'
import masterCSS from '@master/css-vite'

export default defineConfig({
  plugins: [masterCSS()]
})
```

The plugin also needs a CSS entry that your application loads. Keep the Master CSS import in that stylesheet. For a vanilla Vite app using `src/style.css` and `src/main.js`, the relevant files are:

```css name=src/style.css
@import '@master/css';
```

```js name=src/main.js
import './style.css'
```

Use your existing entry filenames in a framework app. Adding the import to a stylesheet that the application never loads does not complete the setup.

For a minimal vanilla example, put the markup directly in `index.html`:

```html name=index.html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="UTF-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1.0" />
    <title>Master CSS with Vite</title>
  </head>
  <body>
    <h1 class="m-2xl italic font-5xl font-heavy fg-text-neutral">
      Hello World
    </h1>
    <script type="module" src="/src/main.js"></script>
  </body>
</html>
```

Run `npm run dev`. The heading should be large, heavy, italic, and separated from the page edge. Then run `npm run build`: Vite's output includes CSS for these classes. In the default static mode, those styles remain available with JavaScript disabled because the generated HTML links the stylesheet.

## Choose the right mode

### Static Rendering

Keep `masterCSS()` when the scanner can find the complete classes you use. State changes can still switch among those classes, and CSS variables, selectors, and media queries keep their native browser behavior. A changing interface alone does not require runtime generation.

Constructed strings such as `` `bg-${tone}` `` need care: source scanning cannot infer every completed class. Prefer an explicit map of complete strings for a finite set of variants, or choose a mode that sees the final class names. See [Scanning latent classes](/guide/scanning-and-pruning) for source-scanning controls.

### Runtime

Choose `masterCSS({ mode: 'runtime' })` when the browser must interpret classes that cannot be enumerated during the build, such as classes entered in a visual editor. The plugin injects the runtime; it generates rules as elements enter or change in the DOM.

This makes styling dependent on runtime startup. Account for that JavaScript work when choosing the mode.

### Pre-rendering

Choose `masterCSS({ mode: 'pre-render' })` when the built HTML contains the page's classes and you do not need runtime generation later. The plugin inserts their rules into `style#master-css` without starting a browser runtime.

This is CSS generation from HTML the build already emits. It does not render your framework's client components into HTML. A class introduced only after the page loads will need CSS supplied separately.

### Progressive Rendering

Choose progressive mode when the built HTML is useful on its own but the browser may later introduce new classes. Replace the plugin call in your existing configuration with:

```js
masterCSS({ mode: 'progressive' })
```

The initial HTML carries its generated rules. At startup, the runtime reads a page hydration manifest and tracks covered classes while its engine is deferred. A class outside the manifest starts the engine, which validates and adopts matching rules before generating new ones. This adds runtime and manifest delivery to the page, so use it when that continuation is needed.

The browser can use the inline CSS before the runtime starts. That describes CSS availability; any effect on paint timing depends on the page and needs measurement.

## What the plugin handles

The CSS entry connects your theme, utilities, and native styles to the integration. In static mode, the plugin scans source classes and includes their generated CSS in the application's stylesheet. Modes with runtime support inject the runtime, while modes with pre-rendering process the emitted HTML.

Keep application-specific CSS in the loaded stylesheet and rendering choices in the plugin configuration. The [rendering modes guide](/guide/rendering-modes) covers delivery details and verification for each mode.

## Start with source-visible classes

For an ordinary app with complete class strings in source, start with static mode and verify the generated stylesheet. Move to pre-rendering when final HTML is the useful input, or add runtime support when new classes must be interpreted after the build. The decision follows the application's rendering behavior, and the markup syntax stays the same.
