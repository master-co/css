## From an idea to an interface

An interface begins with decisions. These items belong together. This heading needs more room. This link should respond to a pointer. This layout should change when there is enough space.

Master CSS lets you express those decisions where you build the element. Fixed utilities such as `flex` and `grid` describe familiar CSS behavior. Named values such as `gap-md` and `p-lg` connect an element to your design system. Selectors and conditions attach to the class they qualify, so the relationship remains visible in the markup.

```html
<a class="inline-flex px-md py-xs r-md fg-blue-60 fg-blue-70:hover@sm"
   href="/journal">
  Read the journal
</a>
```

The last class says something precise: use the `blue-70` color token on hover when the `sm` media condition matches. In the supplied preset, `sm` starts at `52.125rem`. The class becomes a CSS selector inside a media query; the browser evaluates the hover state and the query.

<ReleaseIllustration name="anatomy" />

This way of composing styles extends to responsive layouts, container conditions and motion. You can begin with a small vocabulary, then combine the parts as the interface demands. When a value belongs only to one element, a numeric function such as `grow(1)` or a native declaration such as `(aspect-ratio:4/3)` gives that decision an explicit place.

The result stays inspectable. A class leads to a concrete CSS rule, using selectors and properties you can recognize. Shared patterns can move into your stylesheet or your application’s components as the design takes shape, keeping each part of the source focused on the decisions it owns.

A small vocabulary can take you a long way: from arranging one element to expressing the behavior of an entire interface. The [Syntax tutorial](/guide/syntax-tutorial) is a hands-on place to begin.

## A visual language of your own

The first screen is only the beginning. As a project grows, its visual decisions need names that people can share. A surface should feel related to the next surface. Spacing should have a rhythm. Changing the brand color should be a deliberate project decision.

Master CSS includes a foundation of colors, spacing, typography, radii, shadows and motion tokens. You can use that foundation immediately. When your product needs its own vocabulary, define it in CSS with `@theme`.

In Fieldwork, the journal’s accent and story spacing are shared decisions. After the app stylesheet’s `@import '@master/css'`, these definitions connect them to the markup:

<ReleaseExample name="theme" />

`fg-brand` reads `--color-brand`; `p-story` reads `--spacing-story`. The names describe the decisions, while the stylesheet owns their values. Changing the story spacing updates every element that consumes that token. For Fieldwork, a warm accent, white oak and generous insets establish a quiet editorial character. Another publication can take the same foundation in a very different direction.

<ReleaseIllustration name="tokens" />

The color token above uses native `light-dark()`. With the appropriate `color-scheme` enabled, the browser selects its light or dark value. The markup keeps the same class name. The preset also provides semantic surface and text colors that follow the active scheme, so the elements around the accent can change together.

Shared values deserve careful names. Two elements that happen to have equal padding today do not necessarily need to change together tomorrow. Tokens let you encode that judgment rather than scatter the same number throughout the project.

A useful design system gives those judgments a place to live. Master CSS supplies the vocabulary and the connections; your team supplies the taste. [Theme tokens](/guide/theme) and [Color](/guide/colors) show how to shape the foundation around your own work.

## CSS at the heart of the work

A design system also contains patterns: a story link, a navigation item, a dialog, a complete component. Those patterns often deserve their own CSS. Master CSS gives native styles a clear place alongside the classes in your markup.

The preset establishes five cascade layers: `theme`, `base`, `defaults`, `components` and `utilities`. Put a shared component in the components layer, then use a utility when one instance needs a local adjustment.

<ReleaseExample name="component" />

Both links share the same component definition. The second adds `px-lg`, changing its horizontal padding to the preset’s `1.5rem`. For these normal layered declarations, the utilities layer takes precedence over components. You do not need to increase the component’s selector specificity to express that local choice.

<ReleaseIllustration name="layers" />

There are other useful kinds of reuse. An `@utility` definition registers a class for on-demand generation. An `@mixin` defines reusable CSS that `@apply` expands where you need it. Native selectors and keyframes remain part of the stylesheet. Each mechanism has a job, and you can choose it according to what should be shared.

That separation matters as a project gains contributors. A token names a shared value. A component class names a visual pattern. A UI component can share the markup and behavior. Local utilities make an individual instance’s choices visible. The result is a system that can grow without forcing every decision into the same abstraction.

The CSS knowledge you bring to the project continues to be useful as it grows. [Reusing styles](/guide/reusing-styles) explores the choices; [Cascade layers](/guide/cascade-layers) explains the ordering rules, including important declarations and unlayered styles.

## Choose how your CSS reaches the page

The same authoring model can serve very different applications. A publication may know all its classes at build time. A visual editor may introduce new classes after deployment. A pre-rendered page may need its initial CSS immediately and still allow new styles later.

Master CSS provides a delivery path for each of those situations.

**Static rendering is the default.** The integration scans complete class names in your source and generates a stylesheet. The browser receives ordinary CSS, without a Master CSS runtime or engine. An interactive interface can still switch among those known classes, respond to selectors and media queries, or update CSS custom properties.

**Progressive rendering connects rendered HTML to later browser generation.** A supported build or server rendering path generates the initial rules from the HTML and includes them in the page. With valid pre-rendered CSS and its hydration manifest, the default runtime can defer its engine until a class outside the page’s covered set appears. The initial styles are already available to the browser.

**Runtime rendering generates rules as classes appear in the browser.** That is useful when a playground, editor or deployed content can introduce class names that were unknown when the application was built. It brings browser-side generation and its associated JavaScript cost.

<ReleaseIllustration name="delivery" />

For Fieldwork’s published journal, static rendering is a natural starting point. If the project later grows a visual editor that accepts new class names, that editor has a different requirement. The choice follows when the application knows its classes.

<details>
<summary>Rendering boundaries to keep in view</summary>

The Next.js progressive adapter processes static and pre-rendered HTML from the build; it does not pre-render CSS for dynamic request-time SSR responses. Those responses rely on the browser runtime in that mode. Source scanning also does not evaluate arbitrary string interpolation. The [Rendering modes](/guide/rendering-modes) guide explains these boundaries and how to verify the response your application delivers.

</details>

Underneath these paths, Rust owns the core semantics, while a JavaScript engine executes compiled programs in the browser. The browser engine is checked against the Rust implementation for matching output. This gives the project a common behavioral foundation while allowing each environment to do its own work.

You can begin with the simplest path that meets your application’s needs, with room for a different path when the project asks for it.

## Your project, understood by your tools

A styling language becomes more useful when the tools around it can answer concrete questions. Which tokens exist here? What does this class generate? Why is one declaration winning? Is this suggested change valid for this project?

The Master CSS language service brings project-aware completion and CSS inspection into the editor. You can discover the vocabulary while writing, inspect the generated result on hover, and work with color information without leaving the source. Custom definitions become part of that context.

Linting carries that understanding into review. The available rules can identify invalid classes, report conflicting declarations and keep class order consistent. Optional policies can make a team’s expectations about tokens and raw values explicit. A diagnostic is most useful when it points to a concrete decision you can fix.

<ReleaseIllustration name="tools" />

In the illustrated example, `p-md p-lg` contains two competing padding classes. The tooling reports that `p-lg` is overridden in the generated CSS; its safe fix keeps `p-md`. The order of words in an HTML class attribute does not decide CSS precedence. Inspecting the generated rules gives the editor, the reviewer and the author the same explanation.

That project context is also available to coding agents through the Master CSS MCP server. An agent can query the actual manifest, inspect a class, lint a proposed change and request a fix preview. Applying the preview checks that the affected files still match the source it was prepared against. The workflow makes a proposed edit concrete and reviewable.

That gives a team a shared basis for decisions. The person writing a card, the reviewer checking its CSS and the agent helping refine it can all consult the same definitions. A suggestion can arrive with the generated rule, the diagnostic or the proposed diff that explains it. You can examine the evidence and keep shaping the result.

Bring that context into your process with the [Language service](/guide/language-service), [Code linting](/guide/code-linting) and [AI coding workflow](/guide/ai-coding).
