# AI Notes For `@master/css-vite`

## Responsibility

`@master/css-vite` integrates Master CSS into Vite. It supports `runtime`, `static`, `pre-render`, and `progressive` modes.

## Owns

- Vite plugin orchestration and mode behavior.
- Manifest, runtime program and emittedGlobals virtual modules.
- Shared scanner usage graph lifecycle.
- Stylesheet entries, runtime/virtual CSS imports, FOUC handling, HMR, and HTML pre-rendering.
- Final runtime stylesheet sidecars and emitted-global metadata after complete graph collection.

## Does Not Own

- Core runtime behavior.
- Engine CSS output semantics.
- Project manifest discovery internals.
- Scanner extraction semantics.
- Framework-specific lifecycle behavior outside Vite adapters.

## Public Surface

- Named `createMasterCSSVitePlugin()` factory and ecosystem default export.
- `MasterCSSVitePluginOptions`.
- Project manifest, runtime program (`virtual:master-css-program`, `?master-css-program`)
  and emitted-globals virtual modules. Browser code imports the program; server code the
  manifest.

The runtime bootstrap is generated by `@master/css-internal` and resolved as
`virtual:master-css-runtime`; it is not a public package subpath.

## Key Files

- `src/core.ts`
- `src/options.ts`
- `src/common.ts`
- `src/modes/*`
- `src/plugins/*`

## Risk Areas

- Scanner lifecycle is shared by every mode.
- `static` mode differs by `includeGeneratedCSS`; the style entry pipeline is not static-only.
- `virtual:master-css-manifest` is the project-level manifest API and must not manage stylesheet output or scanner usage.
- `virtual:master-css-emitted-globals` describes delivered variable/definition counts and native resource slots. Build output must use the completed graph, not module-load-time collection state.
- Builder environments may resolve separate configurations, each with its own plugin context. The emitted-globals plugin's `api` is shared across them; adapters whose build links one environment's CSS beside another environment's bundle set `api.finalize` to adjust what each environment's output carries. Plain Vite builds leave it unset.
- Dev class discovery refreshes generated modules per environment (`utils/dev-module-refresh.ts`): browsers take HMR updates, while server environments only invalidate, except the self-accepting server emitted-globals module, which updates one object in place. A server HMR reload restarts module runners such as SvelteKit 3's under in-flight renders.
- Production output must not depend on the checkout path: graph fragments are named by their rendered CSS, local slots hash root-relative module IDs, and production manifests and the programs compiled from them, emitted or inline, omit `source` provenance (`toProductionManifestJSON`). Development manifests keep absolute sources for diagnostics.
- Client builds emit the program as a `master-css-program.bin` asset and runtime mode preloads it (`program-preload.ts`, `rel=preload as=fetch crossorigin`); progressive mode never preloads it.
- Server builds load emitted manifest assets from disk. Vite 8.3+ renders plugin file URLs as public `base` URLs, so `resolveFileUrl` keeps server manifest references chunk-relative, and server detection uses the plugin environment because environment builds share one config.
- HTML entry detection in FOUC transforms.
- Runtime HTML injection and Vite HTML transform interactions.
- Static rendering HMR and SvelteKit pre-render skip behavior.

## Safe Changes

- Focused plugin-mode fixes.
- Entry injection fixes with snapshots.
- Virtual CSS/HMR fixes with tests.

## Dangerous Changes

- Changing default mode or option defaults casually.
- Changing injected runtime code without runtime/integration validation.
- Changing virtual module IDs casually.
- Scanning the workspace here to discover unimported CSS manifest entries.
- Adding multi-plugin files under `src/plugins`; each should define one plugin and default-export it.
